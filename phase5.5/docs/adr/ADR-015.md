# ADR-015：节点故障检测与路由回收

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/registry/keeper.go`、`internal/registry/redis.go`、`internal/registry/registry.go`
- 关联文档：[架构说明](../architecture.md)、[ADR-013](ADR-013.md)、[ADR-014](ADR-014.md)、[集群测试报告](../cluster-test-report.md)

## 1. 背景

集群中的路由指向具体节点。节点可能以三种方式离开：

- 正常退出：进程收到信号，关闭监听、注销自己。
- 崩溃：进程被杀死或机器断电，没有机会执行清理。
- 网络分区：进程还活着，但其它节点无法访问它，或它无法访问 Redis。

路由如果不回收，发送方会持续把消息转发给一个不存在的节点：实时投递失败，重试又被“路由指向存活节点”的判断挡住，消息只能等客户端 PULL。需要一个自动、可幂等重放的回收机制。

## 2. 问题

1. 如何判断一个节点已经死亡，而不依赖它自己上报。
2. 如何在多节点同时清理时避免重复劳动和竞态。
3. 如何只删除“确实属于该死节点”的路由，不误删已被新节点接管的路由。
4. 回收失败或执行到一半时，如何保证下一次还能继续。
5. 故障窗口有多大，如何向使用方说明。

## 3. 候选方案

### 3.1 客户端上报节点死亡

客户端发现连接断开后向其它节点报告。

- 优点：不需要额外的检测机制。
- 缺点：客户端可能直接退出、掉网或永久离线，无法保证有人上报；上报内容不可信；无法覆盖“节点上没有活跃客户端”的情况。
- 结论：不采用。

### 3.2 PostgreSQL 租约表

每个节点在 PostgreSQL 中续租一行，清理任务删除过期租约及其路由。

- 优点：复用现有数据库；租约与路由可以放在同一事务里；强一致。
- 缺点：把在线状态的高频心跳写入主库；需要额外的表、索引与清理任务；增加 vacuum 压力；节点死亡后的回收仍然需要扫描，和 Redis TTL 相比没有明显优势。
- 结论：不采用。PostgreSQL 继续只保存可靠投递数据。

### 3.3 Gossip 失败检测

节点互探测，失败信息在集群内传播。

- 优点：无中心依赖；分区检测更细。
- 缺点：需要成员列表与代际号，收敛与误判处理复杂；当前规模下收益不足；仍然需要解决路由归属与回收竞态。
- 结论：不采用。

### 3.4 Redis TTL + 清理锁 + 定向索引（本决策）

节点心跳续期自己的 hash TTL；任意存活节点定期扫描 `nodes` 集合，对 hash 已过期的节点加清理锁，按 `node_routes` 索引逐条校验并删除路由。

- 优点：TTL 自动表达“失联”；清理逻辑简单、可重入；锁避免并发清理；定向索引避免全键扫描。
- 缺点：检测有延迟；Redis 故障时无法心跳；节点在 Redis 不可达但自身仍存活时会被误判。
- 结论：采用。

## 4. 决策

1. 节点注册写入 `node:<id>` hash（`addr`、`started_at`），设置 `node_ttl` 过期时间，并把 ID 加入 `nodes` 集合。
2. Keeper 每 `heartbeat` 执行一次 `PEXPIRE node:<id> node_ttl` 并 `SADD nodes <id>`；心跳失败只记录警告，不退出进程。
3. Keeper 每 `cleanup` 执行一次 `SweepDeadNodes`。扫描顺序按 node ID 排序，保证测试与日志可复现。
4. 对 `nodes` 中每个 ID，先检查 `node:<id>` 是否存在；存在则跳过。
5. 对不存在的节点，用 `SET node_cleanup:<id> <id> NX PX 30000` 抢清理锁；抢不到说明其它节点正在清理，跳过。
6. 拿到锁后再次检查 `node:<id>` 是否存在；如果节点在两次检查之间恢复心跳，释放锁并跳过。
7. 读取 `node_routes:<id>`，对其中每个路由键执行 Lua 脚本：只有路由 hash 的 `node` 字段仍等于该死节点 ID 时才 `DEL`。
8. 删除 `node_routes:<id>` 索引，从 `nodes` 集合移除该 ID，最后用比较并删除的 Lua 脚本释放锁。
9. 正常退出时，Keeper 先停止心跳循环并等待其退出，再执行 `DeregisterNode`：删除节点 hash、从 `nodes` 移除、删除路由索引。这样最后一次心跳不会把节点写回去。

## 5. 故障窗口

节点在最后一次成功心跳之后失联，其 hash 在 `node_ttl` 后过期；清理任务在下一个 `cleanup` 周期发现并回收。因此：

```
最大回收延迟 = node_ttl + cleanup_interval
```

默认配置为 `15s + 10s = 25s`。测试使用 `node_ttl = 1.5s`、`cleanup = 0.5s`，理论上限 2.0s，实测 `relayx:node:node3` 与 `relayx:node_routes:node3` 在 2.19s 后被回收，与计算同量级（含命令行与 Redis 往返开销）。

需要注意：

- 窗口从最后一次成功心跳开始计算，不是从进程崩溃的瞬间开始。
- 在 hash 过期但尚未被清理的区间内，`LookupNode` 仍可能返回节点，发送方会把消息转发到一个已死地址；转发失败后，投递行保持 SENT，等清理完成后由 PULL 恢复。
- 清理周期是离散的，实际延迟在 `node_ttl` 到 `node_ttl + cleanup_interval` 之间。
- 如果节点只是与 Redis 失联而进程仍存活，它会被当作死亡节点回收；这是可用性优先的取舍，见第 7 节。

## 6. 幂等性与不误删

### 6.1 清理锁

- 锁的值就是该死节点 ID，只有创建锁的清理者能释放；`releaseCleanup` 用 `GET == id` 的 Lua 比较后删除，不会误删其它清理者的锁。
- 锁 TTL 为 30s，明显大于单次清理的预期耗时；清理者崩溃时锁会自动过期，下一轮可以重新抢锁。
- 锁的粒度是“单个死节点”，不同节点可以由不同清理者并行处理。

### 6.2 二次检查

`Exists` 与 `SetNX` 之间节点可能恢复心跳。拿到锁后再次 `Exists`，如果节点已恢复则释放锁并跳过。这覆盖了绝大多数“刚过期又复活”的情况。

仍存在一个窄窗口：节点在二次检查之后、逐条删除路由之前恢复心跳。此时它的 hash 已经重新存在，但清理者已经进入删除阶段，可能删掉该节点仍然有效的路由。该节点不会自动重发路由，受影响设备需要重新登录才能恢复跨节点路由；本地投递与 PULL 不受影响。这是本设计的已知残余风险，当前规模下可接受。

### 6.3 路由归属校验

`sweepRouteScript` 不是无条件删除，而是先 `HGET route node`，只有仍等于该死节点 ID 才删除。因此：

- 路由已经被新登录节点接管（`node` 字段变化），不会被删。
- 路由已经被正常关闭删除（键不存在），脚本返回 0，是空操作。
- 旧节点关闭会话时使用版本 + 节点双校验删除，也不会删掉新路由（见 ADR-013）。

### 6.4 重放与部分失败

- 清理到一半失败：已经删除的路由不会复活；索引和 `nodes` 成员可能还在，下一轮会继续处理，已删除的键再次删除是空操作。
- 删除索引失败：路由可能已删完，但索引残留；下一轮会再次扫描，仍然幂等。
- 删除 `nodes` 成员失败：下一轮 `Exists` 为 0，会重新抢锁并走一遍空操作。
- 锁释放失败：锁在 30s 后自动过期，不影响最终收敛。

### 6.5 正常退出

`Keeper.Stop` 先关闭 `stopCh` 并 `Wait`，确保没有正在进行的心跳，然后 `DeregisterNode`。因为 Gateway 在 `Keeper.Stop` 之前已经 `srv.Shutdown`，正常关闭的会话已经用版本 CAS 删除了自己的路由；`DeregisterNode` 删除索引只是兜底。如果关闭过程中有会话没来得及删除路由，这些路由会失去索引，成为不可回收的残留键；但节点 hash 已删除，`NodeAlive` 为 false，发送方不会再把它们当作在线目标，后续登录也会覆盖同一路由键。

## 7. 失败场景

| 场景 | 表现 | 恢复 |
| --- | --- | --- |
| Gateway 崩溃 | 节点 hash 到期，客户端 TCP 断开并切换节点 | 清理回收路由；客户端在新节点登录后 PULL |
| Gateway 被 `Stop-Process -Force` 杀死 | 无注销流程，索引残留 | 心跳停止，TTL 到期后按索引回收；测试中 2.19s 完成 |
| 节点与 Redis 失联但进程存活 | 心跳与路由查询失败；其它节点视其为死亡并回收路由 | Redis 恢复后心跳会重新 `RegisterNode` 重建已丢失的 node hash，节点自愈；但路由不会自动重发，设备需重新登录。本地投递与 PULL 仍可用 |
| Redis 在清理过程中故障 | 当前脚本报错，清理中止，锁可能残留 | Redis 恢复后锁过期或下一轮重试；部分删除不影响正确性 |
| Redis 数据丢失 | `nodes`、`node:*`、路由、版本计数全部消失 | 存活节点会通过心跳重新 `RegisterNode` 自愈；路由要等客户端重新登录；SEND 将目标视为离线，PULL 不依赖 Redis |
| 节点重启但复用同一 node ID | 新 hash 出现，旧路由可能仍指向该 ID | 新节点收到转发后找不到会话，返回 NOT_FOUND；重试/PULL 恢复；新登录覆盖路由 |
| 两个进程使用同一 node ID | 节点连接互相替换，路由归属混乱 | 不支持；由部署方保证 node ID 唯一 |

## 8. 后果

正向：

- 不需要额外的探测组件；Redis TTL 直接表达失联。
- 清理是按死节点索引定向进行的，不需要 `SCAN` 全库。
- 锁、二次检查、路由归属校验与脚本幂等共同保证多清理者下不会重复或误删已迁移路由。
- 正常退出会主动注销，故障回收只处理异常路径。

负向：

- 崩溃场景下回收延迟至少为 `node_ttl`，默认场景下最长 25s；期间跨节点实时投递可能失败。
- 节点与 Redis 的网络分区会造成误判；恢复后心跳会重新 `RegisterNode` 重建已丢失的 node hash，但客户端重新登录才能恢复路由。
- 每个清理周期至少执行一次 `SMEMBERS nodes` 和每个节点的 `EXISTS`，节点数量很大时扫描成本线性增长。
- 清理单节点的耗时与 `node_routes` 大小成正比；30s 锁 TTL 是当前规模下的经验值，节点拥有大量路由时需要重新评估。
- 二次检查之后的窄窗口仍可能删除刚恢复节点的路由，属于已知残余风险。

## 9. 状态

Accepted。若未来需要更快检测或更强一致性，可以引入独立健康检查或 PG 租约，但必须重新评估误判成本与对主库的压力。
