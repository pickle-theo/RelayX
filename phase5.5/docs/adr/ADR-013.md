# ADR-013：使用 Redis 作为在线路由注册表

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/registry/redis.go`、`internal/registry/keeper.go`、`internal/registry/registry.go`、`internal/gateway/gateway.go`、`cmd/gateway/main.go`
- 关联文档：[架构说明](../architecture.md)、[ADR-014](ADR-014.md)、[ADR-015](ADR-015.md)、[集群测试报告](../cluster-test-report.md)

## 1. 背景

Phase 3 的 Gateway 是单进程：会话表、路由和可靠投递都在同一个进程与同一个 PostgreSQL 实例内完成。Phase 4 需要多个 Gateway 进程同时对外服务，并且：

- 任意节点都能获知某个 `(user, device)` 当前连接在哪个节点、哪个会话上。
- 同一设备跨节点重复登录时，旧节点上的旧会话必须被替换。
- 节点崩溃后，指向它的路由必须能被自动回收，不能永久把消息发给一个不存在的进程。
- PostgreSQL 继续作为消息与投递状态的唯一可靠存储，Redis 不能成为消息真值的来源。

## 2. 问题

需要一个“在线状态”的共享视图，满足以下约束：

1. 数据是易失的：进程退出、机器宕机后，相关记录应自动失效，不能依赖人工清理。
2. 读多写多：每次登录、断线、跨节点发送都会访问；延迟必须显著低于一次数据库写入。
3. 需要原子的“比较并删除”，避免旧会话在关闭时删掉新会话刚刚写入的路由。
4. 需要按节点回收，节点死亡后不能逐条依赖客户端上报。
5. 不能把消息 payload 放进这个共享视图，否则 Redis 会进入数据面关键路径。

## 3. 候选方案

### 3.1 方案 A：PostgreSQL 路由表

在现有 PostgreSQL 中新增 `node_routes` 表，用 `(user_id, device_id)` 做主键，记录 `node_id`、`session_id`、`version`、`updated_at`。

- 优点：不引入新组件；复用现有事务与运维体系；与 `deliveries` 可以放在同一个数据库里做一致性操作。
- 缺点：在线路由是高频、短生命周期数据，会给主库带来额外的写入与锁竞争；需要自己实现 TTL/租约清理任务；节点崩溃后的记录不会自动消失；表随登录/断线频繁更新，增加膨胀与 vacuum 压力；SEND 热路径会增加数据库往返。
- 结论：不采用。PostgreSQL 继续只承担消息、投递与回执等需要持久化的数据。

### 3.2 方案 B：Gossip / SWIM 成员协议

节点之间互相探测，并在集群内传播成员与路由变化。

- 优点：没有中心依赖；分区容忍度较好；天然去中心化。
- 缺点：路由收敛有延迟，冲突解决复杂；需要维护成员列表、代际号和反熵机制；当前集群规模很小，引入 Gossip 的实现与调试成本远高于收益；跨节点登录替换仍需要一个全局的版本来源或冲突规则。
- 结论：不采用。`Registry` 接口保留了未来替换实现的空间。

### 3.3 方案 C：Redis Pub/Sub 作为路由通道

用频道广播“某设备上线/下线”，各节点在本地维护路由缓存。

- 优点：事件驱动，正常情况下时延低；Redis 只做通知。
- 缺点：Pub/Sub 不保留状态，订阅者断线期间的事件会永久丢失；新节点启动时拿不到全量在线视图；无法直接回答“这个设备现在在哪”；需要额外的全量同步与补偿机制；仍然是 at-most-once。
- 结论：不采用。若未来需要降低轮询或缓存失效延迟，可以在当前注册表之上增加 Pub/Sub 通知，但不能替代可查询的路由状态。

### 3.4 方案 D：Redis 键值注册表（本决策）

用 Redis 保存节点成员与在线路由，路由带版本号，写入/删除用 Lua 保证原子性，节点用 TTL 心跳保活。

- 优点：TTL 与在线状态天然匹配；O(1) 查询；Lua 提供原子 CAS；实现小、可观测、易替换；不进入消息 payload 路径。
- 缺点：新增一个有状态依赖；登录路径强依赖 Redis；单实例没有 HA；需要处理故障检测窗口与误回收。
- 结论：采用。

### 3.5 方案 E：Consul / etcd 等服务发现

- 优点：成熟的租约、健康检查与 Watch 能力。
- 缺点：为当前规模引入额外的运维组件；仍然需要自己设计路由键与版本 CAS；Watch 的语义与断线补偿仍需处理。
- 结论：不采用。Redis 已经是本项目测试与部署中可接受的轻量依赖。

## 4. 决策

采用方案 D，并明确以下边界：

1. Redis 只保存两类数据：节点成员信息、在线路由。消息、投递状态、回执全部留在 PostgreSQL。
2. Gateway 只在配置了 `-redis-addr` 时启用集群；未配置时完全不连接 Redis，保持 Phase 3 单节点行为。
3. 路由是“提示”而不是“承诺”：发送方查到路由后仍可能投递失败，可靠性由 `deliveries` 的 SENT 行、owner 节点重试和 PULL 兜底。
4. 所有路由写入与删除都通过 Lua 脚本完成，脚本同时维护 `node_routes:<id>` 索引。
5. 节点通过心跳续期自己的 TTL；死亡节点由任意存活的节点在清理周期内回收。
6. `Registry` 是接口，Redis 实现可以被内存实现（测试）或其他后端替换；`gateway` 只依赖接口。

## 5. 键与版本 / CAS 设计

默认前缀为 `relayx:`。前缀在 `registry.RedisConfig` 中可配置，但 Gateway 当前没有暴露前缀命令行参数，实际部署使用默认值。

| 键 | 类型 | 内容 | TTL |
| --- | --- | --- | --- |
| `relayx:nodes` | SET | 所有已注册的 node ID | 无 |
| `relayx:node:<id>` | HASH | `addr`、`started_at` | `node_ttl`，心跳续期 |
| `relayx:route:<user>\x00<device>` | HASH | `node`、`session`、`version`、`created_at` | 无，断线/回收时删除 |
| `relayx:ver:<user>\x00<device>` | STRING | 单调递增的登录版本号（`INCR`） | 无 |
| `relayx:node_routes:<id>` | SET | 该节点拥有的完整路由键 | 无 |
| `relayx:node_cleanup:<id>` | STRING | 回收锁，值为该死节点 ID | `PX 30000` |

`<user>` 与 `<device>` 使用 `\x00` 分隔，避免用户 ID 或设备 ID 中含冒号时产生歧义；Redis 键是二进制安全的。

### 5.1 登录版本

登录时先执行 `INCR relayx:ver:<user>\x00<device>` 得到新版本，再创建本地会话，最后写入路由。版本号：

- 从 1 开始，单调递增，不回退。
- 被写入路由 hash 的 `version` 字段，也被放入 `NODE_KICK` 帧。
- 接收踢人请求的节点只有在本地会话版本小于帧内版本时才关闭连接，防止延迟到达的旧踢人请求误伤新会话。

### 5.2 路由写入（upsert）

`UpsertRoute` 通过一段 Lua 原子执行：

1. 读取旧路由的 `node` 字段。
2. `HSET` 写入 `node`、`session`、`version`、`created_at`。
3. 如果旧 `node` 存在且与新 `node` 不同，从旧节点的 `node_routes:<old>` 集合中移除该路由键。
4. 把路由键加入新节点的 `node_routes:<new>` 集合。

这样路由迁移和索引迁移在同一次脚本内完成，不会出现“路由已经指向新节点、索引还挂在旧节点”的中间状态。

### 5.3 路由删除（version + node 双校验 CAS）

会话关闭时，节点用 `DeleteRouteIfVersion(user, device, version, node)` 删除路由。Lua 脚本同时检查：

- 路由 hash 中的 `version` 是否等于调用方持有的版本；
- 路由 hash 中的 `node` 是否等于调用方节点。

两者都匹配才执行 `DEL`，并从 `node_routes:<node>` 中移除。典型场景：

- 设备从 node3 登录到 node2，路由版本从 5 变为 6。node3 上旧连接稍后关闭，携带版本 5 删除，脚本发现存储版本是 6，直接返回 0，不会删掉 node2 的新路由。
- 路由已经迁移到其他节点，旧节点即使版本号相同（例如 Redis 数据丢失后计数器重置），`node` 不匹配也会阻止误删。

### 5.4 回收索引

`node_routes:<id>` 是“该节点可能拥有哪些路由”的索引，用于节点死亡后的定向回收，避免全库 `SCAN`。索引本身不保证与路由强一致：

- 正常删除和迁移会维护索引。
- 节点崩溃时索引残留，由清理流程按索引逐条校验后删除。
- 索引中的键可能已经不存在，回收脚本对不存在的路由是空操作。

### 5.5 版本/节点校验的边界

版本 CAS 解决的是“旧会话关闭时误删新路由”，不解决“同一设备同时登录两个节点”的竞争：两个节点各自 `INCR` 得到不同版本，各自写入路由，Redis 以最后一次 `UpsertRoute` 为准；没有获得路由的会话不会被主动踢掉，直到它自然断开或再次登录。该行为在“已知限制”中明确列出，不作为强一致承诺。

## 6. 后果

### 6.1 正向

- 在线状态具备自动过期能力，节点崩溃后无需人工清理。
- 登录、断线、跨节点发送的路由操作都是 O(1)，且不触碰 PostgreSQL 的消息表。
- Lua 保证路由与索引的原子迁移，旧会话关闭不会误删新会话。
- Redis 不保存 payload，消息可靠性仍由 PostgreSQL 保证；Redis 故障时已持久化的消息不丢。
- 通过 `Registry` 接口隔离，未来可以替换为 etcd、Consul 或自研实现。

### 6.2 负向

- 登录路径强依赖 Redis：Redis 不可用时新登录返回 `LOGIN_ACK internal`（日志为 cluster unavailable），发起登录的客户端退出。已建立会话不受影响。
- Redis 在当前部署中是单点，没有 HA；示例配置没有 TLS 和密码，生产环境必须自行加固。
- 故障检测存在窗口：节点死亡后，路由最长在 `node_ttl + cleanup_interval` 内仍可能被发送方视为在线。
- Redis 数据丢失（未持久化、容器重建，或停机超过 `node_ttl`）会丢失全部节点与路由记录。心跳会重新 `RegisterNode` 并重建节点 hash，因此存活节点在 Redis 数据丢失或 TTL 过期后可自愈；但路由键仍需客户端重新登录才会重建。
- `relayx:ver:*` 计数器不设 TTL，设备数量很大时会持续累积键；当前未做清理。
- 每次登录至少增加 `INCR`、`LookupRoute`、`UpsertRoute` 三次 Redis 往返；每次跨节点 SEND 需要 `LookupRoute` 与 `LookupNode`。

## 7. 已知限制

- Redis 不可用时不能完成新登录；SEND 仍会持久化，远程目标会被当作离线并写成 PENDING，PULL 不依赖 Redis。
- Redis 单实例无 HA、无 TLS、无认证示例；不得暴露到不可信网络。
- 路由是最终一致的在线提示，不是强一致锁；并发登录同一设备时以最后一次写入为准。
- 节点 ID 的唯一性由部署方保证；两个进程使用同一 `node_id` 会导致节点连接互相替换。
- 节点故障窗口为 `node_ttl + cleanup_interval`，默认 15s + 10s；测试使用 1.5s + 0.5s。
- Redis 数据丢失或节点 hash 过期后，心跳会重新 `RegisterNode` 重建节点记录（有集成测试覆盖），但路由键仍需客户端重新登录才会重建。

## 8. 状态

Accepted。后续如引入 Redis Sentinel/Cluster、TLS 或路由缓存，应新增 ADR，不修改本决策的边界：Redis 仍然只做在线发现与路由，不承载消息 payload。
