# ADR-011：传输写路径、连接内存与数据库并发优化

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/transport/conn.go`、`internal/transport/server.go`、`internal/config/config.go`、`internal/store/store.go`
- 关联文档：[瓶颈分析](../bottleneck-analysis.md)、[优化报告](../optimization-report.md)、[ADR-010](ADR-010.md)

## 1. 背景

Phase 2 基线在 10k 连接时每连接约 14.7KB 堆、20,007 个协程；可靠链路在
1000 msg/s 时出现 p50 4.3s、p99 10.7s、13,812 条 ACK 丢失。profile 显示：

- `Syscall6` 32%–35%、`futex` 28%–30%，写路径 `writeBatch` cum 30%、`writeLoop` cum 36%；
- `heap-top` 中 `transport.newConn` 50%、`bufio.NewReaderSize` 33%；
- 可靠链路 985/1000 个读协程停在 `database/sql.(*DB).conn`，池仅 16 个连接。

## 2. 当前问题

1. 每批写都要把所有帧拷贝进一个拼接缓冲，能否零拷贝？
2. 每次写后重置写 deadline 是否必要？
3. 每连接发送队列 256 槽、读缓冲 4KB 是否过大？
4. 数据库连接池 16 是否是可靠链路的吞吐上限？提到多少合适？

## 3. 候选方案

### 3.1 批量写

- **拼接缓冲（现状）**：一次 `Write`，但每批一次 `memmove` 与一块最大 64KB 的分配。
- **`net.Buffers` + writev（本决策）**：内核一次 `writev` 写多个切片，无拼接拷贝；
  代价是需要一个临时切片副本，因为 `WriteTo` 会消费传入切片。
- **`syscall.Writev` 手写**：最直接，但需要自己处理部分写、EAGAIN 与 deadline，
  跨平台差，不值得绕开 `net`。
- **每帧一次 `Write`**：实现最简单，但 10k 高频时系统调用翻倍，已被基线否决。

### 3.2 写 deadline

- **写前设置 + 写后重置（现状）**：两次系统调用，重置是为了「避免 deadline 泄漏到下一次写」。
- **写前设置、不重置（本决策）**：每次写都会重新设置绝对时间，零值重置纯属多余。
- **全局固定 deadline**：无法表达「单次写超时」，慢消费者会长时间占用写协程。

### 3.3 每连接内存

- **保持 256 槽 + 4KB 读缓冲**：突发吸收能力最强，但每连接约 14.7KB。
- **64 槽 + 1KB 读缓冲（实验后回退队列）**：空闲堆可降到 80.13MB（-45.7%），
  但 PULL 单页 100 条 DELIVER 加 PULL_DONE 会超过 64 槽，`Send` 按慢消费者
  关闭连接，`TestPullPagination` 稳定失败；因此只保留 1KB 读缓冲。
- **无缓冲/直接 `Write`**：失去批量合并与背压计数，不可取。

### 3.4 数据库并发

- **保持 16 连接**：profile 显示排队 985 个协程。
- **提升到 64（本决策）**：四倍并发，PostgreSQL 侧仍远未打满（8 核、连接空闲多）。
- **提升到 256+**：可能压垮数据库并放大锁竞争，本轮没有证据支持。
- **把持久化移出 readLoop**：理论上最优，但改动大、需要重新定义 ACK 顺序与背压，
  留作第三轮候选。

## 4. 决策

| # | 决策 | 关键实现 |
| --- | --- | --- |
| 1 | 批量写使用 `net.Buffers.WriteTo`（writev） | `writeBatch` 先扫描 CLOSE 帧、累计字节，再 `bufs.WriteTo(c.nc)`；成功后统一归还 encode buffer 与扣减 `queuedBytes` |
| 2 | 复用批次切片 | `Conn.batchBuf` 复用帧列表；`Conn.bufs` 作为 writev 的临时切片，保护原列表用于归还 |
| 3 | 删除写后 deadline 重置 | 每次写前 `SetWriteDeadline(now+writeTimeout)`，成功后不再重置 |
| 4 | 发送队列保持 256 | 64 槽实验导致 PULL 分页回归，已回退；字节预算 `-send-queue-bytes` 保持 4MB |
| 5 | 读缓冲 4096 → 1024 | 小控制帧走缓冲，大 body 由 `bufio` 直读 |
| 6 | 数据库连接池 16 → 64 | `-db-max-open-conns` 与 `store.DefaultMaxOpenConns` 同步 |

## 5. 选择理由与证据

1. **writev 消除每批拼接拷贝**：10k 高频 45s 时活跃堆 201.72MB → 176.47MB（-12.5%），
   15s 时点 169.53MB → 142.78MB（-15.8%），吞吐 370,807 → 370,769（噪声内）。
2. **去掉 deadline 重置**：每批少一次系统调用；profile 中 `Syscall6` 占比未变，
   说明该场景由阻塞 I/O 主导，收益体现在系统调用次数而不是 CPU 百分比。
3. **读缓冲 1KB**：10k 空闲堆 147.45MB → 129.08MB（-12.5%），
   每连接 14.75KB → 12.91KB；10k 高频堆 176.47MB → 119.83MB，
   相对基线 201.72MB 下降 40.6%，吞吐与错误率不变。
4. **发送队列 64 被否决**：虽然能把空闲堆降到 80.13MB（-45.7%），
   但 `TestPullPagination` 在真实 PostgreSQL 上稳定报 `decode frame: EOF`，
   原因是 PULL 单页 100 条 DELIVER 加 PULL_DONE 超过 64 槽后连接被当作慢消费者关闭。
   保留 256 槽是正确性要求，不是性能取舍。
5. **数据库池 64**：可靠链路 1000 msg/s 的 p50 4323ms → 1726ms（-60.1%）、
   ack_missed 13,812 → 1,916（-86.1%）；但仍未闭环，证明池只是限制之一。
6. **保留而不是回退**：两轮都至少改善一项核心指标，且没有 ≥20% 的吞吐或正确性退化。

## 6. 已知限制

1. **可靠链路 1000 msg/s 仍未闭环**：`deliveries_pending` 仍增长，
   每消息 4 次数据库往返与同步读路径是剩余上限。
2. **p99 轻微上升**：10k 高频 profile 档 p99 1.318ms → 2.054ms，
   绝对值仍 <3ms，未观察到用户可见退化；需要更精确的容量结论时应做多次中位数。
3. **writev 的切片副本**：`Conn.bufs` 每连接多占约 384B（16 个指针），
   已在第二轮内存收益中抵扣。
4. **小读缓冲的 syscall 次数**：1KB 缓冲在 64B 载荷下约 9 帧/次读，
   大载荷时 syscall 由 body 大小决定；没有单独统计 syscall 次数。
5. **池 64 是经验值**：没有继续扫描 32/96/128；PostgreSQL 侧仍未饱和，
   更高值可能继续改善，但也会放大数据库压力。

## 7. 被否决 / 暂缓的方案

- **每帧一次写**：系统调用翻倍，基线已证明不可取。
- **手写 `syscall.Writev`**：需要自行处理部分写与 deadline，风险大于收益。
- **无限增大写批次**：会拉高单连接延迟，且高频场景队列通常只有 1 帧。
- **把持久化移出 readLoop（暂缓）**：需要重新定义 ACK 顺序、背压与崩溃语义，
  属于第三轮架构改动，不在本轮「低风险、可回退」的范围。
- **ACK 批量写入（暂缓）**：预计能把每消息 4 次往返降到 2 次，但需要新增队列与
  合并 SQL，本轮时间预算不足；已记录为下一步。
- **共享时间轮替代每连接 Timer（暂缓）**：10k 时定时器 CPU 约 1%–2%，
  当前不是瓶颈；50k 以上再评估。

## 8. 后续演进方向

1. ACK 批量写入：`unnest` 一次落多条回执，并批量重算消息状态。
2. 持久化工作队列：readLoop 只入队，固定 worker 池执行数据库操作，队列满时回压。
3. 心跳定时器共享化：按秒级时间轮驱动，减少 50k 连接时的定时器堆。
4. 对 `-db-max-open-conns` 做 32/64/96 扫描，找到数据库侧拐点。
5. 用 `SO_REUSEPORT` 多监听 + 多进程分摊 50k 以上连接。
