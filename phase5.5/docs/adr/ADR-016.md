# ADR-016：Outbox + Kafka 实现至少一次投递

- 状态：已接受（Accepted）
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/store/outbox.go`、`internal/outbox/relay.go`、`internal/broker/broker.go`、`internal/broker/events.go`、`internal/engine/fanout.go`
- 关联文档：[架构说明](../architecture.md)、[Outbox 与 Kafka](../outbox-and-kafka.md)、[ADR-017](ADR-017.md)

## 1. 背景

Phase 4 的 SEND 在同一个数据库事务里写 `messages` 与 `deliveries`，然后在连接协程里直接投递。这个模型有两个硬约束：

- 收件人展开必须在受理请求内完成，受理延迟随收件人数量线性增长。
- 投递由持有连接的 Gateway 推进；Gateway 重启会中断进行中的重试，且多节点之间没有统一的投递调度。

Phase 5 要把受理与投递拆开。拆分后必须回答一个问题：消息已经提交，但「通知下游去展开收件人」这个动作如何可靠地发生？如果受理事务提交后进程崩溃，通知就丢了；如果先发通知再提交，下游可能读到不存在的消息。

## 2. 问题

1. 如何让「消息落库」与「事件发布」具有同一个原子边界。
2. 发布失败、进程崩溃、Kafka 长时间不可用时，如何保证事件不丢失。
3. 如何允许 relay 水平扩展，同时不重复发布同一行、不产生长时间等待。
4. 下游重复收到事件时，如何不产生重复投递。
5. 如何在不引入分布式事务组件的前提下，把语义明确为「至少一次」并让使用方接受。

## 3. 候选方案

### 3.1 受理事务直接写 deliveries，由数据库轮询推进

不引入 Kafka，受理时仍展开收件人，Worker 直接扫描 `deliveries` 表推动重试。

- 优点：无新增中间件；状态只有一处；实现最简单。
- 缺点：受理延迟与收件人数成正比；大 V 用户或广播场景会把长事务压在受理路径；扫描与受理争用同一批行与索引；无法把「展开」与「投递」独立扩缩容。
- 结论：不采用。它没有解决 Phase 5 要解决的核心问题。

### 3.2 两阶段提交（DB + Kafka 事务）

用 XA 或 Kafka 事务把数据库写入与消息发布绑定。

- 优点：理论上可做到原子可见。
- 缺点：Kafka 不支持 XA；Kafka 事务只覆盖 Kafka 自身，数据库提交仍无法与它原子；需要事务协调者、超时与悬挂事务处理；运维与故障排查成本高。
- 结论：不采用。收益不足以抵消复杂度，且无法真正消除跨系统不确定性。

### 3.3 CDC（Debezium 读取 WAL）

用变更数据捕获工具订阅 `messages` 的插入，转换成 Kafka 事件。

- 优点：应用无需写 outbox；事件与数据库变更严格对应；可复用于其它表。
- 缺点：引入 Connect 集群、连接器、schema registry 等一整套组件；需要数据库复制权限与逻辑复制槽；本地开发与测试环境显著变重；故障域从应用转移到运维平台。
- 结论：不采用。当前项目规模不需要为此付出额外的部署复杂度。

### 3.4 事务性 Outbox + Kafka（本决策）

受理事务只写 `messages` 与 `outbox`，由独立 Relay 用 `FOR UPDATE SKIP LOCKED` 领取并发布到 Kafka。

- 优点：原子边界就是本地数据库事务；Relay 可水平扩展；Kafka 停机不影响受理；积压可观测（`outbox` 行数与 `attempts`）；实现只依赖已有 PostgreSQL。
- 缺点：至少一次，存在重复事件；需要额外的表、索引与 relay 进程；已发布行需要自行清理；事件延迟受 relay 轮询间隔影响。
- 结论：采用。

## 4. 决策

1. 受理事务在插入消息后，向 `outbox` 写入一行：`topic = relayx.fanout.v1`、`partition_key = tenant|user`、`payload` 为预编码的 `FanoutEvent`（`version = 1`）。任何一步失败整体回滚。
2. `outbox.state` 只有两个值：`0` 待发布、`1` 已发布。部分索引 `outbox_pending_idx (next_attempt_at, id) WHERE state = 0` 只服务待发布扫描。
3. `RelayOutbox` 在一个事务内 `SELECT ... WHERE state = 0 AND next_attempt_at <= now() ORDER BY id LIMIT n FOR UPDATE SKIP LOCKED`；逐条 `Publish`，成功置 `state = 1, published_at = now(), attempts = attempts + 1`。
4. 发布失败时 `attempts + 1`，`next_attempt_at = now() + LEAST(base * 2^attempts, max)`，本批立即停止并返回错误；行保持 `state = 0`。
5. 行锁持有到事务提交，因此同一行不会被两个 Relay 同时发布；发布失败后的退避上限默认 1m。
6. 生产者使用 `acks=all`、同步发布（`Async=false`）、`Hash` 分区器；只有 broker 确认后才标记为已发布。
7. 发布到 `relayx.fanout.v1` 的事件由 fan-out Worker 消费：先 `InsertDeliveries`（`ON CONFLICT (message_id, user_id, device_id) DO NOTHING`），再向 `relayx.deliver.v1` 发布唤醒事件。
8. 消费端手动提交 offset：处理函数返回 nil 才 `CommitMessages`；基础设施错误返回错误、offset 不提交，靠重投重试。
9. 系统语义明确为**至少一次**：允许重复事件、重复投递；重复由受理幂等键、投递行唯一约束、租约条件更新与客户端 `message_id` 去重共同吸收。
10. 已发布的 outbox 行不删除，保留审计与排障能力；当前规模下由运维按需清理。

## 5. 后果

### 5.1 正面

- 受理延迟与收件人数解耦，SEND 只做一次消息插入与一次事件插入。
- 原子性由本地事务保证，不需要跨系统协调者。
- Kafka 停机时受理仍然成功，事件在 outbox 中积压，恢复后自动追平。
- Relay 可以多实例并行，`SKIP LOCKED` 避免相互等待。
- 事件与投递状态分离：事件丢失只影响延迟，不影响数据库真值。
- 能够按主题、分区键控制顺序：同一 `tenant|user` 的事件进入同一分区。

### 5.2 负面

- 至少一次意味着重复：受理事务提交前崩溃会导致事件重发；fan-out 必须幂等，客户端必须按 `message_id` 去重。
- 事件延迟至少是一个 relay 轮询周期（默认 500ms），再叠加 fan-out 消费与 Worker 扫描间隔。
- Relay 在事务内发布并持有行锁，Kafka 变慢会拉长事务与锁持有时间，需要控制批大小并监控。
- `attempts` 在成功时也递增，语义是「发布尝试次数」而不是「失败次数」，排障时容易误读。
- 已发布行不清理会让 `outbox` 表持续增长；部分索引降低了查询成本，但存储与 vacuum 成本仍在。
- 需要额外维护 Kafka（本地为 KRaft 单 broker、单副本），部署面比 Phase 4 更重。

## 6. 状态

已接受。若未来需要「恰好一次」端到端语义，需要同时改造消费端 offset 与业务写入的原子性（例如把消费结果写入同一数据库并用事务提交 offset），成本显著上升，当前不采用。
