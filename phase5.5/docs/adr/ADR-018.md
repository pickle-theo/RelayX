# ADR-018：多租户令牌桶限流

- 状态：已接受（Accepted）
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/tenant/limiter.go`、`internal/store/tenant.go`、`internal/store/migrations/0002_outbox_tenants_leases.sql`、`internal/engine/engine.go`、`internal/config/worker.go`
- 关联文档：[Engine 设计](../engine-design.md)、[架构说明](../architecture.md)、[ADR-017](ADR-017.md)

## 1. 背景

Phase 5 引入租户维度：消息带 `tenant_id`，同一套 Worker 为多个租户服务。如果某个租户瞬间产生大量投递，会占满 Worker 的推送并发、Redis 连接与数据库扫描能力，导致其它租户的延迟一起上升。需要在投递侧施加**按租户隔离**的背压，并且不能因为限流把消息判为失败。

## 2. 问题

1. 限额存在哪里、由谁读取，读取失败时是否阻断投递。
2. 如何同时限制速率与并发，两者的拒绝行为如何区分。
3. 被限流的投递如何延后，且不消耗重试次数。
4. 未配置的租户走什么默认值，如何避免「默认拒绝」。
5. 多 Worker 部署时，限额是全局还是进程内；这个差异如何向使用方说明。

## 3. 候选方案

### 3.1 全局 Redis 令牌桶

所有 Worker 共享 Redis 中的桶，用 Lua 原子取令牌。

- 优点：配额是全局的，语义直观。
- 缺点：每次投递增加一次 Redis 往返；Redis 故障会直接阻断投递；需要处理键过期、时钟与原子脚本；与 Phase 4「Redis 只做路由」的定位冲突。
- 结论：不采用。

### 3.2 Gateway 连接层限流

在 LOGIN/SEND 时按租户限制连接数或请求速率。

- 优点：在入口处削峰，保护受理链路。
- 缺点：限制的是受理而不是投递；投递侧的 fan-out、租约扫描与下游推送压力不受控；HTTP Message Service 不经过 Gateway，覆盖不全。
- 结论：不采用为投递限流，可作为未来入口限流的补充。

### 3.3 每次投递查询数据库计数

按租户统计当前在途投递数并据此拒绝。

- 优点：强一致，无缓存不一致。
- 缺点：每条投递一次聚合查询，扫描成本高；热点租户会把主库打满；无法表达速率。
- 结论：不采用。

### 3.4 租户表 + Worker 侧缓存令牌桶 + 在途信号量（本决策）

配额存在 `tenants` 表，每个 Worker 进程按租户维护一个令牌桶与在途计数，缓存 `-tenant-cache-ttl`。

- 优点：投递路径无额外远程调用；限流不依赖 Redis 可用性；速率与并发两个维度都能表达；配额变更可在缓存周期内生效。
- 缺点：配额是进程内的，`N` 个 Worker 的实际总速率约为 `rate * N`；缓存期内配额更新有延迟；Worker 重启会重置桶与计数。
- 结论：采用。

## 4. 决策

### 4.1 配额表

```sql
CREATE TABLE IF NOT EXISTS tenants (
    id           TEXT PRIMARY KEY,
    rate_per_sec INT  NOT NULL DEFAULT 0,
    burst        INT  NOT NULL DEFAULT 0,
    max_inflight INT  NOT NULL DEFAULT 0,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT tenants_rate_non_negative     CHECK (rate_per_sec >= 0),
    CONSTRAINT tenants_burst_non_negative    CHECK (burst >= 0),
    CONSTRAINT tenants_inflight_non_negative CHECK (max_inflight >= 0)
);

INSERT INTO tenants (id) VALUES ('default') ON CONFLICT (id) DO NOTHING;
```

- `rate_per_sec = 0` 表示不限速；`burst = 0` 时回退为 `rate_per_sec`。
- `max_inflight = 0` 表示使用 Worker 的 `-default-inflight`（默认 256）；`-default-inflight 0` 表示不限并发。
- 迁移预置 `default` 零配额行，保证默认租户不会因为缺行而被拒绝。

### 4.2 缓存

`Limiter.entry` 按 `-tenant-cache-ttl`（默认 30s）刷新配额：

- `cacheTTL <= 0` 时每次都重新读取。
- 查询返回「不存在」时按零配额处理（不限速 + 默认在途）。
- 查询返回错误时**不阻断投递**：已有缓存则继续使用旧配额；首次加载失败则使用零配额。
- `Forget(tenantID)` 删除缓存条目，下一次 `Acquire` 重新加载；供运维或测试在配额变更后立即生效。
- 缓存刷新不清空令牌与在途计数，桶状态跨刷新保持连续。

### 4.3 Acquire 顺序

`Acquire(ctx, tenantID, now)` 在单把互斥锁内完成：

1. 读取/刷新配额。
2. 解析在途上限：`quota.MaxInflight`，`<= 0` 用 `defaultInflight`。
3. 在途检查：`limit > 0 && inflight >= limit` → 返回 `retryAfter = 50ms`、`ok = false`。
4. 速率检查：`rate > 0` 时按 `elapsed * rate` 补充令牌，上限 `burst`；`tokens < 1` 时返回 `(1 - tokens) / rate + 1ms`、`ok = false`。
5. 扣一个令牌、`inflight++`，返回 `release` 与 `ok = true`。

令牌桶初始 `tokens = 1`、`last = now`，因此租户的第一条投递不会被误拒。

### 4.4 release

- `Engine.process` 在 `Acquire` 成功后 `defer release()`，覆盖推送成功、无路由、转发失败与提前过期等所有分支。
- `release` 用 `sync.Once` 包裹，重复调用不会重复递减。
- 递减前检查 `inflight > 0`，不会出现负数。

### 4.5 超限不消耗 attempts

被限流时 Engine 调用：

```go
e.retry(ctx, d, now.Add(retryAfter), false)
```

对应 `RetryLeased(incrementAttempts = false)`：

```sql
UPDATE deliveries
SET state = CASE WHEN $4 AND attempts + 1 >= $5 THEN 6 ELSE state END,
    attempts = attempts + CASE WHEN $4 THEN 1 ELSE 0 END,
    next_retry_at = $3,
    lease_until = NULL,
    worker_id = NULL,
    updated_at = now()
WHERE id = $1 AND worker_id = $2 AND state IN (0, 1)
```

当 `$4 = false` 时，`CASE` 恒取 `state`、`attempts` 加 0，即**只改 `next_retry_at`，不增加 `attempts`，不改状态**。这与「推送失败」明确区分：

| 结果 | attempts | next_retry_at | 是否可能变成 FAILED |
| --- | --- | --- | --- |
| 推送成功 | +1 | 按指数退避排下一次重推 | 否（state = 1） |
| 推送失败 | +1 | 按指数退避 | 是，达到 `-retry-max-attempts` 置 6 |
| 无路由 | 不变 | `now + -retry-backoff-base` | 否 |
| 租户限流 | 不变 | `now + retryAfter`（50ms 或补令牌时间） | 否 |

这样长期被限速的租户不会把消息推成 FAILED，只是延迟变大。

### 4.6 计数与观测

- `Engine.Snapshot()` 的 `throttled` 单独计数，不混入 `retried`。
- `Limiter.Snapshot()` 返回所有 `inflight > 0` 的租户及其计数，`cmd/delivery-worker` 按 `-stats-interval` 打日志。
- `Limiter.Inflight(tenantID)` 供单测与临时排查使用。

## 5. 后果

### 5.1 正面

- 一个租户的突发流量不会拖慢其它租户；限额维度与数据模型一致（`tenant_id`）。
- 投递热路径没有远程调用，限流本身不会成为新的故障点。
- 速率与并发两个维度互补：速率限制长期吞吐，在途限制瞬时堆积。
- 限流只延后、不失败，配合租约与扫描即可自动恢复。
- 配额缺省为「不限速 + 默认并发」，新增租户无需先配置即可工作。

### 5.2 负面

- 配额是**每进程**的：`N` 个 Worker 时实际总速率约为 `rate * N`，`max_inflight` 也是每进程上限。需要全局配额时必须按 Worker 数分摊配置。
- 配额变更最多延迟 `-tenant-cache-ttl`（默认 30s）生效；紧急场景需调用 `Forget`。
- Worker 重启会重置令牌与在途计数，重启瞬间可能出现一个小突发。
- 令牌桶与在途计数都受同一把互斥锁保护，热点租户的 `Acquire` 会在进程内串行化。
- 在途已满时固定 50ms 重试，未做退避递增，高并发下会增加一次无效领取与写回。

## 6. 状态

已接受。若未来需要严格的全局配额，可以把令牌桶迁移到 Redis 并用 Lua 原子扣减，或在配额表中引入「按 Worker 分摊」的字段；两者都需要重新评估 Redis 故障时的降级策略。
