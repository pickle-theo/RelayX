# ADR-001：为什么使用 Go 标准库 net

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`phase0/internal/transport/server.go`、`phase0/internal/transport/conn.go`、`phase0/internal/protocol/frame.go`、`phase0/cmd/gateway/main.go`
- 关联决策：[ADR-002 每连接单 Writer](ADR-002.md)

## 1. 背景

Phase 0 的目标是用 Go 标准库完成 TCP Server、TCP Client、长连接、自定义二进制协议、心跳与连接生命周期，并通过 1000 并发连接的压测验证基础可用性。仓库当前 `go.mod` 只有 `module relayx/phase0` 与 `go 1.27`，没有任何第三方依赖；开发与验证环境是 Windows 11（go1.27.3 windows/amd64），压测为本机回环。

传输层需要为上层提供这些能力：

- 每连接独立的读、写、心跳协程，读循环可按 `idle-timeout` 设置读 Deadline。
- `Listener.Accept` 的临时错误退避、`net.ErrClosed` 识别、`Conn.Close()` 的幂等关闭。
- 优雅关闭：停止 Accept、向所有连接广播 CLOSE 帧、等待协程退出。
- 每连接有界发送队列与背压（见 ADR-002）。
- 可观测：日志能带 `conn_id` / `remote`，能通过 goroutine 数和堆内存评估容量。

## 2. 当前问题

需要选定一种 TCP 网络 I/O 模型，并保证：

1. 编程模型能一对一映射「连接」这一生命周期对象——接受、读、写、心跳、关闭、注销都在同一连接上下文中完成。
2. 能直接表达超时语义（读 Deadline、心跳超时、关闭超时），而不是在回调里手工维护定时器状态。
3. 1000 连接的资源开销可接受、可测量，并能在 Phase 3 平滑演进到 1 万至 10 万连接。
4. 不把协议编解码绑定到某个框架的缓冲区类型上——`protocol.Decode` 目前接收 `*bufio.Reader`，`Encode` 接收 `io.Writer`。
5. 在 Windows 开发机上可运行、可测试（测试使用 `127.0.0.1:0` 真实监听）。

## 3. 候选方案

### 方案 A：标准库 `net`（goroutine-per-connection）

阻塞式 API，每个连接占用独立 goroutine；运行时 netpoller 在底层做非阻塞 I/O 与调度。超时通过 `SetReadDeadline` / `SetDeadline` 表达，关闭通过 `Close()` 唤醒阻塞读写。

### 方案 B：gnet（事件循环）

第三方高性能网络框架，以事件循环 + 非阻塞 socket 处理海量连接，回调式 API（`OnConn`、`OnTraffic` 等），自带缓冲区抽象，通常需要自行管理连接状态与定时任务。

### 方案 C：cloudwego/netpoll（事件循环 + 非阻塞）

第三方网络库，事件循环模型，提供 `Reader`/`Writer` 抽象与连接注册机制，主要面向 Linux/Unix 的 epoll 场景。

| 维度 | A 标准库 net | B gnet | C netpoll |
| --- | --- | --- | --- |
| 依赖 | 无 | 第三方模块 | 第三方模块 |
| 编程模型 | 每连接 goroutine，线性代码 | 事件循环 + 回调，需状态机 | 事件循环 + 回调/注册 |
| 超时表达 | `SetReadDeadline` 直接可用 | 需自行维护定时器 | 需自行维护定时器 |
| 平台 | 全平台（含 Windows） | 以 epoll/kqueue 事件循环为核心，非 Unix 平台需单独确认 | 官方支持以 Linux 为主 |
| 每连接成本 | 3 个 goroutine（读/写/心跳）+ 栈 | 回调状态 + 框架缓冲 | 回调状态 + 框架缓冲 |
| 可调试性 | 直接 goroutine dump、pprof、`conn_id` 日志 | 回调栈较深，问题需结合框架内部状态 | 同上 |
| 与现有协议层的契合 | `io.Writer` / `*bufio.Reader` 直接复用 | 需适配框架 buffer | 需适配框架 Reader/Writer |
| 1000 连接实测 | 3004 goroutine、堆峰值 28.26 MB，错误计数 0 | 未实测 | 未实测 |

## 4. 选择的方案

采用 **Go 标准库 `net`**：`net.Listen("tcp", addr)` 建立监听，`Accept` 循环接纳连接，每条连接由 `transport.Conn` 持有一个 `net.Conn`，并启动读、写、心跳三个协程。协议层保持与传输实现无关（`Encode(io.Writer, ...)`、`Decode(*bufio.Reader, ...)`）。

## 5. 选择理由

1. **需求与模型一一对应**。Phase 0 的每条连接本来就有独立的读、写、心跳生命周期，goroutine-per-connection 让 `readLoop`、`writeLoop`、`heartbeatLoop` 都是顺序代码，`Close` 通过 `close(done)` + `nc.Close()` 唤醒所有阻塞点，不需要在回调之间搬运状态。若用事件循环，心跳、读超时、发送队列都要自己做成状态机，复杂度与出错面明显更大。
2. **超时与关闭语义是标准库内建的**。`SetReadDeadline` 直接实现 `-idle-timeout`；`Close()` 会让阻塞中的 `Read`/`Write` 立即返回 `net.ErrClosed`；`Accept` 的临时错误可通过 `net.Error.Temporary()` 判断并退避。这些是当前代码里实际依赖的行为，换成框架都要重新实现。
3. **成本已被实测证明可接受**。1000 连接时服务端 3004 goroutine、堆内存峰值 28.26 MB、连接成功率 100%、57003 条消息零丢失（见[压测报告](../压测报告.md)）。Phase 0 的验收标准没有要求 10 万连接，当前模型没有成为瓶颈证据。
4. **零依赖、可移植**。`go.mod` 无 `require`，Windows 开发机上可直接构建与测试；测试用 `127.0.0.1:0` 起真实监听，不依赖框架的测试钩子。gnet/netpoll 的事件循环优势主要体现在 Linux epoll 场景，在 Windows 上引入会增加验证成本。
5. **保留演进空间**。协议层只依赖 `io.Writer` / `*bufio.Reader`，传输层对外暴露 `Conn.Send` 与 `Server`，未来若 Profiling 证明 goroutine/系统调用是主瓶颈，可以新增一个基于 gnet/netpoll 的 transport 实现，而不改动 `internal/protocol` 与业务 handler。

## 6. 优点和缺点

优点：

- 代码短、路径清晰：`Accept → 注册 → 三协程 → Close → 注销` 一条链即可读完，便于 Phase 0 学习目标与后续接手。
- 平台覆盖好，Windows 本机即可开发、压测、调试；`crypto/tls` 可直接包装 `net.Conn`，为后续 TLS 留路。
- 超时、取消、幂等关闭都使用语言/标准库既有机制，`sync.Once` + `atomic.Bool` 的组合已通过单测验证。
- goroutine 栈按需增长，1000 连接的内存曲线线性且可预测；`runtime.NumGoroutine()` 可直接作为泄漏检查指标。
- 无第三方版本升级、供应链与 API 变更风险。

缺点（具体到本项目）：

- **每连接固定 3 个 goroutine**：1000 连接即 3004 个服务端协程，压测报告已观测到该数字；连接数上升到 10 万时，调度器与栈内存成本会显著放大。
- **每帧至少一次堆分配与一次系统调用**：`Send` 内部用 `bytes.Buffer` 编码，帧头与 Body 会被复制；写协程每帧调用一次 `nc.Write`，没有批量写或 `writev`。
- **缺少跨连接公平性与批量能力**：goroutine 调度由运行时决定，无法像事件循环那样在单线程内批量处理多个连接的 I/O；高并发下 syscall 次数偏多。
- **慢连接会占住一个写协程**：服务端 `writeLoop` 未设置写 Deadline，对端不读时写会阻塞，直到读侧空闲/心跳超时触发 `Close` 才解除；这类阻塞不会传染到其他连接，但会拖住本连接的心跳与 CLOSE 下发。
- **依赖运行时 netpoller 的调度表现**：大量 goroutine 同时就绪时，尾延迟受调度影响，压测中最大 RTT 9.86 ms 即可能来自调度/GC 抖动。

## 7. 后续演进方向

按规划文档 Phase 3（8.3/8.4）：

1. 以标准库实现为基准，分别压测 1,000 / 10,000 / 50,000 / 100,000 连接，覆盖空闲、心跳、低频、高频、慢消费者、大 Payload、集中断线重连。
2. 用 CPU / Memory / Goroutine / GC / 锁竞争 Profiling 找出真实瓶颈；先尝试低风险优化（`sync.Pool` 复用编码缓冲、批量写、减少拷贝），再判断是否需要更换 I/O 模型。
3. 只有在数据表明 goroutine 调度、栈内存或 syscall 开销是主瓶颈时，才在 transport 层引入 gnet 或 netpoll 的可选实现，并以相同协议层、相同压测脚本做 A/B 对比；不预设框架一定更快。
4. 评估结论回写到本 ADR 或新增 ADR，保留基准数据与取舍依据。
