# ADR-002：为什么每连接单 Writer（有界队列）

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`internal/transport/conn.go`（`Send`、`writeLoop`、`Close`）、`internal/transport/server.go`（`Shutdown` 广播 CLOSE）
- 关联决策：[ADR-001 标准库 net](ADR-001.md)

## 1. 背景

TCP 是字节流，没有消息边界；协议帧必须整帧写入，否则对端按 21 字节头 + BodyLen 解码时会错位。Phase 0 的一条连接上存在多个帧生产方：

- `readLoop`：收到 PING 后立即回 PONG，收到 DATA 后调用业务 handler。
- 业务 handler（`cmd/gateway` 的 `echoHandler`）：回显 DATA。
- `heartbeatLoop`：每 `-heartbeat-interval` 发送 PING。
- `Server.Shutdown`：向所有连接发送 CLOSE 帧。

这些生产方可能并发触发。当前实现是：`Conn.Send` 先用 `protocol.Encode` 把整帧编码进 `bytes.Buffer`，再把 `[]byte` 非阻塞投递到容量为 `-send-queue-size`（默认 256）的 `chan []byte`；`writeLoop` 是唯一调用 `nc.Write` 的协程，写失败或刚发出 CLOSE 帧后退出。

## 2. 当前问题

需要一个写路径策略，同时满足：

1. **帧完整性**：并发写入的帧不能交错、不能被拆成互相穿插的片段。
2. **生产者不被慢网络拖死**：读循环、心跳、关闭流程不能因为某个客户端不读数据而长期阻塞。读循环一旦阻塞，就无法继续读入站帧，空闲/心跳超时判定也会失真。
3. **内存有界**：慢消费者不能让待发帧无限堆积。
4. **关闭可控**：`Close` 可被多协程重复调用而不 panic；优雅关闭时 CLOSE 帧有机会在 socket 关闭前刷出。
5. **可观测**：队列深度、队列满、写失败应能通过日志和错误值区分。

## 3. 候选方案

### 方案 A：直接并发写 socket

各生产方自行 `protocol.Encode(nc, frame, maxBody)`。`net.Conn` 文档允许多协程并发调用方法，TCP 连接内部会对写加锁，且当前 `Encode` 是单次 `Write`，因此字节通常不会交错。

问题：

- 帧的**顺序**不可控：PING/PONG/DATA/CLOSE 的先后取决于调度，CLOSE 可能先于排队的数据写出。
- 慢客户端会**直接阻塞调用方**：`readLoop` 卡在 `Write` 上就无法继续读，心跳协程也会卡住，形成「写等对端读、读等本地写」的相互拖累。
- 没有队列就没有背压边界；若为避免阻塞而给每次写开 goroutine，内存与协程数会失控。
- 关闭时无法保证已编码但未写出的 CLOSE 帧被刷出，也无法统计队列压力。

### 方案 B：全局写锁 / 每连接写锁

用 `sync.Mutex` 包住「编码 + 写 socket」。若用全局锁，所有连接的写串行化，一个慢客户端会阻塞全部连接，Phase 0 的 1000 连接压测必然出现长尾。若用每连接锁，爆炸半径缩小到单连接，但：

- 生产方仍然**阻塞在网络 I/O 上**，读循环和心跳依旧会被慢客户端拖住。
- 锁内不能安全地做长时间阻塞操作，关闭与写竞争时容易形成「持锁写、Close 等待」的停顿。
- 没有队列深度、没有明确的队列满策略，内存与延迟都不可控。

### 方案 C：每连接单 Writer + 有界队列（当前实现）

- `Send`：编码 → 非阻塞 `select` 投递到 `sendCh`；队列满则告警、以 `send queue full` 关闭连接并返回 `ErrSendQueueFull`；连接已关闭返回 `ErrConnClosed`。
- `writeLoop`：`select { <-done; data := <-sendCh }`，唯一执行 `nc.Write`；写失败关闭连接；若写出的帧类型为 CLOSE（`data[3]`）则刷出后退出。
- `Close`：`sync.Once` 保证幂等，`close(done)` 通知写协程退出，`nc.Close()` 唤醒阻塞 I/O，`onClose` 注销连接。`sendCh` 故意不关闭，避免向已关闭 channel 发送导致 panic。

| 维度 | A 直接并发写 | B 写锁 | C 单 Writer + 有界队列 |
| --- | --- | --- | --- |
| 帧字节完整性 | 依赖单次 Write + 连接内部锁 | 依赖锁 | 由唯一写者保证，与 Encode 实现无关 |
| 帧顺序 | 不可控 | 抢锁顺序 | FIFO，可控 |
| 慢客户端影响 | 阻塞读循环/心跳 | 阻塞持锁者；全局锁影响全部连接 | 生产者不阻塞，队列堆积至上限后关闭 |
| 内存上界 | 无 | 无 | 每连接 `send-queue-size` 帧 |
| 背压策略 | 无 | 无 | 明确：队列满即关闭，返回 `ErrSendQueueFull` |
| 关闭语义 | 易与并发写竞争 | 需处理持锁阻塞 | `done` 通知 + `nc.Close()` 唤醒，逻辑集中 |
| 额外成本 | 无 | 无 | 每连接 +1 协程、每帧一次入队 |

## 4. 选择的方案

采用 **方案 C：每连接单 Writer + 有界发送队列**，实现位置 `internal/transport/conn.go`。默认队列容量 256 帧，由服务端 `-send-queue-size` 配置；服务端与客户端的所有 socket 写都由各自唯一的写路径完成（客户端演示程序由主 goroutine 串行写，PONG 通过 channel 交回主 goroutine）。

## 5. 选择理由

1. **正确性由结构保证**。只有一个协程调用 `nc.Write`，帧不会交错；即使未来 `Encode` 改成多次 `Write` 或引入 `bufio.Writer`，这一保证仍然成立。相比依赖「`net.Conn` 内部锁 + 单次 Write」的隐式前提，单写者是显式约束，更容易审查与测试。
2. **生产者与网络解耦**。`Send` 不做阻塞 I/O，`readLoop` 能持续读入站帧、刷新 `lastInbound`，`heartbeatLoop` 能按时触发；慢客户端的影响被限制在该连接自己的队列里，不会传染给其他连接。
3. **背压策略明确且可测**。队列满时立即关闭连接并返回 `ErrSendQueueFull`，内存上界是 `send-queue-size × 帧大小`，不会因慢消费者无限增长。`TestSendQueueFullBackpressure` 用阻塞型 `net.Conn` 验证了「第二次 Send 不阻塞、返回 `ErrSendQueueFull`、连接被标记关闭」。
4. **生命周期简单**。`Close` 通过 `sync.Once` + `done` 与写协程汇合，`run()` 在 `readLoop` 返回后 `Close` 并 `wg.Wait()`；发送 CLOSE 帧的路径只需入队，写协程识别帧类型后自行退出，无需在关闭流程里做额外同步。
5. **为批量写留接口**。所有待发帧已经以完整 `[]byte` 形式集中在一个队列中，Phase 3 可以在写协程内一次取出多帧、用 `net.Buffers` 合并写出，生产方无需改动。

## 6. 优点和缺点

优点：

- 写串行化，帧完整性与顺序性可控；PING/PONG、DATA 回显、CLOSE 走同一 FIFO，语义一致。
- 生产方永不因网络阻塞；队列满快速失败，错误值可分类（`ErrConnClosed` / `ErrSendQueueFull`）。
- 每连接内存上界明确，便于容量规划；队列满有告警日志，可观测。
- 关闭路径集中且幂等，避免重复 `close` channel 或重复关闭 socket 的 panic。
- 为后续批量写、缓冲池、队列水位指标提供了天然挂载点。

缺点（具体到本项目）：

- **每连接多一个写协程**，加上读与心跳共 3 个；1000 连接即 3004 个服务端协程（压测报告第 4 节实测），连接数继续上升时协程与栈内存成本线性增长。
- **每帧至少一次堆分配与一次拷贝**：`bytes.Buffer` 生成帧缓冲，`buf.Bytes()` 入队；默认 1 MiB `max-body` 下大帧会明显增加 GC 压力。
- **连接内存在队头阻塞（head-of-line blocking）**：FIFO 意味着前面的大帧或慢写会推迟后面的 PING 与 CLOSE；队列满之前，心跳应答的及时性取决于队首帧的写出速度。
- **队列满即关闭，没有优雅降级**：不做「丢弃最旧帧」或「先排空再关」；`close(done)` 后仍在队列中的帧会被丢弃，适合 Phase 0 的回显语义，但不适合未来的可靠消息。
- **服务端写协程没有写 Deadline**：`writeLoop` 未调用 `SetWriteDeadline`，对端不读时写会一直阻塞，只能依赖读侧空闲超时（默认 120s）或心跳超时（默认 90s）触发 `Close` 来解除。关闭延迟因此受这些超时约束。
- **队列按帧数而非字节数计量**：256 帧的上界在 64 B 小帧与 1 MiB 大帧之间相差 4 个数量级，无法精确控制单连接内存水位。

## 7. 后续演进方向

按规划文档 Phase 3：

1. **批量写**：写协程一次从队列取出多帧，使用 `net.Buffers` / `writev` 合并为一次系统调用，降低 1000+ 连接下的 syscall 次数与尾延迟。
2. **缓冲池与减少拷贝**：用 `sync.Pool` 复用编码缓冲，让 `protocol.Encode` 直接写入池化缓冲区，避免 `bytes.Buffer` 的重复分配；评估把帧头与 Body 合并为一次写入的零拷贝路径。
3. **队列调优**：从「按帧数」改为「按字节数 + 高低水位」，区分控制帧（PING/PONG/CLOSE）与数据帧，必要时给控制帧优先队列，缓解队头阻塞。
4. **慢消费者策略**：在可靠消息阶段（Phase 2）改为可配置策略——断开、丢弃最旧、或按会话上限限流，而不是一律关闭。
5. **可观测性**：暴露每连接队列深度、入队/出队速率、队列满次数、写阻塞时长，结合 Profiling 判断队列大小与批量阈值。
6. **实现评估**：比较 channel 与环形缓冲（ring buffer）的入队/出队开销；若写协程调度成为瓶颈，再评估由事件循环统一驱动写路径，但需保持「单连接单写者」这一正确性约束。
