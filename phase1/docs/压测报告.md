## 2. 命令与参数

两组压测在**同一台机器、同一轮会话**中依次执行：先 A 组（端口 19300），结束后按 PID 停止 gateway 并确认端口释放，再执行 B 组（端口 19301）。两组均为 60s、1000 连接、每秒每连接 1 帧、64 B payload、5s ramp。

公共参数：

| 参数 | 值 | 说明 |
| --- | --- | --- |
| `-conns` | 1000 | 并发连接数 |
| `-duration` | 60s | 压测总时长（计量窗口固定，含 5s 建连 ramp） |
| `-interval` | 1s | 每连接每秒发送 1 帧 |
| `-payload-size` | 64 B | payload 长度；Body 前缀为 `load#<connID>#<seq> ` |
| `-ramp` | 5s | 1000 条连接在 5s 内均匀建立 |
| `-timeout` | 5s | 拨号与单条消息等待超时 |
| `-max-body` | 1 MiB | 与服务端默认值一致 |
| 服务端其他参数 | 默认值 | 心跳 30s、心跳超时 90s、空闲超时 120s、发送队列 256 帧 / 4 MiB、批量写 16 帧 / 64 KiB、写超时 10s、读缓冲 4096 B |

A 组（回显基线）：

```powershell
$gw = Start-Process -FilePath "$PWD\bin\gateway.exe" -ArgumentList "-addr","127.0.0.1:19300","-stats-interval","5s" -RedirectStandardOutput "$PWD\gw-echo.log" -RedirectStandardError "$PWD\gw-echo.err" -PassThru -WindowStyle Hidden
Start-Sleep -Seconds 2
& "$PWD\bin\loadtest.exe" -addr 127.0.0.1:19300 -conns 1000 -duration 60s -interval 1s -ramp 5s -out "$PWD\echo-result.txt"
Stop-Process -Id $gw.Id -Force
```

B 组（登录 + 路由，自路由）：

```powershell
$gw2 = Start-Process -FilePath "$PWD\bin\gateway.exe" -ArgumentList "-addr","127.0.0.1:19301","-stats-interval","5s" -RedirectStandardOutput "$PWD\gw-route.log" -RedirectStandardError "$PWD\gw-route.err" -PassThru -WindowStyle Hidden
Start-Sleep -Seconds 2
& "$PWD\bin\loadtest.exe" -addr 127.0.0.1:19301 -conns 1000 -duration 60s -interval 1s -ramp 5s -route -out "$PWD\route-result.txt"
Stop-Process -Id $gw2.Id -Force
```

B 组中每条连接以 `user=load-<connID>`、`device=d0` 登录，随后 `SEND` 到同名用户（`targetType=0x01`），由 Router 找到自己的 Session 并回投 `DELIVER`。因此 B 组覆盖了 LOGIN 握手、Session 注册、按用户查找、DELIVER 编码与目标队列入队，但不覆盖多设备 fan-out。

两次 `loadtest` 退出码均为 0；结束后 `Get-NetTCPConnection -LocalPort 19300,19301` 无记录，端口已释放。

## 5. 与 Phase 0.5 对比

Phase 0.5 基线来自[其压测报告](../../phase0.5/docs/压测报告.md)，同机、同参数（1000 连接 / 60s / 1 帧每秒 / 64 B）。

| 错误计数（连接/登录/路由/超时/解码/非预期/写） | 全 0 | 全 0 | 全 0 |

| RTT 平均 | 0.043 ms（复测 0.015） | 0.021 ms | 0.019 ms |
| 服务端 goroutine 峰值 | 2004 | 2004 | 2004 |
| 服务端 active_conns 峰值 | 1000 | 1000 | 1000 |

| 客户端 heap_alloc | 3.30 MB | 3.30 MB | 3.26 MB |

解读：

1. **功能路径没有吞吐回退**：A 组 sent/echoed 与 Phase 0.5 完全相同（57003/57003），B 组 sent/delivered 同样为 57003/57003，missed 与各类错误全 0，退出码 0。新增的登录、注册表查找与 DELIVER 编码没有造成丢帧。
2. **协程模型未变**：A、B 两组服务端 goroutine 峰值都是 2004，与 Phase 0.5 相同，说明路由没有新增常驻协程；会话状态只增加对象与 map 条目，不增加协程。
3. **RTT 差异低于时钟分辨率**：A 组 P99 0.562 ms、B 组 0.552 ms，与 Phase 0.5 的 0.537 ms 相差约 0.015–0.025 ms；本机单调时钟粒度约 505 µs，三者的 P50/P90 均为 0.000，因此这点差异不能判定为真实回退或改善。B 组多一次 Router 查找与一次 DELIVER 编码，理论上应略慢于 A 组，但实测 P99 反而低 0.010 ms、平均低 0.002 ms，属于采样噪声。最大值 A 组 3.750 ms、B 组 5.763 ms，均远低于 Phase 0.5 首轮的 35.560 ms，属于调度/GC 抖动。
4. **服务端堆峰值小幅上升**：回显 28.97 MB（+2.18 MB，+8.1%），路由 29.86 MB（+3.07 MB，+11.5%）。回显模式的增量来自 Phase 1 新增的 `gateway.Handler.conns`、`router.Router` 与 handler 调用路径；路由模式在此基础上再增加 1000 个 `Session` 对象与 `byID`/`byUser` 双索引。堆峰值受 GC 触发时机影响，Phase 0.5 自身两轮也有 26.79/27.74 MB 的波动，因此不宜把 8%–12% 当作稳定开销，但方向（会话状态带来额外内存）是确定的。
5. **heap_sys 与采样噪声**：A 组 40.16 MB 与 Phase 0.5 复测的 40.16 MB 相同，B 组 36.16 MB 与 Phase 0.5 首轮相同；两组都在 36–40 MB 区间，差异不构成结论。
6. **客户端资源基本持平**：heap_alloc 3.30/3.26 MB vs 3.30 MB；heap_sys 35.53/39.19 MB vs 32.16 MB，属于单轮分配/GC 抖动。goroutine 均为 2001 → 1。

## 7. 结论

1. 1000 并发连接、每秒 1000 帧、60s、本机回环条件下，回显与登录+路由两组均为 100% 建连成功、57003 帧全部完成（回显或投递）、0 丢失、0 超时、0 解码/非预期帧/写错误，`loadtest` 退出码 0。
2. 登录与路由链路在 1000 会话规模下稳定：`active_sessions` 与 `active_conns` 同步达到 1000，登录失败 0、路由错误 0，没有出现 `replaced by new login`（本轮无重复登录）或队列满。
3. 每连接仍是 2 个服务端协程，服务端 goroutine 峰值与 Phase 0.5 持平（2004），证明 Session/Router 是纯内存状态而非协程模型变化。
4. 服务端堆峰值小幅上升（回显 +2.18 MB、路由 +3.07 MB 相对 Phase 0.5），方向符合"新增会话注册表"的预期，幅度受单轮 GC 时机影响，不作为长期基线。
5. 端口 19300 / 19301 均已释放，无残留 gateway 进程；质量门禁（gofmt / vet / test / Docker race）全部通过。

## 8. 已知限制

1. **仅本机回环**：延迟是本地协议栈往返，不含真实网络 RTT、丢包与重传；客户端与服务端共享同一颗 8 线程 CPU，存在互相抢占。两组依次执行，未做系统背景负载隔离。
2. **RTT 分辨率受限**：本机 Windows 单调时钟粒度在此前 Phase 0.5 实测约 505 µs（同机同 Go 版本），P50/P90 的 0.000 表示"低于可分辨下限"，不是真实 0；P99 的 0.55 ms 约等于一个刻度，不能据此推算亚毫秒真实值。
3. **自路由未压 fan-out**：B 组每个用户只有 1 台设备（`device=d0`），`DeliverToUser` 每次只命中 1 个目标。多设备 fan-out 的放大效应、单用户大量设备时的串行入队开销未覆盖。
4. **单轮采样**：两组各只跑 1 轮，没有像 Phase 0.5 那样补跑复测；尾部（P99/max）与堆峰值受环境噪声影响，不能作为稳定基线。
5. **时长短于心跳/空闲超时**：60s 仅覆盖约 2 次服务端 PING，未触发 90s 心跳超时与 120s 空闲超时路径（这两条路径由单测覆盖）。
6. **负载形态单一**：固定 64 B payload、每秒 1 帧、无突发、无慢消费者、无大帧；`send-queue-bytes` / `write-batch-bytes` 的端到端压测未覆盖。
7. **未做失败路径压测**：目标离线、目标不存在、重复登录踢人、未登录 SEND 等路径由单测覆盖，本轮压测全部为成功投递，`route_errors=0` 不代表这些路径未被验证。
8. **竞态检测范围**：`-race` 只覆盖测试，gateway/loadtest 二进制未以 `-race` 构建，容量数据不代表 race 模式下的性能。
9. **服务端收尾数据不完整**：压测结束后立即按 PID 停止进程，未采集"全部连接断开后"的 stats；B 组只写出 81 条 `connection closed` 与 735 条 `session closed`，其余日志随进程终止丢失。这两项均为**未采集**，不是残留证据。
10. **压测工具报告标题为 `RelayX Phase 0 load test`**：`cmd/loadtest` 的报告头沿用了 Phase 0 文案（业务代码未修改），实际模式由 `mode` 字段区分（`echo` / `route`），不影响本次数据。
11. **未采集项**：每连接发送队列水位、批量写批大小分布、路由 fan-out 设备数分布、syscall 次数均未采集（当前只有日志与 loadtest 汇总）。
