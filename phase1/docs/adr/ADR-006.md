# ADR-006：路由模型与失败处理

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`internal/router/router.go`、`internal/gateway/gateway.go`、`internal/session/session.go`、`internal/transport/conn.go`
- 关联决策：[ADR-005 Session 与 Connection 分离](ADR-005.md)、[ADR-004 批量写与背压](../../../phase0.5/docs/adr/ADR-004.md)

## 1. 背景

Phase 1 的 `SEND` 需要把消息从"发送方的连接"送到"目标方的连接"。当前目标是单机、在线、尽力而为（best-effort）：

- 按用户发送：一个用户可能有多台在线设备。
- 按端点发送：精确到某一条 `sessionID`。
- 目标不在线、目标不存在、目标发送队列已满时，必须有明确且不破坏连接的处理方式。

同时，Phase 0.5 已经确立了背压模型：每个连接有独立的 `sendCh`（帧数上限）与字节预算，`Send` 非阻塞，队列满即关闭**该连接**。路由层必须复用而不是绕过这套模型。

## 2. 当前问题

需要回答：

1. 消息由谁持有、由谁写 socket？
2. 按用户 fan-out 时，一台设备投递失败是否影响其他设备？
3. 目标离线/不存在时，发送方应收到什么？连接是否保持？
4. 目标消费过慢时，背压传递给谁？
5. 是否需要在路由层做队列、重试或离线存储？

## 3. 候选方案

### 方案 A：中心队列 / 写扩散（broker 模式）

Router 持有全局队列，由专门的投递协程从队列取出消息，再写入目标连接。

- 优点：发送方与目标彻底解耦，可以做重试、限流、持久化。
- 缺点：多一层队列与协程；消息生命周期、确认、重试语义全部要设计；Phase 1 不要求可靠投递，复杂度与收益不匹配。

### 方案 B：同步广播（Router 直接阻塞写 socket）

Router 对每个目标直接调用 `nc.Write` 或阻塞式发送，全部写完才返回。

- 优点：语义最直观，"发送成功"即"已写出"。
- 缺点：慢目标会阻塞发送方的 `readLoop`，导致发送方无法继续读入站帧、PONG 无法及时发出、空闲/心跳超时失真；一个慢设备拖垮整条 fan-out。

### 方案 C：复用目标连接的有界发送队列（本决策）

Router 只做"查找 + 对每个目标调用 `Conn.Send`"，实际写 socket 仍由目标连接的 `writeLoop` 完成：

- 按用户：`Manager.FindByUser` 返回该用户全部在线 Session 的副本，逐个 `Send(DELIVER)`。
- 按端点：`Manager.Get(sessionID)` 找到唯一 Session，`Send(DELIVER)`。
- 某台设备 `Send` 失败（队列满/连接已关闭）：跳过该设备，继续 fan-out；全部失败时返回"目标离线"。
- 目标队列满时，transport 关闭的是**目标连接**，不是发送方。

### 方案 D：离线存储 + 重试

目标不在线时把消息落盘/落库，等目标上线再投递。

- 优点：不丢消息。
- 缺点：需要存储、确认、去重、过期与顺序保证；Phase 1 明确不做离线消息。

### 方案 E：全局广播

`SEND` 不指定目标，向所有在线连接广播。

- 优点：实现简单。
- 缺点：没有寻址语义，无法表达"发给某个用户/某个设备"，也不符合即时通讯的基本模型。

## 4. 决策

采用 **方案 C**，具体规则：

1. **按 user fan-out**：`DeliverToUser` 查 `byUser[userID]`，向该用户所有在线设备各投递一份 `DELIVER`。返回成功投递数；无在线设备返回 `ErrTargetOffline`。
2. **按 endpoint 定向**：`DeliverToEndpoint` 把 target 解析为十进制 `uint64`，`Manager.Get` 命中后只投递这一条 Session；未知/已关闭/非数字返回 `ErrTargetNotFound`。允许给自己发（自路由）。
3. **失败回 ERROR，不断连接**：`Handler.handleSend` 把 router 错误映射为短文本（`route: target offline`、`route: target not found` 等），以 `ERROR` 帧回给发送方；发送方连接保持可用。
4. **投递复用目标连接的有界队列**：Router 只调用 `Session.Conn.Send`，不直接写 socket，也不新建队列。`Send` 编码后入 `sendCh`（或控制帧入 `ctrlCh`），由目标 `writeLoop` 批量写出。
5. **目标队列满则关闭目标连接**：`Conn.Send` 在帧数或字节预算超限时回滚计数、归还缓冲、以 `send queue full` 关闭该连接并返回 `ErrSendQueueFull`；router 跳过该目标，若全部失败则向发送方回 `route: target offline`。
6. **`DELIVER` Body 只编码一次**：同一次 fan-out 中所有目标共享同一个 `Body` 切片；这是安全的，因为 `Conn.Send` 同步编码并复制进自己的队列缓冲，不保留、不修改 `Body`。
7. **不重试、不排队、不落盘**：路由层是无状态的"查找 + 入队"，消息一旦交给目标队列，可靠性由该连接的发送队列与 TCP 负责；失败即丢弃并告知发送方。

## 5. 选择理由

1. **复用既有背压模型**：Phase 0.5 已经证明"每连接有界队列 + 非阻塞 Send + 队列满关闭"可用且可观测。Router 直接复用，避免在业务层再造一套队列与超时。
2. **发送方不被慢目标拖住**：`Conn.Send` 只做编码与入队，不等待 socket 写出；发送方的 `readLoop` 可以继续处理后续帧、回 PONG、维持心跳。
3. **fan-out 的失败被隔离**：一台设备队列满只关闭它自己，其他设备仍能收到消息；返回值让调用方知道实际投递数，但当前协议只用它区分"至少一个成功"与"全部失败"。
4. **ERROR 不破坏连接**：目标离线是正常的业务状态（对方没上线），不应因此断开发送方；把失败作为可读文本回给客户端，便于业务层决定是否重试。
5. **无状态 Router 易于测试与扩展**：Router 只持有 `*session.Manager`，没有自己的锁、队列或协程；未来替换为跨节点路由时，接口边界清晰。
6. **明确不做可靠投递**：离线消息、重试、去重需要存储与确认协议，属于 Phase 2；Phase 1 用"best-effort + ERROR"把语义边界划清。

## 6. 背压边界

- **发送方异步不阻塞**：`Handle` 中的 `Send` 只入队；即使目标写得很慢，发送方的 `readLoop` 也不会停在路由调用上。
- **反压落在目标连接**：目标 `sendCh` 满或字节预算超限时，关闭的是目标连接，发送方只看到一条 `ERROR`。
- **ERROR 可能反压发送方自身**：如果发送方在短时间内产生大量无法投递的 `SEND`，每条失败都会向**发送方自己的** `sendCh` 入队一条 `ERROR`。当发送方不读或读得很慢时，其自身队列可能打满，从而被 transport 以 `send queue full` 关闭。这是有意的：错误通知不能无限堆积，发送方必须消费自己的回包。
- **fan-out 的放大效应**：一次 `SEND` 最多产生"设备数"次入队；如果某用户有大量设备且都慢，Router 会依次尝试，但每次 `Send` 都是非阻塞的，不会因为某个目标慢而卡住。
- **控制帧优先**：`PONG`/`CLOSE` 走 `ctrlCh`，不会被大量 `DELIVER`/`ERROR` 数据帧饿死；这保证了高路由负载下心跳与关闭仍然及时。

## 7. 后果（优点和缺点）

优点：

- 路由路径短：一次 map 查找 + 一次 `Send`，无额外队列/协程。
- 失败语义清晰：离线、不存在、未登录、非法目标各有独立错误文本。
- 单设备故障不影响同用户其他设备，也不影响发送方连接。
- 复用 Phase 0.5 的批量写、字节预算、控制帧优先与写超时，行为一致。
- Router 无状态，便于单测（可用 fake Session/Conn）与后续替换。

缺点（具体到本项目）：

- **尽力而为，可能丢消息**：目标队列满时消息被丢弃；没有重试、确认或离线补发。
- **发送方可能被自己的 ERROR 反压**：大量失败会占用发送方队列；客户端必须持续读回包。
- **fan-out 是串行入队**：目标设备很多时，Router 在发送方 `readLoop` 上逐个 `Send`，会拉长该帧的处理时间；当前每用户设备数很小，未做并行化。
- **全部失败才报错**：部分设备投递成功时，发送方收不到任何提示，也不知道哪台设备失败；协议没有 per-target 回执。
- **endpoint 定向依赖进程内 `sessionID`**：重启后旧 ID 失效，跨节点不可用。
- **`DELIVER` 共享 Body 切片**：依赖 `Conn.Send` "同步编码并复制"的实现约定；若未来改为异步编码或保留 Body，需要重新设计所有权。

## 8. 被否决的方案

- **中心队列 / 写扩散**：需要额外的队列、投递协程、确认与重试语义，Phase 1 的 best-effort 目标不需要；还会让消息延迟多一跳。
- **同步广播 / 阻塞式写**：慢目标会阻塞发送方 `readLoop`，破坏心跳/空闲超时与 PONG 时效；一个慢设备即可拖垮整次 fan-out。
- **离线存储 + 重试**：属于 Phase 2 的可靠投递，需要存储、去重、过期与顺序保证，当前明确不做。
- **全局广播**：没有寻址能力，无法表达用户/设备级别的投递语义。
- **在 Router 内维护每用户队列**：会与连接级队列形成两级缓冲，内存上界与背压路径都变得难以估算，且收益不明确。
- **失败即断开发送方**：目标离线是常态，不应升级为连接级错误；这会迫使客户端频繁重连。

## 9. 后续演进方向

1. Phase 2 引入离线消息与确认机制：为 `DELIVER` 增加 ACK，Router 在超时后重试或转入离线存储。
2. 为 `SEND` 增加可选的消息 ID 与去重窗口，支持客户端重试而不产生重复投递。
3. fan-out 改为"收集目标后批量入队"或按设备并行投递，降低大用户量下的单帧处理时间。
4. 暴露路由指标（投递成功/失败数、按原因分类的 ERROR 数、fan-out 设备数分布），替代当前仅靠客户端统计。
5. 跨节点阶段把 `Manager.Get` / `FindByUser` 替换为集群路由表，保持 Router 接口不变。
