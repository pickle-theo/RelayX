## 7. 为什么从失败到通过

### 7.1 四轮结果对比

| 轮次 | 配置/代码 | send_ack | ack_missed | accept p99 | 退出码 |
| --- | --- | --- | --- | --- | --- |
| 1 | `synchronous_commit=on`，受理 = BEGIN + 2 INSERT + COMMIT，另有 `MarkDeliverySent` | 24959 | 32005 | 5872 ms | 1 |
| 2 | 仅把容器改为 `synchronous_commit=off` | 37816 | ≈19100 | ≈5880 ms | 1 |
| 3 | 再把在线投递标记并入受理语句（仍为显式事务） | 38302 | ≈18500 | ≈5894 ms | 1 |
| 4 | 再把受理与两级 ACK 各压缩为**单条语句** | 56995 | 0 | 699 ms | 0 |
| 5（最终，文档所用数据） | 同上，重新构建 `loadtest`（仅修正报告标题字符串）后重跑 | **56994** | **0** | **467 ms** | **0** |

> 第 2、3 轮的原始输出被后续轮次覆盖，未单独归档，表中只保留当时记录的 `send_ack` 与 P99；第 1 轮完整输出见 [loadtest-reliable-sync-on.txt](loadtest-reliable-sync-on.txt)，第 5 轮见 [loadtest-reliable.txt](loadtest-reliable.txt)。第 4、5 轮代码与参数完全相同，差异（P99 699 → 467 ms、send 56995 → 56994）来自同机资源竞争的运行间抖动，两轮均未做数据筛选。

两轮的关键差别不是“有没有提交”，而是**每条消息的数据库往返次数**：第 3 轮仍是每条消息 12 次往返（受理 4 + `MarkDeliverySent` 1 + 两级 ACK 各 4 减去一条语句），第 4 轮降到 3 次。

### 7.2 归因实验

| 实验 | 结果 | 说明 |
| --- | --- | --- |
| `pgbench -c 16 -T 20 -N`（简单 UPDATE） | 10077 tps，1.588 ms/事务 | PostgreSQL 写入能力充足 |
| `pgbench` 复刻受理事务（BEGIN + 2 INSERT + COMMIT） | 6222 tps | 同样的 SQL 在 PG 侧可到 6k/s，瓶颈不在 SQL |
| 存储层基准（受理 + 两级 ACK，16 并发，优化前） | 775 msg/s | Go 侧 12 次往返把利用率拉低到 PG 能力的 1/8 |
| 存储层基准（同上，优化后） | 约 1300 msg/s（0.768 ms/op） | 同样的 Go 代码路径，仅减少往返 |
| 仅受理、不发 ACK（1000 连接 30s） | 约 980 msg/s，`ack_missed=0` | 受理路径本身已接近单核上限，两级 ACK 的三倍写入把它压垮 |

由此可以排除两类假设：**不是 PostgreSQL 容量不足**（pgbench 6k+ tps），**也不是 transport/协程问题**（`active_conns=1000` 稳定、协程数与 Phase 1 同阶、抓包层零错误）。真正的瓶颈是每条消息的 3 个事务、12 次往返在 4 物理核上与负载生成器、Gateway 抢占 CPU 后的排队。

### 7.3 各项改动的贡献

| 改动 | 单独效果 | 说明 |
| --- | --- | --- |
| `synchronous_commit=off` | send_ack 24959 → 37816（+51%） | 去掉每次提交的 WAL fsync 等待；只解决等待，不减少往返 |
| 在线投递标记并入受理语句 | 37816 → 38302（+1.3%） | 去掉每消息 1 次写事务，但受理仍是 4 次往返的显式事务，收益被往返成本抵消 |
| 受理/两级 ACK 各压缩为单条语句 | 38302 → 56994（+49%，`ack_missed` 归零） | 12 → 3 次往返，是达标的关键 |

两者缺一不可：只做语句压缩而保持 `synchronous_commit=on` 时，每次提交仍要等 1.6–1.7 ms fsync，3 次提交/消息在 1000 条/秒下需要约 3.4 核的纯等待，仍会超时。

## 8. 剩余瓶颈与已知限制

1. **单机共置**：Gateway、负载生成器、PostgreSQL 容器共享 4 个物理核。通过的判据是 5s 超时内闭环，不是“余量充足”：`db_open_conns` 稳定打满 16，p99 467 ms 里包含排队；同一配置相邻两轮的 P99 在 467–699 ms 之间波动。
2. **`synchronous_commit=off` 是开发环境取舍**：本轮的 946 条/秒不能外推到 `on`。`on` 模式下每条消息 3 次同步提交，需要批量提交/组提交或更高规格磁盘。
3. **每条消息仍固定 3 次数据库往返**：ACK 语义要求两次独立写入；进一步的提升手段是批量合并 ACK（ADR-007 §8）。
4. **`dbTimeout=5s` 硬编码**：数据库抖动时同一时间窗内的请求会一起失败。
5. **Worker 单实例**：重试与过期扫描不做分布式协调，多实例部署会重复处理。
6. **`PULL` 自带游标乱序缺口**（ADR-009 §6.1）：本轮未使用 PULL，但它是已知设计限制。
7. **未采集资源指标**：本轮没有记录 CPU/IO 曲线，结论基于 pgbench 与存储层基准的间接测量。

## 10. 与 Phase 1 对比

| 指标 | Phase 1（纯 transport） | Phase 2（可靠投递） |
| --- | --- | --- |
| 1000 连接 60s | 57003 / 57003 | 56994 / 56994 |
| p99 RTT | 0.552 ms | 467.273 ms |
| 每消息数据库写入 | 0 | 3 条语句（受理 + 两级 ACK） |
| 退出码 | 0 | 0 |

RTT 从亚毫秒级升到百毫秒级是可靠投递的固有代价：每条消息至少一次数据库提交，且与两级 ACK 的写入共享同一个 16 连接池。要接近 Phase 1 的延迟，需要批量提交/异步确认，那会改变 At-Least-Once 的承诺边界，超出 Phase 2 的范围。
