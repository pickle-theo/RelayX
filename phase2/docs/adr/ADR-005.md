# ADR-005：Session 与 Connection 分离

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`internal/session/session.go`、`internal/gateway/gateway.go`、`internal/transport/conn.go`
- 关联决策：[ADR-006 路由模型与失败处理](ADR-006.md)

## 1. 背景

Phase 0.5 的 `transport.Conn` 只是"一条已建立的 TCP 连接"：有连接 ID、读写协程和发送队列，但没有身份概念。Phase 1 需要：

1. 客户端能声明自己是谁（`userID` + `deviceID`）。
2. 其他客户端能按用户或按具体会话给某条连接发消息。
3. 同一用户可以从多台设备同时在线。
4. 同一 `(user, device)` 在新连接登录后，旧连接必须失效，避免同一设备出现两条可投递的会话。

如果直接把身份字段塞进 `Conn`，transport 将同时承担编解码、连接生命周期与业务身份三种职责，`internal/transport` 会被迫依赖业务语义，后续（鉴权、离线消息、跨节点）也无法独立演进。

## 2. 当前问题

需要明确回答：

- 身份是**连接属性**还是**业务对象**？
- `sessionID` 从哪来、生命周期多长、能否跨重启稳定？
- 同一 `(user, device)` 的旧连接如何处理？
- 未登录连接能不能发消息？
- Phase 1 是否做鉴权？

## 3. 候选方案

### 方案 A：Session 与 Connection 合一

在 `transport.Conn` 上增加 `UserID`、`DeviceID`、`SessionID` 字段，`Server` 内部维护 `byUser` 索引，`Conn.Send` 直接承担投递。

- 优点：少一层对象，查找路径最短。
- 缺点：transport 依赖业务身份；连接关闭逻辑与 Session 注销耦合；测试必须构造真实 `Conn`；后续鉴权/离线/跨节点全部压进 transport。

### 方案 B：Session / Connection 分离（本决策）

- `Session` 是**领域对象**：`ID`、`UserID`、`DeviceID`、`Conn`、`RemoteAddr`、`CreatedAt`。
- `Conn` 是**传输对象**：只负责帧的读写、队列、超时与关闭。
- `session.Manager` 是并发注册表：`byID map[uint64]*Session` + `byUser map[string]map[string]*Session`，`RWMutex` 保护。
- `gateway.Handler` 持有 `conns sync.Map`（连接 ID → Session），把两者关联起来。

### 方案 C：允许同设备多连接并存

同一 `(user, device)` 允许多条 Session，路由时 fan-out 到所有连接。

- 优点：实现简单，不需要踢人逻辑。
- 缺点：客户端重连/网络抖动会产生"幽灵会话"，同一条消息被同一设备重复接收；无法表达"设备当前只有一条有效会话"。

### 方案 D：持久化 Session

把 Session 写入磁盘或外部存储，重启后恢复，`sessionID` 全局稳定。

- 优点：重连后仍可寻址，为离线消息铺路。
- 缺点：Phase 1 是单机内存 Gateway，没有存储依赖；持久化会引入一致性、过期清理与恢复语义，超出当前范围。

## 4. 决策

采用 **方案 B**，并附带以下规则：

1. **Session 是领域对象，Connection 是传输对象**。`session.Conn` 只暴露接口（`ID`、`RemoteAddr`、`Send`、`Close`、`CloseWithReason`、`CloseWithFrame`），测试可用 fake 替代真实 socket。
2. **`sessionID` 进程内单调递增，从 1 开始，重启失效**。由 `Manager.NextSessionID()`（`atomic.Uint64`）分配，只在当前进程内唯一，不作为跨进程或跨重启的稳定标识。
3. **同一 `(user, device)` 新连接替换旧连接**。`Register` 在锁内返回被替换的 Session，调用方在锁外执行 `CloseReplaced`：旧连接先收到 `CLOSE` 帧，再由写协程负责关闭（`CloseWithFrame` 保证帧写出后再断开）。注册表只保留新 Session，旧 Session 的 `Unregister` 因 ID 已不匹配而不会误删新会话。
4. **未登录连接不能 SEND**。`Handler.SessionFor(c)` 为空时回 `ERROR "not logged in"`；`DATA` 不受影响，继续回显以兼容 Phase 0/0.5。
5. **Phase 1 不做鉴权**。`LOGIN` 只是"声明身份"，服务端不校验密码、令牌或设备合法性；任何客户端都可以声明任意 `userID`/`deviceID`。鉴权属于后续阶段。
6. **连接关闭即注销**。`transport.Server.SetOnClose(handler.OnConnClosed)`，在 `Conn.Close` 内同步回调，删除 `conns` 映射并 `sessions.Unregister`，不阻塞。

## 5. 选择理由

1. **职责单一**：transport 不需要知道 `userID` 是什么，session 也不需要知道帧如何编码。两者通过 `session.Conn` 接口解耦，测试可以分别验证"传输行为"与"身份/注册表行为"。
2. **路由查找是只读快路径**：`FindByUser` / `Get` 只持 `RLock`，返回副本切片，调用方在锁外逐个 `Send`，避免持有注册表锁做可能失败的 I/O 入队。
3. **踢旧连接是显式的、可观测的**：`CloseWithFrame` 让旧客户端能收到 `CLOSE` 而不是莫名 EOF；日志记录 `reason="replaced by new login"`，便于排查"设备重复登录"。
4. **`sessionID` 简单够用**：单机进程内单调递增即可满足 endpoint 定向；不做持久化，避免在 Phase 1 引入存储与恢复语义。重启后旧 ID 失效是明确接受的行为。
5. **未登录限制把错误前移到最靠近入口的位置**：`SEND` 在 handler 层直接拒绝，router 不需要处理"来源身份为空"的复杂情况。
6. **不做鉴权是范围控制**：Phase 1 的目标是验证"连接 → 会话 → 路由"链路，而不是安全模型；把鉴权留到后续阶段可以避免在协议与存储未定型时过早固化认证流程。

## 6. 后果（优点和缺点）

优点：

- 传输层与业务层可独立测试、独立演进。
- 同一用户多设备天然支持（`byUser` 的 value 是 device → Session 的 map）。
- 重复登录语义明确：新连接生效、旧连接收到 `CLOSE`、注册表无残留。
- 连接关闭路径统一：transport 的 `onClose` 回调负责注销，业务代码不需要在每个错误分支手动清理。
- Session 注销是"按对象身份"而非"按 ID"删除，旧会话的延迟清理不会误删新会话。

缺点（具体到本项目）：

- **多一次间接层**：投递需要先查 `Manager`，再调 `Session.Conn.Send`；相比"Conn 自带身份"多一次 map 查找与接口调用，但实测在 1000 连接、每秒 1000 帧下可忽略（见[压测报告](压测报告.md)）。
- **`conns sync.Map` 与 `Manager` 双写**：登录时先 `sessions.Register` 再 `conns.Store`，两者不是原子操作；当前依赖"同一连接只在 readLoop 上串行处理 LOGIN"来避免并发登录，属于隐式约束。
- **`sessionID` 重启失效**：客户端不能把 `sessionID` 当作长期地址；跨重启的 endpoint 定向会得到 `target not found`。
- **无鉴权**：任何客户端可冒充任意用户，只适合受信网络与功能验证。
- **踢人是"先发 CLOSE 再关闭"**：如果旧连接发送队列恰好打满，`CloseWithFrame` 入队失败会立即 `Close`，旧客户端可能收不到 `CLOSE`；这是有界队列的固有取舍。

## 7. 被否决的方案

- **Session == Connection**：让 transport 承担身份与路由，破坏分层；连接关闭、测试与后续鉴权都会耦合进传输层。
- **允许同设备多连接并存**：会产生幽灵会话与重复投递，无法表达"设备当前只有一条有效会话"；重连场景下尤其明显。
- **持久化 Session**：Phase 1 无存储依赖，持久化会引入一致性、过期清理、重启恢复与 `sessionID` 分配策略，超出"单机实时 Gateway"的范围。
- **把 `sessionID` 做成 UUID / 全局雪花 ID**：当前没有跨节点需求，单调递增的 `uint64` 更小、更易读，也便于 endpoint 用十进制字符串表达。
- **登录时做鉴权**：协议、存储与运维模型尚未定型，Phase 1 明确不做；留待后续 ADR。

## 8. 后续演进方向

1. 引入鉴权（令牌/证书）后，`LOGIN` 的语义从"声明"变为"认证"，`Session` 增加认证主体与权限字段。
2. 为 `Session` 增加心跳/最后活跃时间，支持按空闲时间回收与运维查询。
3. 若进入多节点阶段，把 `sessionID` 升级为"节点 ID + 本地序号"或全局 ID，并引入跨节点注册表。
4. 把 `conns` 与 `Manager` 的双写收敛为一次原子注册，消除对"单协程处理 LOGIN"的隐式依赖。
5. 为重复登录提供可配置策略（踢旧 / 拒绝新 / 允许多连接），供不同业务选择。
