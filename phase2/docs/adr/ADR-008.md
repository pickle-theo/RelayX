# ADR-008：两级 ACK、幂等键与条件更新状态机

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/protocol/ack.go`、`internal/gateway/gateway.go`、`internal/store/message.go`、`internal/store/delivery.go`
- 关联决策：[ADR-007 事务边界与 ACCEPTED](ADR-007.md)、[ADR-009 离线 PULL 与重试](ADR-009.md)

## 1. 背景

Phase 1 的 `SEND → DELIVER` 没有任何确认：发送方不知道目标是否收到，平台也不知道投递是否成功。Phase 2 需要：

1. 区分“客户端收到了”与“业务处理完了”。
2. 目标离线、实时推送失败、进程崩溃后都能继续投递。
3. 客户端重连/重发时不产生重复消息。
4. 一条消息有多个收件端点时，能给出一个可查询的总体状态。

这要求 ACK 协议、幂等键与状态机三者一起设计，而不是只加一个“收到”标志位。

## 2. 当前问题

- ACK 应该有几级？分别由谁发送、在什么时机发送？
- 幂等键放在帧头还是 Body？由客户端生成还是服务端生成？
- 重复 `SEND`、重复 ACK、乱序 ACK 如何做到幂等？
- 多端点投递时，消息状态如何从投递状态聚合？
- 状态更新会不会互相覆盖（例如业务 ACK 覆盖过期）？

## 3. 候选方案

### 3.1 ACK 层级

#### 方案 A：单级 ACK

`DELIVER` 后客户端回一个 `ACK`，平台收到即认为成功。

- 优点：协议最简单，一次写入。
- 缺点：无法区分“收到但业务失败”与“业务成功”；平台会在业务失败时停止重试，丢失补救机会；也无法表达“已收到但还在处理”。

#### 方案 B：两级 ACK（本决策）

- `RECEIPT_ACK`：客户端收到并解码 `DELIVER` 后立即回，表示“已收到，可以停止无脑重推”。
- `BUSINESS_ACK`：业务处理完成后回，`status=0` 表示成功，非 0 表示业务失败。

- 优点：平台可以更早停止重试，同时保留业务结果；客户端实现可以分阶段。
- 缺点：两次写入、两种状态；客户端必须两处都实现。

#### 方案 C：三级 ACK（收到 / 入库 / 业务完成）

- 优点：语义最细。
- 缺点：多一级状态与超时，收益不明显；本项目没有“客户端本地持久化入库”的概念。

#### 方案 D：无 ACK，仅靠 TTL 与 PULL

- 优点：协议最简单。
- 缺点：平台无法知道何时停止重试；只能永远重推到 TTL，资源浪费且会产生大量重复。

### 3.2 幂等键

#### 方案 A：复用 SEND 帧头 `MsgID`（本决策）

- 优点：协议零改动；客户端本来就为每个 SEND 生成序号；数据库唯一约束直接落地。
- 缺点：`MsgID` 是 `uint64`，语义上只是“发送方序号”，需要文档明确其幂等含义；不同发送方的相同 `MsgID` 不冲突（唯一键包含 `from_user`）。

#### 方案 B：Body 中增加客户端 UUID

- 优点：全局唯一、可跨用户。
- 缺点：需要扩展 `SEND` Body；索引更宽；客户端要生成并持久化 UUID。

#### 方案 C：payload 哈希

- 优点：无需客户端配合。
- 缺点：哈希碰撞、计算成本、相同内容的不同消息会被误判为重复。

#### 方案 D：只用服务端生成的 `message_id`

- 优点：ID 全局唯一且单调。
- 缺点：客户端超时重发时拿不到原 ID，会创建新消息；无法解决“发送方重试”的幂等。

### 3.3 状态更新方式

- **读-改-写**：先 `SELECT state`，再在 Go 里判断，再 `UPDATE`。并发下会丢失更新，需要额外锁。
- **无条件 `UPDATE`**：直接写目标状态。重复/乱序 ACK 会把终态改回去。
- **条件 `UPDATE` + 影响行数判断（本决策）**：`WHERE state = 期望前态`，0 行即 no-op。

## 4. 决策

1. **两级 ACK**：
   - `RECEIPT_ACK(0x0B)`：`messageID(8)`，把 `SENT` 推进到 `RECEIPT_ACKED`。
   - `BUSINESS_ACK(0x0C)`：`messageID(8) + status(1)`，把 `SENT` 或 `RECEIPT_ACKED` 推进到 `BUSINESS_ACKED`（`status=0`）或 `BUSINESS_FAILED`（`status!=0`）。
2. **幂等键 = SEND 帧头 `MsgID`**，数据库唯一约束 `(from_user, client_msg_id)`。命中冲突时返回原消息 ID，`SEND_ACK.status=DUPLICATE`，不写消息、不写投递、不推送。
3. **`DELIVER` 帧头 `MsgID` = 平台 `message_id`**。客户端在两种 ACK 中都回填这个值；平台再结合登录身份 `(user_id, device_id)` 定位唯一投递行。
4. **所有状态变更使用条件 `UPDATE`**：
   - `RECEIPT_ACK`：`WHERE message_id=$1 AND user_id=$2 AND device_id=$3 AND state = 1`
   - `BUSINESS_ACK`：`WHERE ... AND state IN (1,2)`
   - `MarkDeliverySent`（保留，SEND 路径已改为受理时直接插入 `SENT`）：`WHERE ... AND state = 0`
   - `MarkDeliveryFailed`：`WHERE id=$1 AND state IN (0,1)`
   - `MarkDeliveryRetried` / `ClearRetrySchedule`：`WHERE id=$1 AND state = 1`
   影响行数为 0 时不报错，事务只提交一个 no-op。
5. **消息聚合在修改投递的同一条语句内重算**（ACK 路径内联，其它路径用 `recomputeMessageState`）：
   - 消息已是 `EXPIRED(3)` → 保持 3；
   - 全部投递终态（3/4/5/6）→ `COMPLETED(2)`；
   - 部分终态 → `PARTIAL(1)`；
   - 否则 → `ACCEPTED(0)`。
6. **重复 ACK 是幂等空操作**：重复 `RECEIPT_ACK` 在 `state=2/3/4` 时 0 行；重复 `BUSINESS_ACK` 在 `state=3/4` 时 0 行。晚到的 `RECEIPT_ACK` 不会把 `BUSINESS_ACKED` 降级。
7. **重复 `SEND` 不重新推送**：返回 `DUPLICATE` 后直接结束，不进入 `MarkDeliverySent` / `Deliver` 分支。

## 5. 选择理由

1. **两级 ACK 对应两个真实决策点**：客户端“收到了”与业务“处理完了”是不同事实；把两者分开，平台才能在业务失败时保留 `BUSINESS_FAILED` 终态，而不是误以为成功。
2. **帧头 `MsgID` 是现成的幂等载体**：Phase 1 已经为每个 SEND 填 `MsgID`，复用它不需要改 Body 布局，也不需要客户端引入 UUID 库。
3. **唯一约束比应用层去重可靠**：并发重复 SEND 也只有一个事务能插入；`ON CONFLICT DO NOTHING RETURNING` 让“插入或取回原 ID”成为一条 SQL。
4. **条件更新天然抗乱序**：网络可能让 `BUSINESS_ACK` 先于 `RECEIPT_ACK` 到达；`BUSINESS_ACK` 接受 `(1,2)`，先到也能正确落终态，后到的 `RECEIPT_ACK` 因 `state!=1` 自动忽略。
5. **聚合与投递同事务**：外部永远不会读到“投递已 `BUSINESS_ACKED`、消息仍 `ACCEPTED`”的中间态；查询消息状态即可得到一致结论。
6. **`EXPIRED` 粘性**：过期是业务上不可逆的终态；即使之后收到迟到的 ACK，也不应把消息“复活”为 `COMPLETED`。

## 6. 后果（优点和缺点）

优点：

- 发送方重试安全：同一 `MsgID` 只会产生一条消息。
- ACK 乱序/重复安全：条件更新 + 影响行数判断，不需要额外锁。
- 平台能区分“已收到未处理”与“业务成功/失败”，便于运维排查。
- 消息状态可直接用于报表与告警，不必每次聚合 `deliveries`。
- 协议只新增 5 种帧，Body 布局紧凑。

缺点（具体到本项目）：

- **两次 ACK 意味着两次数据库事务**：高频 ACK 会放大提交次数；压测中 ACK 写入与受理共用连接池。
- **幂等键的作用域是发送方用户，不是设备**：同一用户两台设备使用相同 `MsgID` 会被判重；客户端应保证 `MsgID` 在用户维度单调且重启后不复用。
- **演示客户端每次启动从 1 开始编号**：同一 user 重启后发送会与历史消息冲突并得到 `DUPLICATE`；这是演示客户端的限制，不是服务端缺陷。生产客户端需要持久化上次 `MsgID`。
- **`MsgID` 是 `uint64`，数据库列是 `BIGINT`**：当前只发送正数；超过 `2^63-1` 会溢出，协议层尚未拒绝。
- **`attempts` 同时被实时推送与 PULL 递增**：它不是严格意义上的“重试次数”，见 ADR-009。
- **消息状态是聚合结果，不是事实来源**：排障时仍应查 `deliveries` 的具体状态；聚合只用于快速判断。

## 7. 被否决的方案

- **单级 ACK**：无法表达业务失败，平台会在业务失败时停止重试；也无法区分“收到”与“处理完”。
- **三级 ACK**：多一级状态与超时，当前没有客户端本地持久化入库的语义，收益不足。
- **无 ACK + 永久重推**：资源浪费、重复爆炸，且无法在业务成功后停止。
- **客户端 UUID 作为幂等键**：需要改 Body、加宽索引、引入 UUID 生成与持久化；帧头 `MsgID` 已够用。
- **payload 哈希去重**：碰撞与 CPU 成本，且“相同内容”不等于“同一条消息”。
- **只用服务端 `message_id`**：无法解决客户端超时重发；重发会创建新消息。
- **读-改-写状态机**：并发下丢失更新，需要显式行锁；条件更新更简单。
- **无条件 `UPDATE`**：重复/乱序 ACK 会把终态改回前态，破坏幂等。
- **事件溯源（每条 ACK 追加事件）**：查询与聚合更复杂，当前规模不需要审计级事件流。
- **把消息状态做成投递状态的视图**：每次查询都要聚合，且无法表达“过期”这种消息级终态。

## 8. 后续演进方向

1. 让客户端持久化 `MsgID`（或改用 UUID），消除重启后的误判重。
2. 为 ACK 增加批量帧或合并写入，降低高频小事务的提交成本。
3. 增加 `RECEIPT_ACK` 超时监控与 per-status 指标，区分“客户端不读”与“网络丢包”。
4. 若引入多租户，把幂等键扩展为 `(tenant_id, from_user, client_msg_id)`。
5. 评估把 `messages.state` 改为由投递状态物化视图维护，减少每次 ACK 的额外 `UPDATE`。
