# ADR-007：PostgreSQL、pgx、事务边界与 ACCEPTED 语义

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/store/store.go`、`internal/store/message.go`、`internal/store/delivery.go`、`internal/store/migrations/0001_init.sql`、`cmd/gateway/main.go`、`docker-compose.yml`
- 关联决策：[ADR-008 两级 ACK 与幂等键](ADR-008.md)、[ADR-009 离线 PULL 与重试](ADR-009.md)

## 1. 背景

Phase 1 的 Gateway 是纯内存的：消息只存在于发送方 `readLoop` 的调用栈与目标连接的发送队列里，进程退出或目标离线即丢失。Phase 2 要求：

1. 受理后的消息在进程崩溃后仍可恢复。
2. 目标离线时消息不丢，登录后能补发。
3. 发送方重试不能产生重复消息。
4. 单机、可本地复现、不引入运维复杂度。

这要求一个**持久化存储**、明确的**事务边界**，以及一个可被客户端理解的“已受理”语义。

## 2. 当前问题

需要回答：

1. 用什么存储？嵌入式数据库、内存 WAL，还是独立数据库？
2. 受理消息时，消息行与投递行是否在同一个事务里？
3. 什么时候回 `SEND_ACK`？“已受理”到底承诺了什么？
4. 数据库驱动怎么选？连接池多大？
5. 迁移如何执行，多个进程同时启动会怎样？

## 3. 候选方案

### 3.1 存储

#### 方案 A：SQLite（嵌入式，单文件）

- 优点：零运维、单文件、随项目分发；事务与索引能力足够。
- 缺点：写并发只有单写者；`SELECT ... FOR UPDATE` 不可用；与 Go 进程共享文件锁在 Windows 上行为复杂；后续多实例无法直接扩展。

#### 方案 B：内存 + 追加 WAL 文件

- 优点：延迟最低，完全可控。
- 缺点：需要自己实现恢复、索引、过期清理、并发控制；本质是重造一个数据库，测试面远大于业务面。

#### 方案 C：PostgreSQL（本机 Docker，本决策）

- 优点：成熟的事务/隔离级别、部分索引、`FOR UPDATE`、`ON CONFLICT`、`pg_advisory_xact_lock`；本机 Docker 一条 `make db-up` 即可复现；后续可平滑迁移到独立实例。
- 缺点：引入容器与连接管理；每次提交有 WAL fsync 成本；单机单容器是单点。

#### 方案 D：MySQL / MariaDB

- 优点：同样成熟，团队可能更熟悉。
- 缺点：本项目没有既有 MySQL 运维资产；PostgreSQL 的部分索引、`FILTER`、`RETURNING`、advisory lock 更贴合当前 SQL。

#### 方案 E：托管 PostgreSQL / 云数据库

- 优点：免运维、可扩展。
- 缺点：Phase 2 的目标是本地可复现实验，引入网络与账号依赖会破坏“一条命令跑起来”的体验。

### 3.2 驱动

- **`database/sql` + `pgx/v5/stdlib`（本决策）**：标准接口、连接池由 `database/sql` 管理、测试可用 `sqlmock` 或真实库；pgx 提供高性能协议实现。
- **pgx 原生 `pgxpool`**：性能与类型支持更好，但 API 面更大，项目其余部分只需要 `Query/Exec/BeginTx`。
- **`lib/pq`**：成熟但维护模式，类型与性能不如 pgx。

### 3.3 受理事务边界

- **方案 1：消息与投递分两个事务**：先插消息，再逐条插投递。崩溃可能留下“有消息无投递”的孤儿，需要补偿任务。
- **方案 2：消息与全部投递同一事务（本决策）**：要么全部可见，要么全部不可见。
- **方案 3：先写投递再写消息**：外键约束要求消息先存在；且同样需要补偿。

## 4. 决策

1. **使用 PostgreSQL 17（`postgres:17-alpine`），由本机 Docker Compose 提供，容器名 `relayx-phase2-pg`，端口 `5432`，数据放命名卷。** `make db-up` / `make db-down` 管理生命周期。开发/压测环境的容器以 `command` 追加 `-c synchronous_commit=off -c max_connections=100`（理由与风险见第 9 节）。
2. **使用 `database/sql` + `github.com/jackc/pgx/v5/stdlib`**，驱动名 `pgx`；不引入 ORM，SQL 全部显式书写。
3. **连接池默认 `MaxOpenConns=16`、`MaxIdleConns=8`**；启动时 `PingContext` 受 `-db-connect-timeout`（默认 5s）约束，失败信息只暴露 host，不泄露 DSN 密码。
4. **迁移内嵌在二进制中**（`//go:embed migrations/*.sql`），每个版本在独立事务中执行，先取 `pg_advisory_xact_lock(0x72656c6179)`，再查 `schema_migrations`；已应用的版本跳过。重复/并发启动不会重复建表。
5. **受理是单条语句（隐式事务）**：一个 `WITH msg AS (INSERT messages ... ON CONFLICT DO NOTHING RETURNING id), created AS (INSERT deliveries ... SELECT ... FROM msg CROSS JOIN unnest(...)) SELECT id FROM msg` 同时写入消息与全部投递行。重复消息返回空集，再走一次只读 `SELECT id` 分支。原子性与“消息 + 全部投递要么都在、要么都不在”的约束不变。
6. **`SEND_ACK(ACCEPTED)` 在语句成功返回之后发送**。`ACCEPTED` 的唯一承诺是：消息行 + 全部收件端点的投递行已持久化。它不承诺在线、不承诺写出 socket、不承诺客户端或业务已处理。
7. **在线端点的投递行在受理时直接写成 `SENT`**：`AcceptRequest.Online` 标记受理前仍有活跃 Session 的端点，这些行以 `state=1, attempts=1, next_retry_at=now()+backoff(0)` 插入，受理后只做一次内存队列推送，**不再有单独的 `MarkDeliverySent` 写事务**。离线端点仍写 `PENDING`，等待 PULL。若目标在受理与推送之间掉线，行已是 `SENT` 且有重试时间，由 Worker 兜底——与旧实现“先标记再推送失败”的恢复路径完全一致。
8. **`dbTimeout=5s` 约束连接协程内的每一次数据库调用**；统计协程使用独立的 1s 超时，超时以 `deliveries_pending=-1` 作为哨兵。

## 5. 选择理由

1. **事务边界与业务语义一致**：一条消息对 N 个端点的投递要么全部存在，要么全部不存在；不存在“部分端点可拉取、部分端点永远收不到”的中间态。
2. **提交先于 ACK**：客户端收到 `ACCEPTED` 后可以安全地停止重发；即使 Gateway 随后崩溃，消息也能通过 PULL/重试恢复。反过来（先 ACK 后提交）会产生“客户端认为已受理、服务端实际没落库”的丢消息窗口。
3. **`ON CONFLICT` 是数据库级幂等**：不依赖进程内缓存或分布式锁；并发重复 SEND 也只有一个事务能插入成功。
4. **pgx + `database/sql` 的取舍**：项目只需要标准查询与事务，`database/sql` 的连接池、超时、`Rows` 生命周期足够；pgx 提供底层协议性能与 `TIMESTAMPTZ`/`BYTEA` 的良好支持。
5. **本机 Docker 换取可复现性**：评审者不需要安装 PostgreSQL，`make db-up` 即可得到与压测一致的环境；代价是 Docker Desktop 的 WAL fsync 与端口转发开销（见压测报告）。
6. **迁移内嵌 + advisory lock**：二进制自带 schema，不会出现“代码版本与迁移文件不一致”；advisory lock 让并发启动安全。

## 6. 后果（优点和缺点）

优点：

- 受理是原子的，崩溃恢复语义清晰。
- 幂等由唯一约束保证，不依赖应用层状态。
- schema 随二进制发布，部署只需一个可执行文件 + DSN。
- 部分索引、`FOR UPDATE`、`RETURNING` 让 PULL、ACK、过期都能用单条 SQL 表达。
- 连接池与超时有明确上界，故障时请求不会无限挂起。

缺点（具体到本项目）：

- **每条消息固定 3 次数据库往返**：受理、RECEIPT_ACK、BUSINESS_ACK 各一条自包含语句。每条消息的 3 次写入是可靠投递语义决定的，不能靠合并 ACK 消除；能优化的只是每次写入的往返次数与提交等待（见第 9 节实测）。
- **单机单容器是单点**：容器或磁盘故障会同时丢失受理与投递能力；没有主备/副本。
- **连接池是全局瓶颈**：默认 16 条连接被 1000 个连接协程共享，数据库调用排队会直接表现为 `SEND_ACK` 延迟。
- **`ACCEPTED` 容易被误读**：调用方若把它当成“已送达”，会在业务上产生错误预期；文档与协议注释必须反复强调。
- **迁移只前进不后退**：没有 down migration；schema 变更需要手工回滚或新建版本。
- **`dbTimeout=5s` 是硬编码**：不可通过 flag 调整；数据库抖动时所有请求在同一时间窗失败。
- **`resolveRecipients` 与 `AcceptMessage` 各用独立的 5s 上下文**：受理不再有后续的写事务，因此不存在“第二个写操作继承已耗尽 deadline”的问题；但端点的在线判断发生在受理之前，若目标在这段窗口内掉线，该行仍按在线写入 `SENT`，需要 Worker 重试一次才能纠正。

## 7. 被否决的方案

- **SQLite**：单写者与缺少 `FOR UPDATE` 会让 PULL 的并发正确性依赖应用层锁；Windows 文件锁与容器化部署也更麻烦。
- **内存 + 自研 WAL**：恢复、索引、过期、并发控制全部自研，测试成本远高于业务价值。
- **MySQL**：没有既有运维资产；当前 SQL 大量使用 PostgreSQL 专有能力。
- **托管数据库**：破坏本地一条命令复现的目标；Phase 2 不需要多可用区。
- **`lib/pq`**：维护模式，类型与性能不占优。
- **原生 `pgxpool`**：API 面更大，当前只需要标准 `database/sql` 能力。
- **消息与投递分事务**：会产生孤儿消息，需要额外补偿任务；收益只是“消息先可见”，对本项目无意义。
- **先 ACK 后提交**：会产生丢消息窗口，违背 At-Least-Once 的核心承诺。
- **把在线端点的 `PENDING → SENT` 标记并入受理事务（最初否决，后采纳）**：当初的顾虑是“目标是否在线”会参与受理事务的成败。实测后改为在受理前解析在线集合、只传递一个布尔标记，在线判断不会让受理失败，只决定投递行的初始状态，因此采纳（见第 9 节）。

## 8. 后续演进方向

1. **批量处理 ACK**：当前每条 ACK 一次数据库往返；若吞吐需要继续提升，可把同一连接的多个 ACK 合并为一条 `UPDATE ... WHERE (message_id, user_id, device_id) IN (...)`，用“单次往返更新多行”换取吞吐（代价是 ACK 的持久化延迟略微增加）。
2. **调优 WAL/提交**：`synchronous_commit=off` 已用于开发/压测环境（第 9 节）。生产环境应保持 `on`，改用批量提交、更高规格存储或独立数据盘。
3. **连接池与超时可配置**：把 `dbTimeout` 提升为 flag，并按 CPU/磁盘实测调整 `MaxOpenConns`。
4. **读写分离/分区**：`messages` 按时间分区，`deliveries` 按终态归档，控制单表增长。
5. **多实例**：引入 advisory lock 之外的租约或队列，避免多个 Gateway 同时扫描同一批重试/过期行。

## 9. 2026-11-11 压测后的修订

初版在 1000 连接可靠模式下未通过（`ack_missed=32005`，见[压测报告](../压测报告.md)）。排查结论与对应修订：

| 测量 | 结果 | 结论 |
| --- | --- | --- |
| `pgbench` 16 客户端简单更新 | 10077 tps，1.588 ms/事务 | PostgreSQL 本身不是瓶颈 |
| `pgbench` 复刻受理事务 | 6222 tps | 同样的两条 INSERT，PG 侧可到 6k/s |
| 存储层基准（受理 + 两级 ACK，16 并发） | 775 msg/s（12 次往返/消息） | Go 侧往返与提交等待是瓶颈 |
| 仅受理、不发 ACK（1000 连接 30s） | 约 980 msg/s，`ack_missed=0` | 受理路径本身接近上限，ACK 让总写入翻三倍 |

修订内容：

1. **开发/压测容器加 `-c synchronous_commit=off -c max_connections=100`**。取舍：PostgreSQL 进程崩溃不丢已提交事务，但 OS 崩溃/断电可能丢失最近若干毫秒到数百毫秒的提交。**生产必须用 `on`**，本仓库不声称 `on` 下能达到同样吞吐。
2. **在线端点的投递行在受理语句中直接写为 `SENT`**（`AcceptRequest.Online`），删除单独的 `MarkDeliverySent` 调用。
3. **受理与两级 ACK 各压缩为一条语句（隐式事务）**，每条消息的数据库往返从 12 次降到 3 次。

结果：同一台机器、同样的 1000 连接 × 60s 参数，从 `ack_missed=32005`、`P99 5872 ms`、退出码 1，变为 `ack_missed=0`、退出码 0；两次通过的运行 P99 分别为 699 ms 与 467 ms（同机抖动，见[压测报告](../压测报告.md)第 7.1 节）。
