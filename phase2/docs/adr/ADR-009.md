# ADR-009：离线 PULL、游标、TTL、重试与背压

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/protocol/pull.go`、`internal/gateway/gateway.go`、`internal/store/delivery.go`、`internal/delivery/worker.go`
- 关联决策：[ADR-007 事务边界](ADR-007.md)、[ADR-008 两级 ACK](ADR-008.md)、[ADR-006 路由与背压](../../../phase1/docs/adr/ADR-006.md)

## 1. 背景

在线实时推送只能覆盖“目标此刻有连接”的情况。Phase 2 的目标是单机 At-Least-Once，因此必须回答：

1. 目标离线期间的消息放在哪里、占多少内存？
2. 目标重新上线后，如何知道从哪条开始补发？
3. 推送失败/客户端不 ACK 时，重试多久、多少次？
4. 消息永久不处理时，如何回收？
5. 目标消费过慢时，背压落在谁身上？

## 2. 当前问题

- 能否在服务端为每个用户维护离线队列？
- 补发由服务端主动推，还是客户端主动拉？
- 游标用什么字段？游标由谁保存？
- 重试的退避曲线、上限与终止条件是什么？
- PULL 一页多大？服务端如何避免被大量离线消息拖垮？

## 3. 候选方案

### 3.1 离线补发

#### 方案 A：服务端内存离线队列

每个用户一个 `chan`/切片，离线时入队，上线时消费。

- 优点：上线推送延迟低，实现直观。
- 缺点：进程重启即丢；每用户队列内存无上界；需要额外的淘汰、优先级与持久化，最终还是要落库。

#### 方案 B：服务端持久化 + 主动推送（push-only）

离线消息落库，后台协程不断扫描并对在线目标重推。

- 优点：不需要客户端改协议。
- 缺点：目标刚上线时，服务端不知道“从哪条开始”，只能全量扫描；大量离线目标会造成无效扫描；客户端无法控制补发节奏。

#### 方案 C：在线推送 + 离线 PULL（本决策）

在线走实时 `DELIVER`；离线保持 `PENDING`，客户端登录后主动 `PULL`，按投递 ID 游标分页。

- 优点：服务端不为离线用户保留内存队列；补发节奏由客户端控制；游标天然分页；崩溃后游标可从 0 重放（有重复但可幂等）。
- 缺点：客户端必须实现 PULL 循环与游标持久化；补发有额外一次往返；游标与并发提交存在乱序风险（见第 6 节）。

#### 方案 D：服务端保存每设备 offset

服务端为 `(user, device)` 维护已确认到的水位，客户端不传游标。

- 优点：客户端简单。
- 缺点：多一份需要持久化与清理的状态；多设备/重装/换机时语义复杂；当前 `deliveries` 已经是事实来源，再存 offset 属于重复状态。

### 3.2 游标字段

- **`deliveries.id`（本决策）**：单调递增、有主键索引、与 `(user_id, device_id, id)` 部分索引完全匹配。
- **`messages.created_at`**：同一毫秒内多条消息需要额外 tie-breaker，且与投递顺序不完全一致。
- **`messages.id`**：一条消息 fan-out 到多个端点时，端点维度不连续；仍可作为候选，但需要 join 与额外过滤。
- **复合 `(created_at, id)`**：更精确，但索引与比较都更复杂。

### 3.3 重试策略

- **固定间隔**：实现简单，但故障恢复时会产生大量同时重试。
- **指数退避（本决策）**：`base * 2^attempts`，上限 `60s`，默认最多 5 次；分散重试压力。
- **无限重试**：不丢消息，但永久占用扫描批次；必须依赖 TTL 终止。
- **只靠 PULL、不重试**：在线但短暂抖动的目标会延迟到下一次 PULL，实时性差。

## 4. 决策

1. **在线推送 + 离线 PULL 并存**：
   - 受理前解析每个端点是否有活跃 Session（`AcceptRequest.Online`）。
   - 目标在线：投递行在受理语句中直接写为 `SENT`、`attempts=1`、已排首次重试，随后只做一次内存队列 `DELIVER`，没有额外的写事务。
   - 目标离线：写 `PENDING`，等待客户端 `PULL`。
2. **PULL 协议**：`PULL(cursor uint64, limit uint16)`；`limit=0` 用服务端 `-pull-limit`（默认 100），上限 `-pull-max-limit`（默认 500，硬上限 65535）。响应 `PULL_DONE(count uint16, nextCursor uint64, hasMore bool)`。
3. **游标语义**：服务端查询 `WHERE user_id=$1 AND device_id=$2 AND state IN (0,1) AND id > cursor ORDER BY id LIMIT limit+1`；多取 1 行只用于 `hasMore`。`nextCursor` 是本页最后一条**成功入队**的投递 ID；入队失败时立即停止、`hasMore=true`、游标不前进。
4. **PULL 是单事务**：`SELECT ... FOR UPDATE OF d` 锁行，逐行 `UPDATE` 为 `SENT`、`attempts+1`、设置 `next_retry_at`，然后提交。行在发送 `DELIVER` 前已变为 `SENT`；若进程在发送前崩溃，Worker 会按 `next_retry_at` 重试。
5. **TTL**：`expire_at = 受理时刻 + -message-ttl`（默认 24h）。Worker 每 `-retry-interval`（默认 1s）扫描一次，`-expire-batch`（默认 100）条；过期消息的非终态投递转 `EXPIRED`，消息转 `EXPIRED`。
6. **重试退避**：`delay = min(base * 2^attempts, max)`，`base=2s`、`max=60s`；`-retry-max-attempts=5`。首次实时推送计 1 次，之后最多 4 次重试。
7. **离线/队列满不重试**：Worker 发现目标无在线 Session，或 `Deliver` 入队失败（队列满/连接关闭），调用 `ClearRetrySchedule` 把 `next_retry_at` 置空，交由客户端 PULL 恢复；这样避免对离线目标做无效扫描。
8. **背压边界**：
   - 实时推送复用目标连接的**有界发送队列**（默认 256 帧 / 4 MiB），`Send` 非阻塞；队列满只影响该目标，不阻塞发送方。
   - PULL 单页最多 500 条，服务端不会一次性把全部离线消息读入内存。
   - Worker 单轮最多处理 100 条到期重试 + 100 条过期消息，避免单轮占用连接池过久。
   - 离线消息只存在于 PostgreSQL，不在 Gateway 内存中排队。
9. **游标由客户端保存**：服务端不记录每设备 offset；客户端重装/换机后从 0 开始会重复收到 `PENDING/SENT` 行，业务按 `messageID` 幂等。

## 5. 选择理由

1. **离线消息的内存上界为 0**：所有离线状态都在 PostgreSQL，Gateway 重启不会丢；这是单机可靠投递最重要的性质。
2. **PULL 让客户端控制节奏**：弱网/移动端可以先拉一页、处理完再拉下一页；服务端不需要为每个离线用户跑推送协程。
3. **`deliveries.id` 与索引完全匹配**：`(user_id, device_id, id) WHERE state IN (0,1)` 让游标查询是索引范围扫描，不需要额外排序或过滤。
4. **`FOR UPDATE` + 单事务**：同一端点的并发 PULL 不会重复取到同一行；页内标记与读取原子可见。
5. **退避 + 上限 + TTL 三重终止**：不会出现“永远重试一条坏消息”；离线目标也不会消耗重试批次。
6. **入队失败不丢行**：在线投递行在受理语句中已落为 `SENT` 并排好首次重试，`Deliver` 入队失败后行仍有重试时间；若目标已离线，Worker 会 `ClearRetrySchedule`，最坏情况由 PULL 兜底。

## 6. 已知限制

1. **游标与并发提交的乱序风险**：`deliveries.id` 在 `INSERT` 时分配，但事务提交顺序可能与 ID 顺序不同。端点 A 的投递 `101` 先提交、`100` 后提交时，客户端 `PULL(cursor=101)` 会永久跳过 `100`。当前没有低水位/提交序列游标；单机、低并发下窗口很小，但这是设计上的真实缺口。
2. **PULL 会计入 `attempts`**：每次 PULL 都把行标记 `SENT` 并 `attempts+1`。客户端反复拉取但不 ACK，会让 `attempts` 很快达到 5；之后 Worker 可能把该投递转 `FAILED`。`attempts` 的语义是“推送次数”，不是“失败重试次数”。
3. **重复投递**：在线推送、Worker 重试、PULL 三条路径可能各发一次 `DELIVER`；平台按 At-Least-Once 设计，客户端必须按 `messageID` 幂等。
4. **客户端游标不持久化**：从 0 重放会重复收到所有 `PENDING/SENT` 行；没有服务端 offset 可以“续传”。
5. **无严格全局顺序**：PULL 按 `deliveries.id` 排序，但并发受理的提交顺序不保证；跨发送方的消息顺序也不保证。
6. **PULL 页大小与往返**：默认 100、最大 500；大量积压时需要多次往返，客户端应循环到 `hasMore=false`。
7. **TTL 扫描是单协程、批量 100**：积压超过 100 时，过期处理会跨多轮；在过期扫描处理到之前，`PullPending` 不过滤 `expire_at`，仍可能把已过期的 `PENDING/SENT` 行返回给客户端。Worker 重试会检查 `expire_at` 并跳过（交给过期扫描）。
8. **Worker 单实例**：没有租约/选主；多 Gateway 同时运行会对同一批到期行重复推送。当前定位是单机单实例。

## 7. 被否决的方案

- **服务端内存离线队列**：重启即丢、内存无上界、仍需持久化；与 At-Least-Once 目标冲突。
- **push-only + 全量扫描**：目标上线时无法高效定位起点，离线用户多时扫描成本高。
- **无限重试**：永久占用批次，坏消息无法终止；必须依赖 TTL，语义也不清晰。
- **只靠 PULL、不做在线推送**：在线目标也要等下一次 PULL，实时性差。
- **服务端保存每设备 offset**：多一份需要持久化、清理与迁移的状态；`deliveries` 已是事实来源。
- **用 `messages.created_at` 做游标**：同毫秒多消息需要 tie-breaker，且与端点投递顺序不一致。
- **长轮询/WebSocket 流式补发**：协议改动大，当前 14 帧的请求-响应模型已够用。
- **优先队列/多级重试队列**：当前只有一种消息类型，引入优先级会放大状态与运维复杂度。

## 8. 后续演进方向

1. 引入**低水位游标**：以事务提交序列（如 `pg_current_snapshot()` / `xmin`）或“安全水位”避免跳过晚提交的低 ID 行。
2. 区分 `attempts` 与 `pull_count`：PULL 不计入失败重试，避免客户端频繁拉取导致 `FAILED`。
3. 客户端持久化游标与已处理 `messageID`，实现断点续传与更精确的幂等。
4. 为 PULL 增加服务端限流与按端点配额，防止单个设备一次拉走过多消息。
5. 多实例阶段引入租约/选主或 `SKIP LOCKED` 批量领取，避免 Worker 重复推送。
6. 为 TTL 与重试增加指标（过期数、失败数、重试延迟分布），替代当前仅靠 stats 日志。
