# Phase 2 数据模型

本文描述 Phase 2 的 PostgreSQL schema、字段语义、唯一约束、索引与查询、事务边界、幂等键、游标语义和状态聚合规则。DDL 以 [`internal/store/migrations/0001_init.sql`](../internal/store/migrations/0001_init.sql) 为唯一事实来源。

## 1. 表概览

| 表 | 作用 | 增长特征 |
| --- | --- | --- |
| `endpoints` | 登录过的 `(user_id, device_id)` 端点 | 与用户设备数同阶，登录时 upsert |
| `messages` | 一条逻辑消息（发送方幂等键、目标、payload、TTL、聚合状态） | 每条被受理的消息 1 行 |
| `deliveries` | 一条消息对一个端点的投递状态 | 每个收件端点 1 行；在线/离线、重试都只更新本行 |
| `schema_migrations` | 已应用的迁移版本 | 仅迁移时写入 |

没有软删除、消息历史归档或死信表；终态行保留到运维侧清理。

## 2. DDL 摘要

```sql
CREATE TABLE endpoints (
    user_id      TEXT        NOT NULL,
    device_id    TEXT        NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (user_id, device_id)
);

CREATE TABLE messages (
    id            BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    client_msg_id BIGINT      NOT NULL,
    from_user     TEXT        NOT NULL,
    from_device   TEXT        NOT NULL,
    target_type   SMALLINT    NOT NULL,
    target        TEXT        NOT NULL,
    payload       BYTEA       NOT NULL,
    state         SMALLINT    NOT NULL DEFAULT 0,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    expire_at     TIMESTAMPTZ NOT NULL,
    CONSTRAINT messages_from_user_client_msg_id_key
        UNIQUE (from_user, client_msg_id)
);

CREATE TABLE deliveries (
    id            BIGINT      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    message_id    BIGINT      NOT NULL REFERENCES messages (id) ON DELETE CASCADE,
    user_id       TEXT        NOT NULL,
    device_id     TEXT        NOT NULL,
    state         SMALLINT    NOT NULL DEFAULT 0,
    attempts      INT         NOT NULL DEFAULT 0,
    next_retry_at TIMESTAMPTZ,
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT deliveries_message_user_device_key
        UNIQUE (message_id, user_id, device_id)
);

CREATE TABLE schema_migrations (
    version    INT PRIMARY KEY,
    applied_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

说明：

- 没有 `CHECK` 约束限制 `state` / `target_type` 的取值，合法性由 Go 层常量保证。
- `payload BYTEA NOT NULL`；Go 层把 `nil` payload 归一化为空字节串。
- `deliveries.message_id` 外键 `ON DELETE CASCADE`，删除消息会连带删除投递。
- `endpoints` 不存“在线状态”；在线只存在于 `session.Manager`，数据库只记录“曾经登录过的端点”。

## 3. 字段语义

### 3.1 `endpoints`

| 字段 | 语义 |
| --- | --- |
| `user_id` | 登录 userID，1..64 字节，大小写敏感 |
| `device_id` | 登录 deviceID，1..64 字节；为空时客户端回退为 `-name` |
| `created_at` | 首次 upsert 时间 |
| `last_seen_at` | 最近一次 LOGIN 时间；`ON CONFLICT DO UPDATE` 刷新 |

### 3.2 `messages`

| 字段 | 语义 |
| --- | --- |
| `id` | 平台消息 ID（`BIGINT IDENTITY`），`DELIVER` 帧头 `MsgID` 与两级 ACK 的 `messageID` 都用它 |
| `client_msg_id` | 发送方 SEND 帧的 `MsgID`（`uint64` 存入 `BIGINT`） |
| `from_user` / `from_device` | 受理时的登录身份，不接受客户端自报 |
| `target_type` | `1` = user，`2` = endpoint |
| `target` | userID，或 endpoint 模式下十进制 session ID 的文本 |
| `payload` | 原始字节；服务端不做内容解析 |
| `state` | 聚合状态，见第 8 节；默认 `0 ACCEPTED` |
| `created_at` | 受理事务开始后的数据库时间 |
| `expire_at` | Gateway 以 `受理时刻 + -message-ttl` 计算并显式写入 |

`client_msg_id` 是 `BIGINT`，而帧头 `MsgID` 是 `uint64`；当前客户端只发送正数，因此不会溢出。若未来允许 `> 2^63-1` 的 `MsgID`，需要在协议层拒绝或改用 `NUMERIC`。

### 3.3 `deliveries`

| 字段 | 语义 |
| --- | --- |
| `id` | 投递 ID，按插入顺序递增；PULL 游标使用它 |
| `message_id` | 所属消息 |
| `user_id` / `device_id` | 收件端点；受理时由 `endpoints` 解析结果写入 |
| `state` | 投递状态，见第 7 节；默认 `0 PENDING` |
| `attempts` | 已发起的推送次数；实时推送、PULL、重试都会 `+1` |
| `next_retry_at` | 下一次可重试时间；`NULL` 表示不参与重试扫描 |
| `updated_at` | 最近一次状态/重试时间变更 |

### 3.4 `schema_migrations`

| 字段 | 语义 |
| --- | --- |
| `version` | 迁移文件名数字前缀，如 `0001_init.sql` → `1` |
| `applied_at` | 该版本提交时间 |

迁移由 `store.Migrate` 在 `pg_advisory_xact_lock(0x72656c6179)` 下逐版本执行；已应用的版本跳过，因此重复启动/并发启动不会重复建表。

## 4. 唯一约束与幂等键

| 约束 | 列 | 作用 |
| --- | --- | --- |
| `endpoints_pkey` | `(user_id, device_id)` | 一个用户在一个设备上只有一条端点记录 |
| `messages_from_user_client_msg_id_key` | `(from_user, client_msg_id)` | **发送幂等键**：同一发送方的同一 `MsgID` 只受理一次 |
| `deliveries_message_user_device_key` | `(message_id, user_id, device_id)` | 一条消息对同一端点只有一条投递；受理循环也会在 Go 层去重 |

幂等的精确语义：

1. 幂等范围是**发送方用户**，不是设备。同一 `from_user` 的两台设备使用相同 `client_msg_id`，第二台会被判为重复。
2. 命中唯一约束时，`AcceptMessage` 走 `INSERT ... ON CONFLICT DO NOTHING RETURNING id` 的 `sql.ErrNoRows` 分支，改为 `SELECT id` 返回原消息 ID；不写消息、不写投递、不推送，Gateway 回 `SEND_ACK(DUPLICATE, 原 messageID)`。
3. 重复 `SEND` 不会刷新 `expire_at`，也不会改变原消息状态。
4. 幂等键只保证“入库一次”，不保证“只投递一次”；客户端仍可能收到重复 `DELIVER`（实时推送与重试/ PULL 交叉）。

## 5. 索引与对应查询

| 索引 | 定义 | 对应查询 | 说明 |
| --- | --- | --- | --- |
| `deliveries_pull_idx` | `(user_id, device_id, id) WHERE state IN (0,1)` | `PullPending`：`WHERE user_id=$1 AND device_id=$2 AND state IN (0,1) AND id>$3 ORDER BY id LIMIT $4 FOR UPDATE OF d` | 部分索引只覆盖“待推送/已推送未确认”，按 `id` 顺序直接满足游标与排序 |
| `deliveries_retry_idx` | `(next_retry_at) WHERE state = 1` | `DueRetries`：`WHERE state=1 AND next_retry_at IS NOT NULL AND next_retry_at <= $1 ORDER BY next_retry_at, id LIMIT $2` | 只索引 SENT 行，避免 PENDING 与终态行进入重试扫描 |
| `messages_expire_idx` | `(expire_at) WHERE state IN (0,1)` | `ListExpiredMessages`：`WHERE expire_at <= $1 AND state IN (0,1) ORDER BY expire_at LIMIT $2` | 只索引非终态消息 |

辅助索引（由约束自动创建）：

- `messages_from_user_client_msg_id_key` 支撑重复 SEND 的原 ID 查询。
- `deliveries_message_user_device_key` 的前导列 `message_id` 支撑 ACK、过期、`MarkDeliverySent` 按消息定位投递。
- `endpoints_pkey` 的前导列 `user_id` 支撑 `ListEndpoints`。

已知的查询放大点：

- `PullPending` 在同一事务内对每一行执行一条 `UPDATE`，一页 N 行就是 N 次语句往返（仍是一次提交）。
- `CountPendingDeliveries` 是 `SELECT count(*) FROM deliveries WHERE state IN (0,1)`，走 `deliveries_pull_idx` 的部分索引，但仍是全索引计数；它在 stats 协程中执行，超时 1s。

## 6. 事务边界

隔离级别为 PostgreSQL 默认的 **READ COMMITTED**。`withTx` 只在函数返回 `nil` 时 `COMMIT`，否则 `ROLLBACK`。

### 6.1 受理（`AcceptMessage`）

单条语句，隐式事务（`WITH ... INSERT ... RETURNING`）：

```text
WITH msg AS (
  INSERT INTO messages (...) VALUES (...)
    ON CONFLICT (from_user, client_msg_id) DO NOTHING
    RETURNING id
), created AS (
  INSERT INTO deliveries (message_id, user_id, device_id, state, attempts, next_retry_at)
  SELECT msg.id, u.user_id, u.device_id,
         CASE WHEN u.online THEN 1 ELSE 0 END,          -- 在线目标直接 SENT
         CASE WHEN u.online THEN 1 ELSE 0 END,          -- attempts=1
         CASE WHEN u.online THEN now()+backoff(0) END   -- 首次重试时间
  FROM msg
  CROSS JOIN unnest($uids::text[], $devs::text[], $online::boolean[]) AS u
  ON CONFLICT (message_id, user_id, device_id) DO NOTHING
  RETURNING 1
)
SELECT id FROM msg
```

```text
├─ 返回 1 行：新消息，SEND_ACK(ACCEPTED, id)
└─ 返回 0 行（重复）
     SELECT id FROM messages WHERE from_user=$1 AND client_msg_id=$2
     SEND_ACK(DUPLICATE, 原 id)，不写任何新行
```

- 消息与**全部**投递行在同一条语句内提交；不存在“消息已入库但投递行只写了一半”的可见状态。
- 语句成功返回后才回 `SEND_ACK(ACCEPTED)`；失败回 `SEND_ACK(INTERNAL)`，不产生任何行。
- `unnest` 的三数组等长，端点去重由 `ON CONFLICT (message_id, user_id, device_id) DO NOTHING` 兜底；调用方仍会先做一次内存去重。
- 在线端点由 `AcceptRequest.Online` 标记（Gateway 在受理前 `sessions.FindByDevice` 解析），插入即为 `SENT`、`attempts=1`、已排首次重试，因此**不再有单独的 `MarkDeliverySent` 写事务**。离线端点保持 `PENDING`，等待 PULL。
- 若目标在受理与推送之间掉线，行已是 `SENT` 且有重试时间，Worker 会重试并在目标离线时清除重试计划；不会丢消息。
- 一次语句往返取代了 `BEGIN` + 两条 `INSERT` + `COMMIT` 四次往返。`MarkDeliverySent` 方法仍保留（其他路径/测试可用），但 Gateway 的 SEND 路径不再调用它。

### 6.2 两级 ACK

`ApplyReceiptAck`（单条语句，隐式事务）：

```text
WITH upd AS (
  UPDATE deliveries SET state=2, next_retry_at=NULL, updated_at=now()
  WHERE message_id=$1 AND user_id=$2 AND device_id=$3 AND state = 1
  RETURNING message_id
)
UPDATE messages m SET state = CASE
    WHEN m.state = 3 THEN 3                                  -- EXPIRED 粘性
    WHEN EXISTS (SELECT 1 FROM deliveries d
                 WHERE d.message_id=$1 AND d.state IN (3,4,5,6)) THEN 1
    ELSE 0
  END
FROM upd WHERE m.id = upd.message_id
```

`ApplyBusinessAck` 条件为 `state IN (1,2)`，目标状态：

- `status = 0` → `3 BUSINESS_ACKED`
- `status != 0` → `4 BUSINESS_FAILED`

聚合条件用“快照中的终态数 + 本行”判断：终态数 + 1 等于该消息投递总数 → `COMPLETED`，否则 `PARTIAL`。

- 投递更新与消息聚合在**同一条语句**内完成，外部不会读到“投递已终态、消息仍是 ACCEPTED”的中间态。
- `RECEIPT_ACKED(2)` 不是终态，因此 RECEIPT_ACK 不会把消息推进到 `COMPLETED`，只会按是否已有终态投递得到 `ACCEPTED` 或 `PARTIAL`。
- 0 行更新（重复/乱序 ACK）时外层 `UPDATE ... FROM upd` 也影响 0 行，函数返回 `changed=false`，等价 no-op。

### 6.3 PULL（`PullPending`）

```text
BEGIN
  SELECT d.id, d.message_id, ..., m.payload
  FROM deliveries d JOIN messages m ON m.id = d.message_id
  WHERE d.user_id=$1 AND d.device_id=$2 AND d.state IN (0,1) AND d.id > $3
  ORDER BY d.id
  LIMIT limit+1
  FOR UPDATE OF d
  ├─ 多取 1 行作为 hasMore 探针；探针不返回、不更新
  └─ 对返回的每一行：
       UPDATE deliveries
       SET state=1, attempts=attempts+1,
           next_retry_at=now()+backoff, updated_at=now()
       WHERE id=$1
COMMIT
```

- `FOR UPDATE OF d` 锁住投递行，避免同一端点的并发 PULL 重复取到同一行。
- `limit+1` 探针只用于 `hasMore`，不会泄露给客户端。
- 行在**发送 `DELIVER` 之前**就已标记 `SENT`；若随后入队失败，`PULL_DONE.nextCursor` 不前进，下一次 PULL 会再次取到该行（`state=1` 仍在 `IN (0,1)` 范围内）。
- 一次 PULL 最多一个事务提交；但每行一次 `UPDATE`，页越大语句往返越多。

### 6.4 重试与失败

`DueRetries` 只读：

```sql
WHERE d.state=1 AND d.next_retry_at IS NOT NULL AND d.next_retry_at <= $1
ORDER BY d.next_retry_at, d.id LIMIT $2
```

`MarkDeliveryRetried`：单条 `UPDATE ... WHERE id=$1 AND state=1`，`attempts+1`，重排 `next_retry_at`。

`ClearRetrySchedule`：单条 `UPDATE ... SET next_retry_at=NULL WHERE id=$1 AND state=1`，用于目标离线或入队失败时“交给 PULL 恢复”。

`MarkDeliveryFailed`：

```text
BEGIN
  UPDATE deliveries SET state=6, next_retry_at=NULL, updated_at=now()
  WHERE id=$1 AND state IN (0,1)
  RETURNING message_id
  ├─ 0 行：COMMIT（已被 ACK/PULL 抢先，忽略）
  └─ 1 行：recomputeMessageState(message_id)
       COMMIT
```

Worker 在 `attempts >= 5` 时调用它。`attempts` 在每次推送前已 `+1`，因此默认配置下最多实际推送 5 次（首次实时推送 + 4 次重试）；当 `attempts` 达到 5 后的下一轮扫描把投递转为 `FAILED`。

### 6.5 过期（`ExpireMessage`）

```text
BEGIN
  UPDATE deliveries
  SET state=5, next_retry_at=NULL, updated_at=now()
  WHERE message_id=$1 AND state IN (0,1,2)

  UPDATE messages SET state=3 WHERE id=$1
COMMIT
```

- 只有 `PENDING` / `SENT` / `RECEIPT_ACKED` 会被改为 `EXPIRED`；已是 `BUSINESS_ACKED` / `BUSINESS_FAILED` / `FAILED` 的投递保持原终态。
- 消息状态无条件写 3；调用方 `ListExpiredMessages` 只返回 `state IN (0,1)` 的消息，因此正常路径不会覆盖 `COMPLETED`。
- 边界：若消息在“扫描返回 ID”与“执行 `ExpireMessage`”之间刚好完成全部业务 ACK，仍会被写成 `EXPIRED`。窗口是 Worker 同一轮内的毫秒级；业务上该消息已过 `expire_at`，视为过期可接受。见第 10 节。

## 7. 状态定义

### 7.1 消息（4 态）

| 值 | 常量 | 名称 | 含义 |
| --- | --- | --- | --- |
| 0 | `MessageAccepted` | `ACCEPTED` | 已持久化，尚无投递进入终态 |
| 1 | `MessagePartial` | `PARTIAL` | 至少一个投递终态，但未全部终态 |
| 2 | `MessageCompleted` | `COMPLETED` | 全部投递终态 |
| 3 | `MessageExpired` | `EXPIRED` | 超过 TTL，终态且不被重算覆盖 |

### 7.2 投递（7 态）

| 值 | 常量 | 名称 | 终态 |
| --- | --- | --- | --- |
| 0 | `DeliveryPending` | `PENDING` | 否 |
| 1 | `DeliverySent` | `SENT` | 否 |
| 2 | `DeliveryReceiptAcked` | `RECEIPT_ACKED` | 否 |
| 3 | `DeliveryBusinessAcked` | `BUSINESS_ACKED` | 是 |
| 4 | `DeliveryBusinessFailed` | `BUSINESS_FAILED` | 是 |
| 5 | `DeliveryExpired` | `EXPIRED` | 是 |
| 6 | `DeliveryFailed` | `FAILED` | 是 |

终态集合：`state IN (3,4,5,6)`。

## 8. 状态聚合规则

`recomputeMessageState` 必须在修改投递的同一事务内执行：

```sql
WITH agg AS (
    SELECT count(*) AS total,
           count(*) FILTER (WHERE state IN (3,4,5,6)) AS terminal
    FROM deliveries
    WHERE message_id = $1
)
UPDATE messages
SET state = CASE
    WHEN messages.state = 3 THEN 3
    WHEN agg.total > 0 AND agg.terminal = agg.total THEN 2
    WHEN agg.terminal > 0 THEN 1
    ELSE 0
END
FROM agg
WHERE messages.id = $1;
```

规则：

1. `EXPIRED` 优先：消息已是 3 就保持 3，ACK/重试不会把它改回 1/2。
2. `total > 0 且 terminal = total` → `COMPLETED`。
3. `terminal > 0` 但未全部终态 → `PARTIAL`。
4. 否则 → `ACCEPTED`。
5. 消息至少有一条投递行（受理时 `Endpoints` 非空），所以正常情况下 `total > 0`。

## 9. `ACCEPTED` 的准确含义

`SEND_ACK(ACCEPTED)` 与 `messages.state = 0` 都只表示：

> 消息行与**全部**收件端点的投递行已在同一个 PostgreSQL 事务中提交成功。

它**不**表示：

- 目标在线
- `DELIVER` 已写出 socket
- 客户端已 `RECEIPT_ACK`
- 业务已处理
- 消息最终不会过期

真正的送达证据是投递状态进入 `RECEIPT_ACKED` / `BUSINESS_ACKED`；最终成功证据是 `BUSINESS_ACKED`。

## 10. 已知边界

1. **游标与并发提交的乱序风险（ADR-009）**：`deliveries.id` 在 `INSERT` 时分配，但事务提交顺序可能与 ID 顺序不同。端点 A 的投递 `101` 先提交、`100` 后提交时，客户端 `PULL(cursor=101)` 会永久跳过 `100`。当前实现不提供“低水位”或“按提交时间”游标；依赖受理路径逐一提交且窗口很小，但这是设计上的真实限制。
2. **过期与 ACK 的竞态**：如 6.6 所述，`ExpireMessage` 无条件把消息写成 `EXPIRED`；在扫描与执行之间完成的业务 ACK 可能被覆盖。影响仅限已过 `expire_at` 的消息。
3. **重复投递**：实时推送、Worker 重试、PULL 三条路径可能对同一投递各发一次 `DELIVER`；平台按 At-Least-Once 设计，客户端必须按 `messageID` 幂等。
4. **`attempts` 语义**：PULL 和实时推送都会让 `attempts+1`；它不是“重试次数”，而是“推送次数”。因此频繁 PULL 的客户端会更快触发 `FAILED` 阈值（默认 5）。
5. **无 `CHECK` 约束**：状态值越界只能由 Go 常量与测试保证，数据库不会拒绝手工写入的非法值。
6. **容量观测**：本轮 1000 连接压测（60s）后，`messages` 总大小 8504 kB、`deliveries` 6848 kB，共 29425 条消息 / 29425 条投递；这是当前 schema 与索引在该数据量下的实测值，不是容量上限。
