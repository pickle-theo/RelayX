# ADR-010：Phase 3 性能工程与压测方法

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`bench/run.sh`、`bench/run.ps1`、`cmd/loadtest/main.go`、`cmd/gateway/main.go`、`Makefile`
- 关联文档：[基线报告](../baseline-report.md)、[瓶颈分析](../bottleneck-analysis.md)、[优化报告](../optimization-report.md)

## 1. 背景

Phase 1/2 的压测在 Windows 宿主机上直接运行，受 Windows 计时器精度、杀毒软件与
后台更新影响，且没有 profiling 入口。Phase 3 要回答的是「能支撑多少连接、瓶颈在哪、
优化是否真的有效」，因此需要一个**可重复、可观测、与生产形态接近**的压测环境。

## 2. 当前问题

1. 在哪个操作系统上测？跨平台结论是否可信？
2. 客户端与服务端是否同机？会不会互相抢 CPU 导致结论失真？
3. 一次压测跑多久、如何预热、如何避免幂等去重干扰？
4. 如何在不污染压测数据的前提下采集 CPU/heap/goroutine/block/mutex？
5. 容量数字如何标注边界，避免被当成绝对容量？

## 3. 候选方案

### 3.1 运行环境

- **Windows 宿主机直接压测**：最方便，但 `time.Timer` 精度、端口回收、防火墙与后台任务都不可控，跨机器不可复现。
- **Linux 容器（本决策）**：`golang:1.27` 镜像内构建并运行 gateway/loadtest，与生产 Linux 形态一致；容器资源可限制、临时端口范围可查询；宿主机只需 Docker。
- **独立 Linux 虚拟机**：隔离性最好，但本机资源有限（8 核/8GB），启动与传输成本高。

### 3.2 拓扑

- **客户端与服务端同容器**：受同一 CPU 配额约束，测到的是「进程处理能力」而非网络容量；但开销最低、最容易复现。
- **客户端与服务端分容器**：更接近真实部署，但 Docker Desktop 的 NAT 会增加抖动，且 8 核要分成两份。
- **PostgreSQL 位置**：本机 Docker 容器（`relayx-phase2-pg`），网关经 `host.docker.internal` 访问，模拟「数据库不同机」。

### 3.3 测量协议

- 固定 `-duration`、`-ramp`、`-interval`、`-payload-size`、`-timeout`，复测必须与基线完全一致。
- 压测前清空 `messages/deliveries/endpoints`（仅可靠链路），避免历史数据影响索引与扫描。
- 客户端 MsgID 以墙钟为种子，避免第二次压测被服务端幂等去重。
- 低频场景的读超时取 `max(timeout, 2*interval)+1s`，避免空闲期误判断连。

## 4. 决策

1. **环境**：Docker Desktop + `golang:1.27` Linux 容器，`--ulimit nofile=1048576`，
   `--add-host host.docker.internal:host-gateway`，Go 构建缓存挂命名卷 `relayx-phase3-gocache`。
2. **拓扑**：gateway 与 loadtest 同容器，通过 `127.0.0.1:19330` 通信；PostgreSQL 在
   宿主机 Docker（`127.0.0.1:5432`），网关 DSN 指向 `host.docker.internal`。
3. **场景矩阵**：`idle`、`heartbeat`、`steady-low`、`steady-high`、`slow-consumer`、
   `large-payload`、`reconnect-storm`，各自固定连接数/间隔/载荷/时长，写进
   `bench/run.ps1` 的默认值与 `Makefile` 的 `bench-1k` / `bench-10k` / `bench-50k`。
4. **基线口径**：每个场景跑一次，报告记录 `finished_at`、`elapsed`、参数块、环境块、
   loadtest 原文、退出码与网关 stats 尾部；不对单次结果做中位数或截尾。
5. **Profiling**：网关暴露 `-pprof-addr`；压测开始 **10s 后**再采集，CPU 采样 15s，
   随后采集 heap/goroutine/block/mutex；`-block-profile-rate=10000`、
   `-mutex-profile-fraction=100` 只在开启 pprof 时设置。
6. **优化判定**：同参数复测，核心指标改善 ≥20% 视为有效；若吞吐/错误率恶化 ≥20%
   且无其它明确收益，则回退。每轮结论写入优化报告。
7. **容量口径**：同时记录服务端 `active_conns`、goroutines、heap、以及失败原因；
   容器临时端口范围（32768–60999）作为硬边界写进报告，不外推。

## 5. 选择理由

1. **Linux 容器与生产同构**：epoll、TCP 参数、`time.Timer` 行为与生产一致，
   Phase 3 的 syscall/futex 结论才有意义。
2. **同容器压测排除网络变量**：本轮目标是「进程内瓶颈」，同机回环让 RTT 主要由
   调度与系统调用决定，profile 更容易解读；网络容量不在本轮范围。
3. **延迟采集避免空跑**：最先的实现先采集再压测，抓到的是空闲网关（9 个 goroutine）；
   改为压测后延迟 10s 采集，profile 才能反映稳态。
4. **每次复测只跑一次 + 保留原始报告**：本机噪声存在，但同参数同环境的相对变化
   足以支撑优化决策；原始文件保留，读者可自行判断。
5. **端口边界明确**：50k/100k 失败不是网关拒绝，而是客户端 `cannot assign
   requested address`；把边界写清楚，避免把 28,232 当成网关容量。

## 6. 已知限制

1. **客户端与服务端共享 CPU**：高频档的 loadtest 自身占用数核，网关可用 CPU 被压缩，
   吞吐数字偏保守。
2. **单次运行**：没有三次中位数，p99 的批次间波动可达 20%–50%。
3. **Docker Desktop NAT**：PostgreSQL 经 `host.docker.internal` 访问，单次往返延迟
   高于同机进程，可靠链路的数据库上限被放大。
4. **临时端口**：容器默认 32768–60999，最多约 28k 客户端连接；50k/100k 需要调整
   `net.ipv4.ip_local_port_range` 或多客户端，本轮未做。
5. **profile 只在单点采集**：CPU 15s 覆盖 ramp 后段到稳态前段，长时间泄漏需要重复采集。
6. **没有对照组**：Phase 2 基线就是对照组；没有在相同容器里跑「未优化」的第二个进程。

## 7. 复现命令

```powershell
# 10k 高频 echo + profiling
powershell -ExecutionPolicy Bypass -File bench\run.ps1 `
  -Conns 10000 -Duration 45s -Scenario steady-high -Interval 1s `
  -Ramp 15s -Timeout 5s -Mode echo -Profile 1 `
  -Out docs/bench/raw/opt2-10k-echo-high.txt

# 可靠链路 1000 连接 / 1 msg/s
docker exec relayx-phase2-pg psql -U relayx -d relayx `
  -c "TRUNCATE deliveries, messages, endpoints RESTART IDENTITY CASCADE"
powershell -ExecutionPolicy Bypass -File bench\run.ps1 `
  -Conns 1000 -Duration 40s -Scenario steady-low -Interval 1s `
  -Mode reliable -Ack both -Timeout 10s `
  -Out docs/bench/raw/opt1-1k-reliable.txt
```

## 8. 被否决的方案

- **Windows 直接压测**：计时器与端口行为不可复现，profile 结论不可信。
- **先采集再压测**：抓到空闲网关，已在本轮修正。
- **多容器分离客户端**：本轮目标是进程内瓶颈，网络变量会掩盖 syscall/futex 证据。
- **三次中位数**：单次成本约 2–3 分钟，Phase 3 每轮要跑 4–6 次；相对变化已足够，
  后续需要精确容量时再补。
- **调整临时端口范围突破 50k**：属于环境调参，不是网关优化；记录边界即可。
