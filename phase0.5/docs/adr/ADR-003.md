# ADR-003：池化与缓冲所有权

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`internal/transport/pool.go`、`internal/transport/conn.go`（`Send`、`readLoop`、`writeBatch`）、`internal/protocol/frame.go`（`AppendFrame`、`DecodeInto`）
- 关联决策：[ADR-002 每连接单 Writer](ADR-002.md)、[ADR-004 批量写与背压](ADR-004.md)

## 1. 背景

Phase 0 的发送与接收路径每帧都新建缓冲：`Send` 用 `bytes.Buffer` 编码后再取 `Bytes()` 入队，`Decode` 每次 `new(Frame)` 并按 BodyLen `make([]byte, n)`。在 1000 连接、每秒 1000 帧的回显负载下，每帧至少产生 2 次堆分配（编码缓冲 + 解码 Body），`BenchmarkSend64` 为 3 allocs/op、240 B/op，`BenchmarkDecode64` 为 ≈3 allocs/帧。

Phase 0.5 的目标是在不改变线格式与对外 API 语义的前提下，把这些高频短生命周期对象从 GC 压力中移走。

## 2. 当前问题

需要一套缓冲复用策略，同时满足：

1. **分配次数可测地下降**，且不引入跨连接的数据竞争。
2. **内存有界**：池不能把大帧的底层数组长期钉在内存里。
3. **所有权清晰**：缓冲在生产者、队列、写协程之间流转，任何一方在归还后都不能再读写。
4. **零第三方依赖**，只用标准库。
5. **对调用方透明**：`Encode` / `Decode` 的签名与错误语义不变，老代码不改。

## 3. 候选方案

### 方案 A：维持每帧分配（Phase 0 现状）

实现最简单、所有权天然清晰，但每帧至少 1–3 次分配；1000 连接持续发送时分配速率与 GC 次数随吞吐线性增长。

### 方案 B：全局大缓冲 + 互斥锁

所有连接共享一个固定大小缓冲，写入前加锁、写完解锁。问题：全局锁把 1000 条连接的写路径串行化，慢连接会阻塞全部连接；缓冲大小只能按最大帧配置，内存浪费且无法承载并发写入。

### 方案 C：分级 `sync.Pool`（本决策）

两组独立池：

- 编码缓冲：512 B / 4 KiB / 64 KiB 三个容量等级，`getEncodeBuf(n)` 返回能容纳 n 的最小等级；`putEncodeBuf` 只回收容量恰好等于等级尺寸的缓冲。
- `*protocol.Frame`：`getFrame` / `putFrame` 复用帧对象与 Body 数组。

`n > 64 KiB` 的请求精确 `make` 且 `putEncodeBuf` 不回收；`cap(f.Body) > 64 KiB` 的帧在 `putFrame` 时把 Body 置 nil。

### 方案 D：只调 GC（`GOGC` / `GOMEMLIMIT`）

不动代码，靠调大堆目标降低 GC 频率。问题：不减少分配总量与对象数量，只是把回收推迟；内存上限不可控，且对 `-race`、容器限额场景不友好。

| 维度 | A 每帧分配 | B 全局缓冲 + 锁 | C 分级池 | D 调 GC |
| --- | --- | --- | --- | --- |
| 分配次数 | 1–3/帧 | 0（但串行化） | ≈1 次装箱/帧 | 不变 |
| 并发性 | 好 | 差（全局锁） | 好（per-P 池） | 好 |
| 内存上界 | 由 GC 决定 | 固定但按最大帧 | 每 P 至多保留各级若干块 | 不可控 |
| 大帧处理 | 正常分配 | 浪费或截断 | >64 KiB 精确分配、不回收 | 正常分配 |
| 所有权风险 | 无 | 高（共享缓冲） | 中（需约定归还后失效） | 无 |
| 实现复杂度 | 低 | 中 | 中 | 低 |

## 4. 选择的方案

采用 **方案 C：分级 `sync.Pool`**，实现于 `internal/transport/pool.go`。协议层配合新增 `AppendFrame(dst, f, maxBody)` 与 `DecodeInto(r, f, maxBody)`，让池化缓冲可以直接作为目标切片传入；`Encode` / `Decode` 保留原签名，内部改为 `AppendFrame(nil, ...)` / `DecodeInto(&Frame{})`，因此线格式与调用方式都不变。

## 5. 选择理由

1. **容量等级贴合实际帧分布**。64 B Body 的帧总长 85 B，落在 512 B 级；1 KiB Body 的帧 1045 B，落在 4 KiB 级；默认 `max-body` 1 MiB 下的大帧则精确分配。池化只覆盖高频小帧，不为极端大帧保留空间。
2. **`sync.Pool` 天然并发安全且 per-P**，不需要额外锁；GC 会在每个周期清空池，避免长期驻留。
3. **大缓冲不回收是刻意的内存上界**。`maxPooledBuffer = 64 KiB` 之上的缓冲若进入池，可能让某个连接的一次大帧把几十 MB 钉在池里；精确分配交给 GC 回收更稳妥。
4. **`putFrame` 清零关键字段**：`Type`、`Flags`、`MsgID` 置 0，`Body` 截断为 0 长度；Body 容量超过 64 KiB 时置 nil。这样下一轮 `DecodeInto` 只会复用容量合适的 Body，不会误读上一帧的元数据。
5. **所有权规则可以写成契约并测试**：

   | 对象 | 获取 | 归还 | 归还后 |
   | --- | --- | --- | --- |
   | 编码缓冲 | `getEncodeBuf(n)` | `putEncodeBuf`（`Send` 成功后由 writeLoop 复制完即归还） | 任何协程都可能复用，不得再读写 |
   | `Frame` | `getFrame()` | `putFrame`（handler 返回后） | `f` 与 `f.Body` 均失效，需要保留必须拷贝 |

   具体到调用链：`Send` 成功入队后缓冲归 writeLoop；`writeBatch` 把帧复制进批次缓冲后立即 `putEncodeBuf`；`readLoop` 在 `handler` 返回或 `Send(PONG)` 返回后才 `putFrame`。`TestEncodeBufReuse`、`TestOversizedEncodeBufNotRecycled`、`TestPutFrameResetsFields`、`TestPutFrameDropsOversizedBody`、`TestDecodeIntoReusesBody` 覆盖了这些约定。
6. **实测收益**：`BenchmarkSend64ReuseFrame`（模拟真实归还）130.5 ns/op、24 B/op、1 alloc/op，相比 Phase 0 `Send64` 的 191.4 ns/op、240 B/op、3 allocs/op，耗时 −31.8%、字节 −90%、分配次数 −66.7%。

## 6. 优点和缺点

优点：

- 高频小帧不再触发分配；`Frame` 的 Body 数组在稳态下复用，解码路径的 3 allocs/帧只在 `Decode`（非 `DecodeInto`）基准中出现。
- 池化局部于 `transport` 包，协议层只暴露"向 dst 追加"的通用 API，不依赖 `sync.Pool`，未来可替换为 ring buffer 或 slab。
- 内存有明确上界（单缓冲 64 KiB 级），不会因个别大帧污染全局。
- 所有权规则集中在一个文件的注释中，配套测试可在 `-race` 下验证。

缺点（具体到本项目）：

- **仍剩 1 alloc/op**：`sync.Pool.Put` 把 `[]byte` 装箱成 `interface{}` 会产生固定 24 B 分配，标准库无法避免；若追求 0 alloc，需要使用 `unsafe` 或自定义无接口池，超出"只用标准库、保持可读"的边界。
- **池会保留部分内存**：`sync.Pool` 的 per-P 私有槽与共享链在每个 GC 周期才清空，突发大流量后 RSS 不会立刻下降；`heap_alloc` 峰值因此只从 28.26 MB 降到 26.79 MB（见[压测报告](../压测报告.md)）。
- **所有权违约不会立刻报错**：handler 若在返回后继续读 `f.Body`，读到的是被复用的内存，表现为难以定位的数据错乱；只能靠文档与 code review 约束。
- **调试成本**：池化后 pprof 的分配点更少，但也更难通过分配热点定位逻辑问题。

## 7. 被否决的方案

- **全局大缓冲 + 锁**：串行化写路径，慢连接阻塞全部连接，且在 1000 连接压测下必然出现长尾。
- **只调 `GOGC` / `GOMEMLIMIT`**：不减少对象数量，内存上界不可控，属于把问题推给运行时。
- **`net.Buffers` / `writev` 风格的缓冲复用**：Windows 上 `net.Buffers` 退化为顺序 `Write`，无法获得 syscall 合并收益，且要求缓冲在写完成前保持存活，与池的"归还即失效"冲突（见 [ADR-004](ADR-004.md)）。

## 8. 后续演进方向

1. 用 pprof `alloc_space` 确认装箱分配（24 B/次）在总分配中的占比，评估是否值得引入泛型/无接口对象池。
2. 观察长时间运行后的 RSS 与 `heap_sys`，必要时在空闲时主动清空池或为池设置容量上限。
3. 若未来引入 ring buffer 收发，可把"编码缓冲"升级为按连接持有的固定环形缓冲，进一步消除池的 per-P 抖动。
4. 为 handler 提供显式的 `CopyBody` 辅助或在 `HandlerFunc` 文档中固化所有权契约，降低误用风险。
