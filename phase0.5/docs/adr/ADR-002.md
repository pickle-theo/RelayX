# ADR-002：为什么每连接单 Writer（有界队列）

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`internal/transport/conn.go`（`Send`、`writeLoop`、`drainData`、`writeBatch`、`Close`）、`internal/transport/server.go`（`Shutdown` 广播 CLOSE）、`internal/transport/pool.go`
- 关联决策：[ADR-001 标准库 net](ADR-001.md)、[ADR-003 池化与缓冲所有权](ADR-003.md)、[ADR-004 批量写与背压](ADR-004.md)

## 1. 背景

TCP 是字节流，没有消息边界；协议帧必须整帧写入，否则对端按 21 字节头 + BodyLen 解码时会错位。Phase 0.5 的一条连接上存在多个帧生产方：

- `readLoop`：收到 PING 后立即回 PONG，收到 DATA 后调用业务 handler。
- 业务 handler（`cmd/gateway` 的 `echoHandler`）：回显 DATA。
- `writeLoop`：内置的 `time.Timer` 到点后发送 PING（Phase 0.5 已把心跳并入写协程）。
- `Server.Shutdown`：向所有连接发送 CLOSE 帧。

这些生产方可能并发触发。当前实现是：`Conn.Send` 用 `getEncodeBuf` 取一个池化缓冲，再用 `protocol.AppendFrame` 把整帧编码进去，然后按帧类型非阻塞投递到 `sendCh`（DATA/ERROR）或容量固定为 16 的 `ctrlCh`（PING/PONG/CLOSE）；`writeLoop` 是唯一调用 `nc.Write` 的协程，数据帧会被贪心聚合成批后一次写出，写失败、写超时或刚发出 CLOSE 帧后退出。

## 2. 当前问题

需要一个写路径策略，同时满足：

1. **帧完整性**：并发写入的帧不能交错、不能被拆成互相穿插的片段。
2. **生产者不被慢网络拖死**：读循环、心跳、关闭流程不能因为某个客户端不读数据而长期阻塞。读循环一旦阻塞，就无法继续读入站帧，空闲/心跳超时判定也会失真。
3. **内存有界**：慢消费者不能让待发帧无限堆积。
4. **关闭可控**：`Close` 可被多协程重复调用而不 panic；优雅关闭时 CLOSE 帧有机会在 socket 关闭前刷出。
5. **可观测**：队列深度、队列满、写失败、写超时应能通过日志和错误值区分。

## 3. 候选方案

### 方案 A：直接并发写 socket

各生产方自行 `protocol.Encode(nc, frame, maxBody)`。`net.Conn` 文档允许多协程并发调用方法，TCP 连接内部会对写加锁，且当前 `Encode` 是单次 `Write`，因此字节通常不会交错。

问题：

- 帧的**顺序**不可控：PING/PONG/DATA/CLOSE 的先后取决于调度，CLOSE 可能先于排队的数据写出。
- 慢客户端会**直接阻塞调用方**：`readLoop` 卡在 `Write` 上就无法继续读，心跳也会卡住，形成「写等对端读、读等本地写」的相互拖累。
- 没有队列就没有背压边界；若为避免阻塞而给每次写开 goroutine，内存与协程数会失控。
- 关闭时无法保证已编码但未写出的 CLOSE 帧被刷出，也无法统计队列压力。

### 方案 B：全局写锁 / 每连接写锁

用 `sync.Mutex` 包住「编码 + 写 socket」。若用全局锁，所有连接的写串行化，一个慢客户端会阻塞全部连接，1000 连接压测必然出现长尾。若用每连接锁，爆炸半径缩小到单连接，但：

- 生产方仍然**阻塞在网络 I/O 上**，读循环和心跳依旧会被慢客户端拖住。
- 锁内不能安全地做长时间阻塞操作，关闭与写竞争时容易形成「持锁写、Close 等待」的停顿。
- 没有队列深度、没有明确的队列满策略，内存与延迟都不可控。

### 方案 C：每连接单 Writer + 有界队列（当前实现）

- `Send`：池化缓冲 + `AppendFrame` 编码 → 非阻塞 `select` 投递；控制帧走 `ctrlCh`，数据帧走 `sendCh`。队列满（帧数）或超出 `send-queue-bytes` 预算时，回滚计数、归还缓冲，告警并以 `send queue full` 关闭连接，返回 `ErrSendQueueFull`；连接已关闭返回 `ErrConnClosed`。
- `writeLoop`：先非阻塞检查 `ctrlCh`，再 `select { <-done; <-ctrlCh; <-sendCh; <-hbC }`；数据帧经 `drainData` 聚合后由 `writeBatch` 单次写出；唯一执行 `nc.Write`；写前设置 `SetWriteDeadline`。
- `Close`：`sync.Once` 保证幂等，`close(done)` 通知写协程退出，`nc.Close()` 唤醒阻塞 I/O，`onClose` 注销连接。`sendCh` / `ctrlCh` 故意不关闭，避免向已关闭 channel 发送导致 panic。

| 维度 | A 直接并发写 | B 写锁 | C 单 Writer + 有界队列 |
| --- | --- | --- | --- |
| 帧字节完整性 | 依赖单次 Write + 连接内部锁 | 依赖锁 | 由唯一写者保证，与 Encode 实现无关 |
| 帧顺序 | 不可控 | 抢锁顺序 | 数据帧 FIFO；控制帧优先于数据 |
| 慢客户端影响 | 阻塞读循环/心跳 | 阻塞持锁者；全局锁影响全部连接 | 生产者不阻塞，队列堆积至上限后关闭；写超时兜底 |
| 内存上界 | 无 | 无 | 每连接 `min(send-queue-size × 帧长, send-queue-bytes)` |
| 背压策略 | 无 | 无 | 明确：帧数或字节预算超限即关闭，返回 `ErrSendQueueFull` |
| 关闭语义 | 易与并发写竞争 | 需处理持锁阻塞 | `done` 通知 + `nc.Close()` 唤醒，逻辑集中 |
| 额外成本 | 无 | 无 | 每连接 +1 协程、每帧一次入队、批内一次拷贝 |

## 4. 选择的方案

采用 **方案 C：每连接单 Writer + 有界发送队列**，实现位置 `internal/transport/conn.go`。默认队列容量 256 帧、字节预算 4 MiB，由服务端 `-send-queue-size` / `-send-queue-bytes` 配置；控制帧队列固定 16。服务端与客户端的所有 socket 写都由各自唯一的写路径完成（客户端演示程序由主 goroutine 串行写，PONG 通过 channel 交回主 goroutine）。

## 5. 选择理由

1. **正确性由结构保证**。只有一个协程调用 `nc.Write`，帧不会交错；即使编码改为批量拼接，这一保证仍然成立。相比依赖「`net.Conn` 内部锁 + 单次 Write」的隐式前提，单写者是显式约束，更容易审查与测试。
2. **生产者与网络解耦**。`Send` 不做阻塞 I/O，`readLoop` 能持续读入站帧、刷新 `lastInbound`；心跳定时器在写协程内按时触发；慢客户端的影响被限制在该连接自己的队列里，不会传染给其他连接。
3. **背压策略明确且可测**。除 256 帧上限外，`queuedBytes` 按线格式字节统计 `sendCh` + `ctrlCh` 中尚未写出的数据，超过 `send-queue-bytes` 立即回滚并关闭。`TestSendQueueByteBudget` 用阻塞型 `net.Conn` 验证了「预算不超、返回 `ErrSendQueueFull`、连接关闭、原因为 `send queue full`」；`TestSendQueueFullBackpressure` 覆盖帧数上限。
4. **生命周期简单**。`Close` 通过 `sync.Once` + `done` 与写协程汇合，`run()` 在 `readLoop` 返回后 `Close` 并 `wg.Wait()`；发送 CLOSE 帧的路径只需入队，写协程识别帧类型后自行退出，无需在关闭流程里做额外同步。
5. **批量写与控制帧优先已在此结构上落地**。所有待发帧以完整 `[]byte` 集中在一个队列中，写协程可以一次取出多帧合并写出；控制帧独立队列使其不被数据积压饿死（详见 [ADR-004](ADR-004.md)）。

## 6. 优点和缺点

优点：

- 写串行化，帧完整性与顺序性可控；控制帧优先于数据帧，心跳与 CLOSE 的时效性有保证。
- 生产方永不因网络阻塞；队列满快速失败，错误值可分类（`ErrConnClosed` / `ErrSendQueueFull`）。
- 每连接内存上界明确（帧数与字节双约束），便于容量规划；队列满有告警日志，可观测。
- 关闭路径集中且幂等，避免重复 `close` channel 或重复关闭 socket 的 panic。
- 为缓冲池、批量写、写 Deadline 提供了天然挂载点。

缺点（具体到本项目）：

- **每连接仍有一个写协程**，加上读协程共 2 个；1000 连接即 2004 个服务端协程（压测报告实测），连接数继续上升时协程与栈内存成本线性增长。
- **发送路径仍有分配与拷贝**：池化后仍剩 `sync.Pool.Put` 的 24 B 装箱分配；批量写需要把每帧复制进批次缓冲，大帧场景比 `writev` 多一次 memcpy。
- **数据帧之间存在队头阻塞**：同一 FIFO 中前面的大帧或慢写会推迟后面的数据帧；控制帧已通过 `ctrlCh` 缓解，但数据帧本身没有优先级。
- **队列满即关闭，没有优雅降级**：不做「丢弃最旧帧」或「先排空再关」；`close(done)` 后仍在队列中的帧会被丢弃，适合 Phase 0.5 的回显语义，但不适合未来的可靠消息。
- **写 Deadline 以批为单位**：`write-timeout` 能兜住慢对端（Phase 0 完全没有），但整批共享一个 Deadline，无法定位具体卡住的帧。
- **字节预算按线格式计**：包含 21 B 帧头，小帧的实际可用帧数低于直觉估算，容量规划需按线格式计算。

## 7. 后续演进方向

按规划文档 Phase 3：

1. **批量写的进一步评估**：当前已在单连接内做贪心聚合；下一步可在 Linux 上比较 `net.Buffers` / `writev` 与拼接写的 syscall 与拷贝成本（见 [ADR-004](ADR-004.md)）。
2. **缓冲池与减少拷贝**：已用 `sync.Pool` 复用编码缓冲；下一步评估每连接固定批次缓冲或 ring buffer，消除每批的池 Get/Put 与装箱分配。
3. **队列调优**：已增加字节预算与控制帧优先队列；下一步引入高低水位与按控制/数据分账的预算，并让批大小随队列水位自适应。
4. **慢消费者策略**：在可靠消息阶段（Phase 2）改为可配置策略——断开、丢弃最旧、或按会话上限限流，而不是一律关闭。
5. **可观测性**：暴露每连接队列深度、入队/出队速率、队列满次数、写阻塞时长、批大小分布，结合 Profiling 判断队列大小与批量阈值。
6. **实现评估**：比较 channel 与环形缓冲（ring buffer）的入队/出队开销；若写协程调度成为瓶颈，再评估由事件循环统一驱动写路径，但需保持「单连接单写者」这一正确性约束。
