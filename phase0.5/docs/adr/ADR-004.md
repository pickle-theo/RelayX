# ADR-004：批量写与背压

- 状态：Accepted
- 日期：2026-11-10
- 决策者：项目作者
- 相关代码：`internal/transport/conn.go`（`Send`、`writeLoop`、`drainData`、`writeBatch`）、`internal/config/config.go`（`send-queue-bytes`、`write-timeout`、`write-batch-frames`、`write-batch-bytes`）
- 关联决策：[ADR-002 每连接单 Writer](ADR-002.md)、[ADR-003 池化与缓冲所有权](ADR-003.md)

## 1. 背景

Phase 0 的写协程每出队一帧就调用一次 `nc.Write`，即 1 次系统调用/帧。1000 连接、每秒 1000 帧的回显负载意味着服务端每秒约 2000 次写系统调用，帧长只有 85 B 左右，系统调用开销远超有效载荷。同时 Phase 0 的背压只按帧数（`send-queue-size`，默认 256）计量，64 B 小帧与 1 MiB 大帧的内存上界相差 4 个数量级；控制帧与数据帧共用一个 FIFO，数据积压会推迟 PING/PONG 与 CLOSE。

## 2. 当前问题

需要同时满足：

1. 降低每次发送的固定开销（系统调用次数）。
2. 控制帧（心跳应答、关闭通知）不能被数据流量饿死。
3. 内存上界可估：既要限制帧数，也要限制字节数。
4. 慢对端不能永久占住写协程。
5. `Send` 不能被网络阻塞，否则 readLoop 停止读入站帧，空闲/心跳超时判定失真。

## 3. 候选方案

### 方案 A：保持 1 帧 1 次 `Write`

实现最简单，但系统调用次数与帧数相等；小帧场景固定开销占比极高。

### 方案 B：`net.Buffers` / `writev`

在 Unix 上把多个切片合并为一次 `writev`，无需拼接拷贝。问题：Windows 上标准库的 `net.Buffers` 退化为顺序 `Write`，本项目的主要开发与压测环境是 Windows，拿不到收益；且 `net.Buffers` 要求切片在写完成前保持有效，与池化缓冲"复制后立即归还"的所有权模型不兼容。

### 方案 C：写协程内贪心聚合 + 拼接后单次 `Write`（本决策）

- 数据帧：从 `sendCh` 取到第一帧后，`drainData` 继续非阻塞地取，直到达到 `write-batch-frames`（默认 16）或 `write-batch-bytes`（默认 64 KiB）目标；`writeBatch` 把所有帧复制进一个池化缓冲，单次 `nc.Write`。
- 控制帧：独立的 `ctrlCh`（容量 16），writeLoop 每轮先做一次非阻塞优先检查，再在 `select` 中把 `ctrlCh` 排在数据通道之前。
- 背压：`send-queue-bytes`（默认 4 MiB）按**线格式字节数**统计 `sendCh` + `ctrlCh` 中的待发数据，与 `send-queue-size` 的帧数上限共同生效。
- 写超时：每次 `Write` 前 `SetWriteDeadline(now+write-timeout)`，写完清除；超时以 `write timeout` 关闭连接。

### 方案 D：无界队列 / 阻塞式 `Send`

- 无界队列：慢消费者会让内存无限增长，与"内存有界"直接冲突。
- 阻塞式 `Send`：调用方（readLoop）停在入队上就无法继续读，心跳超时与空闲超时失效，且 `Server.Shutdown` 广播 CLOSE 时可能互相等待。

| 维度 | A 1 帧 1 写 | B `net.Buffers` | C 聚合 + 单次写 | D 无界/阻塞 |
| --- | --- | --- | --- | --- |
| syscall 次数 | = 帧数 | Unix 1 次/批；Windows = 帧数 | 1 次/批 | 取决于实现 |
| 是否需要拼接拷贝 | 否 | 否（Unix） | 是（一次 memcpy） | — |
| 控制帧时延 | 与数据同队，可能被推迟 | 同左 | ctrlCh 严格优先 | 不可控 |
| 内存上界 | 帧数上限 | 帧数上限 | 帧数 + 字节双上限 | 无 |
| 慢对端 | 写协程永久阻塞 | 同左 | 写 Deadline 超时关闭 | 恶化 |
| 生产者阻塞 | 否（Phase 0 非阻塞入队） | 否 | 否 | 是/内存爆炸 |
| 平台一致性 | 好 | Windows 无收益 | 好 | — |

## 4. 选择的方案

采用 **方案 C**，实现位置 `internal/transport/conn.go`。默认参数：`write-batch-frames=16`、`write-batch-bytes=64 KiB`、`send-queue-bytes=4 MiB`、`write-timeout=10s`、`ctrlCh` 容量固定 16。

## 5. 选择理由

1. **收益直接可测**：`TestWriteCallsBatched` 预入队 10 个数据帧，写协程只调用 1 次 `Write`，并把捕获字节流重新解码、逐帧校验 Type/MsgID/Body。Phase 0 同场景是 10 次。
2. **批大小上限是延迟与内存的折中**：16 帧与 `sendCh` 的默认容量（256）相比只占很小一段，单批最多引入"聚合当前已排队帧"的拷贝时间，不会为了等满一批而 sleep；64 KiB 与 64 KiB 缓冲池等级对齐，避免批次缓冲频繁跨级，也大致相当于多个 TCP 段，减少巨帧造成的队头阻塞。
3. **ctrlCh 优先是正确性要求**：心跳应答若排在 200 多个数据帧之后，PING 的 RTT 会被数据积压放大；`Server.Shutdown` 的 CLOSE 若被数据阻塞，优雅退出可能直接超时。固定容量 16 足够容纳"一个心跳周期内的 PING/PONG/CLOSE"，同时防止控制通道本身被滥用。
4. **双预算覆盖帧大小差异**：只按帧数计，1 MiB 帧 × 256 = 256 MiB/连接；只按字节计，则零长帧可以无限堆积。两者同时生效后，连接内存上界约为 `min(队列帧数 × 单帧, send-queue-bytes)`。`queuedBytes` 在入队前 `Add`，超限立即回滚，写协程把帧复制进批次后 `Add(-len)`，因此预算统计的是"尚未发出"的字节。
5. **写 Deadline 是慢对端的唯一出口**：Phase 0 的 `writeLoop` 没有写 Deadline，对端不读时只能等 90s 心跳超时或 120s 空闲超时触发 `Close`；现在 10s 内未完成写即关闭，日志原因可区分（`write timeout`）。单测 `TestWriteTimeout` 用阻塞型 `net.Conn` 验证了原因与退出路径。
6. **超限关闭而不是阻塞调用**：`Send` 必须保持非阻塞，否则 readLoop 无法继续读、PONG 无法及时发出、关闭流程可能死锁。队列满/字节超预算时回滚计数、归还缓冲、以 `send queue full` 关闭连接并返回 `ErrSendQueueFull`，把"慢消费者"变成一次可观测的快速失败。代价是突发流量可能直接断开连接，而不是短暂排队。

## 6. 优点和缺点

优点：

- 小帧场景系统调用次数按批下降（实测 10 → 1），尾延迟受 syscall 抖动影响更小。
- 控制帧不再被数据队头阻塞，心跳/关闭的时效性与数据量解耦。
- 内存上界由帧数与字节数共同约束，容量规划可计算。
- 写失败、写超时、队列满都有独立的关闭原因与错误值，便于日志检索与测试。
- 实现只用标准库，Windows/Linux 行为一致，不依赖 `writev`。

缺点（具体到本项目）：

- **多一次拷贝**：批次缓冲需要把每帧复制一次；对 64 B 小帧可忽略，对 1 MiB 大帧是额外带宽。未采用 `writev` 是因为 Windows 无收益且与池化所有权冲突。
- **批内共享一个写 Deadline**：超时以整批为单位，无法定位具体是哪一帧卡住；批内某帧写出缓慢会连带整批失败。
- **聚合不等待**：`drainData` 只取"已经排队"的帧，低负载时批大小接近 1，收益随负载升高才显现；这保证了延迟，但也意味着低 QPS 下 syscall 不会减少。
- **队列满即断开**：没有"丢弃最旧帧"或"降级为阻塞"的策略；对回显语义可接受，对未来的可靠消息需要重新设计（Phase 2）。
- **控制通道容量固定 16**：若业务代码大量发送 PING/PONG（当前只有心跳与应答），控制通道也可能被填满并触发 `send queue full`；目前由协议使用方式保证不会发生。
- **字节预算按线格式计**：包含 21 B 帧头，因此小帧的实际帧数上限低于 `send-queue-bytes/帧长` 的直觉估算，需要在容量规划时按线格式计算。

## 7. 被否决的方案

- **`net.Buffers` / `writev`**：Windows 上退化为多次 `Write`，无法达成"减少 syscall"的目标；且要求缓冲在写完成前保持存活，破坏池化缓冲"复制后立即归还"的所有权约定。
- **无界发送队列**：慢消费者会让单连接内存无上限增长，直接违背背压目标。
- **阻塞式 `Send`**：会让 readLoop 停止读入站帧，空闲/心跳超时失真；`Shutdown` 广播 CLOSE 时存在互相等待风险。
- **每帧一个写协程**：协程数随帧速率增长，调度与栈内存不可控。
- **只按帧数或只按字节计量**：前者在大小帧混合时内存上界失真，后者无法限制零长帧数量。

## 8. 后续演进方向

1. 在 Linux 上评估 `writev`（`net.Buffers`）与拼接写的 A/B 对比，用 syscall 计数与 pprof 验证收益；若采用，需要为"写完成后再归还"设计引用计数或每连接批次缓冲。
2. 把 `drainData` 的目标改为"按当前队列水位自适应"：低水位小批、高水位大批，减少低负载下无意义的拼接。
3. 为队列满引入可配置策略（断开 / 丢弃最旧 / 短暂阻塞），供 Phase 2 的可靠投递选择。
4. 暴露每连接队列字节水位、批大小分布、写超时次数等指标，替代当前仅靠日志的观测方式。
5. 评估把数据帧与控制帧的预算分开统计，避免业务突发挤占心跳配额。
