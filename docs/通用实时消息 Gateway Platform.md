# 通用实时消息 Gateway Platform
# 项目建设与技术成长计划书

**项目名称：** Real-time Messaging Gateway Platform  
**项目定位：** 个人技术成长型工程项目  
**主要技术栈：** Go、TCP、WebSocket、PostgreSQL、Redis、Kafka  
**建设方式：** 渐进式开发、持续验证、按需演进  
**最终目标：** 构建具备千万级扩展能力的通用实时消息 Gateway Platform

---

# 一、项目背景与建设动机

## 1.1 项目背景

本项目并非源于某个具体商业业务需求，而是希望通过建设一个完整的实时消息 Gateway Platform，系统性地学习和掌握后端基础设施开发所涉及的核心技术。

相比于单独学习网络编程、数据库、缓存、消息队列和分布式系统，通过一个完整项目将这些技术串联起来，更容易理解各个技术组件的作用、相互关系以及实际应用场景。

实时消息 Gateway Platform 涉及的技术领域比较全面，既包含底层网络编程，也包含复杂的并发控制、消息可靠性、分布式协调和大规模系统设计，适合作为长期技术实践项目。

# 二、项目定位与建设目标

## 2.1 项目定位

建设一个业务无关、可扩展、具备可靠消息投递能力的通用实时消息 Gateway Platform。

平台只负责消息接入、连接管理、消息路由和可靠投递，不负责任何具体业务逻辑。

业务系统通过标准 API 接入平台，客户端通过统一协议连接 Gateway。

平台不关心消息 Payload 的具体含义，只负责按照约定将消息可靠地送达目标 Endpoint。

## 2.2 项目边界

### 项目建设范围

1. TCP/WebSocket 长连接服务。
2. 统一通信协议。
3. 客户端身份认证。
4. Connection 和 Session 管理。
5. 消息路由。
6. 多设备消息投递。
7. 离线消息持久化。
8. Receipt ACK。
9. Business ACK。
10. 消息重试与 TTL。
11. 多 Gateway 节点管理。
12. 分布式消息投递。
13. 高并发连接管理。
14. 消息可靠性和故障恢复。

### 非项目建设范围

1. 用户注册和用户管理。
2. 好友关系。
3. IM 会话管理。
4. 群组管理。
5. 业务消息解析。
6. 业务消息处理。
7. 业务权限系统。
8. 业务数据存储。

## 2.3 核心产品原则

| 维度 | 设计原则 |
|---|---|
| Identity | 业务方定义身份 |
| Endpoint | 一个业务身份支持多个设备 |
| Payload | 业务自定义，平台不解析 |
| Delivery | At-Least-Once |
| ACK | Receipt ACK + Business ACK |
| Offline | 支持离线消息持久化 |
| TTL | 消息具有有效期 |
| Tenant | 支持多租户隔离 |
| Architecture | 渐进式架构演进 |

## 2.4 最终建设目标

最终形成一个能够支持以下场景的通用实时消息平台：

- 海量客户端长连接。
- 多 Gateway 节点部署。
- 跨 Gateway 消息路由。
- 大规模消息 Fan-out。
- 可靠消息持久化。
- 多设备独立投递。
- 消息 ACK 和重试。
- 大规模离线消息恢复。
- 分布式任务调度。
- 水平扩展和故障恢复。

需要注意：千万级规模是最终架构能力目标，而不是第一阶段的性能承诺。最终容量以实际硬件、网络、存储和压测结果为准。

# 三、总体建设原则

## 3.1 最小架构起步

第一阶段只建设单进程、单节点系统。

不提前引入 Redis、Kafka、分布式数据库、微服务和 Kubernetes。

先通过最简单的架构验证核心模型和功能正确性。

## 3.2 模块化优先于微服务化

初期采用模块化单体架构。

模块之间通过清晰的接口交互，但仍然部署在同一个进程中。

当出现明确的性能、资源隔离或独立扩缩容需求时，再考虑拆分服务。

## 3.3 先功能正确，再可靠性，最后性能

建设顺序：

1. 网络连接和消息通信。
2. Session 和消息路由。
3. 消息持久化。
4. ACK 和重试。
5. 故障恢复。
6. 高并发优化。
7. 分布式扩展。

## 3.4 通过实际问题驱动架构演进

不为了使用某项技术而引入该技术。

每次架构演进都必须回答：

- 当前架构遇到了什么问题？
- 通过什么指标发现问题？
- 为什么现有架构无法解决？
- 新架构引入了什么机制？
- 新架构解决了什么问题？
- 新架构带来了什么额外复杂性？

## 3.5 每个阶段必须有可验证的交付成果

每个阶段都需要包含：

- 功能实现。
- 核心测试。
- 故障测试。
- 性能测试。
- 技术总结。
- 架构决策记录。

# Phase 0.5：Phase 0 极致优化（标准库内）

## 5.6 阶段目标

在不更换 Go 标准库 net 架构的前提下，用可重复的 Benchmark 与 Profiling 找出 Phase 0 的真实开销，把内存分配、系统调用、定时器与协程模型优化到该架构的合理上限，为 Phase 1 提供高性能传输层基线。

本阶段是 Phase 0 的独立子项目（`phase0.5/`），不覆盖、不修改 Phase 0 代码；后续 Phase 3 的性能对比以 Phase 0 与 Phase 0.5 的数据为参照。

## 5.7 实施内容

先建立基线，再按数据优化，禁止未测量就替换组件。

### 基准与观测

- 为 Encode、Decode、Send 与写循环建立 Benchmark（含 `-benchmem`）。
- 接入 CPU、Memory、Block、Mutex、Goroutine Profiling。
- 记录每个优化项前后的 ns/op、B/op、allocs/op、系统调用次数、RSS 与 P99。

### 内存池化

- 编码 buffer 与解码 Body 分级池化，明确 buffer 所有权与归还时机。
- Frame 对象池；限制池中单个 buffer 的保留上限，避免大帧推高常驻内存。
- 评估 `bufio.Reader/Writer` 大小与连接数带来的内存放大，按场景可配置。
- 只对 Profiling 证明的热点池化，池化后 `allocs/op` 必须下降。

### 写路径

- 批量写：Writer 一次取出多条帧合并写出，减少系统调用。
- 有界队列改为「帧数 + 字节预算」双上限，避免大帧造成内存放大。
- 控制帧（PING/PONG/CLOSE）优先，避免排在数据帧之后。
- 增加写 Deadline，防止对端不读导致 Writer 永久阻塞。

### 读路径

- 读 Deadline 从每帧刷新改为粗粒度空闲扫描，降低 timer 开销。
- 合并每帧的多次时间读取，减少每帧临时对象。
- 调整读缓冲区大小，并用压测验证系统调用与内存的取舍。

### 协议与并发

- 编码避免 `bytes.Buffer` 与接口调用，减少 Body 拷贝（header/body 直接写出）。
- 心跳循环并入 Writer 或改用全局时间轮，降低协程与 timer 数量。
- 仅在 Profiling 显示锁或 channel 竞争时，再评估分片注册表或替代队列。

### 系统参数

- TCP Keepalive、监听 backlog、Socket 缓冲区按实测调整。
- 基准测试在 Linux 容器中执行，避免 Windows IOCP 与 Linux epoll 数据混用。

## 5.8 明确不做

- 不引入 gnet、netpoll 或自研事件循环。
- 不做 CPU 绑核、多 Reactor、GC 参数硬调。
- 不引入 Redis、Kafka、数据库。
- 服务端不做「连接池」（长连接本身即复用）；连接池只属于客户端与后续 RPC 场景。

以上留给 Phase 3 在 Profiling 数据支持下评估。

## 5.9 验收标准

- 存在可重复执行的 Benchmark 与 Profiling 流程。
- 找到至少三个由数据证明的真实瓶颈。
- 至少两轮优化有优化前后对比数据。
- 优化后每消息的内存分配与系统调用数量有量化下降。
- 空闲连接的内存占用与协程数量达到设定目标。
- `go test -race ./...` 通过，协程泄漏检查维持基线偏差不超过 5。
- Phase 0 的功能与协议兼容性不被破坏。

## 5.10 阶段成果

形成优化后的 Phase 0.5 独立子项目、Benchmark/Profiling 报告与相应 ADR，作为 Phase 1 的传输层基线。

# Phase 1：单机实时消息 Gateway

+--------------------+

+--------------------+
          |
          v
+--------------------+
| Connection Manager |
+--------------------+
          |
          v
+--------------------+
|   Session Manager  |
+--------------------+
          |
          v
+--------------------+
|    Message Router  |
+--------------------+
          |
          v

- Session 与 Connection 映射。
- 重复登录处理。
- 断线清理。

### Message Routing

- 单播消息。
- 指定 Endpoint 投递。
- 同用户多设备投递。
- 消息广播的基础实现。
- 路由失败处理。

### Protocol

- 消息类型。
- 消息 ID。
- Payload。

## 6.4 暂不实现

- Redis。
- Kafka。
- 离线消息。
- 分布式 Gateway。
- 分布式任务调度。

## 6.5 验收标准

- 多客户端可以稳定连接。
- 可以通过身份找到对应 Session。

完成一个功能完整、结构清晰的单机实时消息 Gateway。

- 每个 Endpoint 独立的投递状态。
- ACK 的状态转换规则。

- 消息过期和取消规则。

## 7.5 故障测试

- 消息保存后进程崩溃。
- Gateway 推送成功但 ACK 丢失。
- ACK 重复提交。
- 客户端离线。
- Worker 执行过程中崩溃。
- 消息 TTL 到期。
- 数据库暂时不可用。

## 7.6 验收标准

- 消息接受后能够持久化恢复。
- 支持多设备独立投递。
- 支持两级 ACK。
- 重复请求不会产生重复逻辑消息。
- ACK 重复提交不会破坏状态。
- 离线客户端重新连接后可以恢复消息。
- 过期消息不会继续重试。

## 7.7 阶段成果

完成一个单机部署、具备完整可靠投递能力的消息系统。

# Phase 3：单机高并发与性能优化

- 发送队列优化。
- 网络 I/O 优化。

## 8.3 压测计划

逐步测试：

- 1,000 个并发连接。
- 10,000 个并发连接。
- 50,000 个并发连接。
- 100,000 个并发连接。

每个连接规模分别测试：

- 空闲连接。
- 心跳。
- 低频消息。
- 高频消息。
- 慢消费者。
- 大 Payload。
- 集中断线和重连。

## 8.4 技术对比

使用标准库 net 建立基准版本。

再根据 Profiling 结果，评估：

- gnet。
- netpoll。
- 更高效的协议编码。
- Buffer Pool。
- 批量写入。

不预设某项技术一定更好。

## 8.5 验收标准

- 建立可重复的压测环境。
- 能够分析 CPU、内存、GC 和锁竞争。
- 找到至少三个真实性能瓶颈。
- 完成至少两轮有数据对比的性能优化。
- 优化前后有可量化的结果。

## 8.6 阶段成果

完成单机 Gateway 性能基准和优化报告。

# Phase 4：分布式 Gateway

## 9.1 阶段目标

从单机架构进入多节点架构，理解分布式路由、服务发现和节点故障恢复。

## 9.2 架构变化

```text
                Business
                    |
                    v
                Access API
                    |
                    v
              Gateway Router
                    |
             +------+------+
             |      |      |
             v      v      v
            GW1    GW2    GW3
             |      |      |
             v      v      v
          Clients Clients Clients
                    |
                    v
                  Redis
```

## 9.3 实施内容

- 多 Gateway 实例。
- Gateway 节点注册。
- Gateway 心跳。
- Redis 在线路由。
- Endpoint 与 Gateway 映射。
- Connection Version。
- 跨节点消息投递。
- Gateway 故障检测。
- 路由过期。
- 客户端重连。
- 路由恢复。

## 9.4 核心技术问题

- 如何确定客户端连接在哪个 Gateway？
- 如何在节点间发送消息？
- 如何处理 Gateway 异常退出？
- 如何避免旧连接清理新连接？
- Redis 路由信息如何更新？
- 如何避免路由短暂不一致导致消息丢失？

## 9.5 验收标准

- 多个 Gateway 可以同时工作。
- 客户端可以连接任意 Gateway。
- 跨 Gateway 消息能够正确投递。
- Gateway 故障后客户端可以重新连接。
- 旧连接不会错误清理新连接。
- 路由数据可以恢复。

## 9.6 阶段成果

完成具备横向扩展能力的分布式 Gateway Cluster。

# Phase 5：分布式 Delivery Engine

- Scheduler Partition。
- Retry Scheduler。
- ACK Processor。
- 消息聚合状态。
- 分布式任务恢复。
- 多租户限流。

## 10.4 核心技术问题

- 数据库与消息队列双写如何保证可靠？
- Kafka 重复消费如何处理？
- Worker 崩溃后任务如何恢复？
- 如何避免多个 Worker 同时执行同一个任务？
- 大规模 Fan-out 如何分批处理？

- 消息与 Outbox 能够原子提交。
- Fan-out 可以恢复。
- Worker 可以并行处理。
- Worker 崩溃后任务可以重新领取。
- 重复消费不会破坏业务状态。
- 大规模投递不会无限占用内存。
- 多租户之间具备基础资源隔离。

## 10.6 阶段成果

完成分布式可靠投递引擎。

# 六、工程管理与开发规范

## 12.1 代码规范

- 使用 Go 官方推荐的代码风格。
- 明确模块职责。
- 避免过度抽象。
- 控制接口数量。
- 优先使用标准库。
- 统一错误处理。
- 统一日志格式。
- 关键状态转换必须有测试。
- 并发代码必须考虑生命周期和退出机制。

## 12.2 测试规范

每个模块至少包含：

- Unit Test。
- Integration Test。
- Concurrency Test。
- Failure Test。

涉及并发的代码需要运行：

`go test -race ./...`

性能测试独立维护，避免普通功能测试与压力测试混在一起。

## 12.3 文档规范

每个阶段维护：

- README。
- Architecture Overview。
- Module Design。
- API Specification。
- Data Model。
- Test Report。
- Benchmark Report。
- ADR。

## 12.4 架构决策记录

重要技术选型采用 ADR。

例如：

- ADR-001：为什么使用 Go 标准库 net。
- ADR-002：为什么采用单连接单 Writer。
- ADR-003：为什么使用 Delivery Record。
- ADR-004：为什么引入 Redis。
- ADR-005：为什么使用 Kafka。
- ADR-006：为什么引入数据库分片。

每份 ADR 至少说明：

1. 背景。
2. 当前问题。
3. 候选方案。
4. 选择的方案。
5. 选择理由。
6. 优点和缺点。
7. 后续演进方向。

# 九、第一阶段启动计划

项目启动后，不直接进入千万级架构设计。

首先完成 Phase 0、Phase 0.5 和 Phase 1。

Phase 0.5 作为 Phase 0 的独立优化子项目，在 Phase 0 验收后单独规划，遵循「先基准、后优化」的顺序，不阻塞 Phase 1 的功能建设。

## 第一批任务

1. 创建 Go 项目和基础目录。
2. 实现 TCP Server。
3. 实现 TCP Client。
4. 实现自定义二进制协议。
5. 实现消息编解码。
6. 实现并发连接管理。
7. 实现 Connection 生命周期。
8. 实现 Session 管理。
9. 实现客户端身份绑定。
10. 实现指定客户端消息转发。
11. 实现心跳机制。
12. 实现单连接单 Writer。
13. 实现有界发送队列。
14. 编写单元测试和集成测试。

## 第一阶段明确不做

- Redis。
- Kafka。

- 分布式任务调度。

## 第一阶段验收

完成一个能够稳定运行、支持多个客户端连接、身份识别、消息转发、心跳和断线处理的单机 TCP Gateway。

完成这一目标后，再进入可靠消息系统建设。

# 十、项目成功标准

本项目的成功不以代码量、组件数量或技术复杂度衡量。

真正的成功标准是：

1. 能够独立解释系统中每个核心模块的职责。
2. 能够解释每个关键数据模型为什么这样设计。
3. 能够解释消息从发送到完成 ACK 的完整生命周期。
4. 能够通过测试证明核心状态转换正确。
5. 能够通过故障注入验证系统恢复能力。
6. 能够通过 Profiling 找到真实性能瓶颈。
7. 能够说明每次架构演进的原因和收益。
8. 能够根据容量指标设计下一阶段架构。

**最终目标不是提前写出一个看起来很复杂的千万级系统，而是通过不断解决真实的工程问题，逐步成长为能够设计、实现、优化和演进大型分布式系统的工程师。**
