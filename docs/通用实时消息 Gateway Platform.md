# 通用实时消息 Gateway Platform
# 项目建设与技术成长计划书

**项目名称：** Real-time Messaging Gateway Platform  
**项目定位：** 个人技术成长型工程项目  
**主要技术栈：** Go、TCP、WebSocket、PostgreSQL、Redis、Kafka  
**建设方式：** 渐进式开发、持续验证、按需演进  
**最终目标：** 构建具备千万级扩展能力的通用实时消息 Gateway Platform

---

# 一、项目背景与建设动机

## 1.1 项目背景

本项目并非源于某个具体商业业务需求，而是希望通过建设一个完整的实时消息 Gateway Platform，系统性地学习和掌握后端基础设施开发所涉及的核心技术。

相比于单独学习网络编程、数据库、缓存、消息队列和分布式系统，通过一个完整项目将这些技术串联起来，更容易理解各个技术组件的作用、相互关系以及实际应用场景。

实时消息 Gateway Platform 涉及的技术领域比较全面，既包含底层网络编程，也包含复杂的并发控制、消息可靠性、分布式协调和大规模系统设计，适合作为长期技术实践项目。

# 二、项目定位与建设目标

## 2.1 项目定位

建设一个业务无关、可扩展、具备可靠消息投递能力的通用实时消息 Gateway Platform。

平台只负责消息接入、连接管理、消息路由和可靠投递，不负责任何具体业务逻辑。

业务系统通过标准 API 接入平台，客户端通过统一协议连接 Gateway。

平台不关心消息 Payload 的具体含义，只负责按照约定将消息可靠地送达目标 Endpoint。

## 2.2 项目边界

### 项目建设范围

1. TCP/WebSocket 长连接服务。
2. 统一通信协议。
3. 客户端身份认证。
4. Connection 和 Session 管理。
5. 消息路由。
6. 多设备消息投递。
7. 离线消息持久化。
8. Receipt ACK。
9. Business ACK。
10. 消息重试与 TTL。
11. 多 Gateway 节点管理。
12. 分布式消息投递。
13. 高并发连接管理。
14. 消息可靠性和故障恢复。
15. 客户端身份认证与传输加密。
16. 服务可观测性与运维支撑。
17. 数据生命周期管理。

### 非项目建设范围

1. 用户注册和用户管理。
2. 好友关系。
3. IM 会话管理。
4. 群组管理。
5. 业务消息解析。
6. 业务消息处理。
7. 业务权限系统。
8. 业务数据存储。

## 2.3 核心产品原则

| 维度 | 设计原则 |
|---|---|
| Identity | 业务方定义身份 |
| Endpoint | 一个业务身份支持多个设备 |
| Payload | 业务自定义，平台不解析 |
| Delivery | At-Least-Once |
| ACK | Receipt ACK + Business ACK |
| Offline | 支持离线消息持久化 |

| Tenant | 支持多租户隔离 |
| Architecture | 渐进式架构演进 |

## 2.4 最终建设目标

最终形成一个能够支持以下场景的通用实时消息平台：

- 海量客户端长连接。
- 多 Gateway 节点部署。
- 跨 Gateway 消息路由。
- 大规模消息 Fan-out。
- 可靠消息持久化。
- 多设备独立投递。
- 消息 ACK 和重试。
- 大规模离线消息恢复。
- 分布式任务调度。
- 水平扩展和故障恢复。

需要注意：千万级规模是最终架构能力目标，而不是第一阶段的性能承诺。最终容量以实际硬件、网络、存储和压测结果为准。

# 三、总体建设原则

## 3.1 最小架构起步

第一阶段只建设单进程、单节点系统。

不提前引入 Redis、Kafka、分布式数据库、微服务和 Kubernetes。

先通过最简单的架构验证核心模型和功能正确性。

## 3.2 模块化优先于微服务化

初期采用模块化单体架构。

模块之间通过清晰的接口交互，但仍然部署在同一个进程中。

当出现明确的性能、资源隔离或独立扩缩容需求时，再考虑拆分服务。

## 3.3 先功能正确，再可靠性，最后性能

建设顺序：

1. 网络连接和消息通信。
2. Session 和消息路由。
3. 消息持久化。
4. ACK 和重试。
5. 故障恢复。
6. 高并发优化。
7. 分布式扩展。

## 3.4 通过实际问题驱动架构演进

不为了使用某项技术而引入该技术。

每次架构演进都必须回答：

- 当前架构遇到了什么问题？
- 通过什么指标发现问题？
- 为什么现有架构无法解决？
- 新架构引入了什么机制？
- 新架构解决了什么问题？
- 新架构带来了什么额外复杂性？

## 3.5 每个阶段必须有可验证的交付成果

每个阶段都需要包含：

- 功能实现。
- 核心测试。
- 故障测试。
- 性能测试。
- 技术总结。
- 架构决策记录。

# Phase 0.5：Phase 0 极致优化（标准库内）

## 5.6 阶段目标

在不更换 Go 标准库 net 架构的前提下，用可重复的 Benchmark 与 Profiling 找出 Phase 0 的真实开销，把内存分配、系统调用、定时器与协程模型优化到该架构的合理上限，为 Phase 1 提供高性能传输层基线。

本阶段是 Phase 0 的独立子项目（`phase0.5/`），不覆盖、不修改 Phase 0 代码；后续 Phase 3 的性能对比以 Phase 0 与 Phase 0.5 的数据为参照。

## 5.7 实施内容

先建立基线，再按数据优化，禁止未测量就替换组件。

### 基准与观测

- 为 Encode、Decode、Send 与写循环建立 Benchmark（含 `-benchmem`）。
- 接入 CPU、Memory、Block、Mutex、Goroutine Profiling。
- 记录每个优化项前后的 ns/op、B/op、allocs/op、系统调用次数、RSS 与 P99。

### 内存池化

- 编码 buffer 与解码 Body 分级池化，明确 buffer 所有权与归还时机。
- Frame 对象池；限制池中单个 buffer 的保留上限，避免大帧推高常驻内存。
- 评估 `bufio.Reader/Writer` 大小与连接数带来的内存放大，按场景可配置。
- 只对 Profiling 证明的热点池化，池化后 `allocs/op` 必须下降。

### 写路径

- 批量写：Writer 一次取出多条帧合并写出，减少系统调用。
- 有界队列改为「帧数 + 字节预算」双上限，避免大帧造成内存放大。
- 控制帧（PING/PONG/CLOSE）优先，避免排在数据帧之后。
- 增加写 Deadline，防止对端不读导致 Writer 永久阻塞。

### 读路径

- 读 Deadline 从每帧刷新改为粗粒度空闲扫描，降低 timer 开销。
- 合并每帧的多次时间读取，减少每帧临时对象。
- 调整读缓冲区大小，并用压测验证系统调用与内存的取舍。

### 协议与并发

- 编码避免 `bytes.Buffer` 与接口调用，减少 Body 拷贝（header/body 直接写出）。
- 心跳循环并入 Writer 或改用全局时间轮，降低协程与 timer 数量。
- 仅在 Profiling 显示锁或 channel 竞争时，再评估分片注册表或替代队列。

### 系统参数

- TCP Keepalive、监听 backlog、Socket 缓冲区按实测调整。
- 基准测试在 Linux 容器中执行，避免 Windows IOCP 与 Linux epoll 数据混用。

## 5.8 明确不做

- 不引入 gnet、netpoll 或自研事件循环。
- 不做 CPU 绑核、多 Reactor、GC 参数硬调。
- 不引入 Redis、Kafka、数据库。
- 服务端不做「连接池」（长连接本身即复用）；连接池只属于客户端与后续 RPC 场景。

以上留给 Phase 3 在 Profiling 数据支持下评估。

## 5.9 验收标准

- 存在可重复执行的 Benchmark 与 Profiling 流程。
- 找到至少三个由数据证明的真实瓶颈。
- 至少两轮优化有优化前后对比数据。
- 优化后每消息的内存分配与系统调用数量有量化下降。
- 空闲连接的内存占用与协程数量达到设定目标。
- `go test -race ./...` 通过，协程泄漏检查维持基线偏差不超过 5。
- Phase 0 的功能与协议兼容性不被破坏。

## 5.10 阶段成果

形成优化后的 Phase 0.5 独立子项目、Benchmark/Profiling 报告与相应 ADR，作为 Phase 1 的传输层基线。

- 消息保存后进程崩溃。
- Gateway 推送成功但 ACK 丢失。
- ACK 重复提交。
- 客户端离线。
- Worker 执行过程中崩溃。
- 消息 TTL 到期。
- 数据库暂时不可用。

## 7.6 验收标准

- 消息接受后能够持久化恢复。
- 支持多设备独立投递。
- 支持两级 ACK。
- 重复请求不会产生重复逻辑消息。
- ACK 重复提交不会破坏状态。
- 离线客户端重新连接后可以恢复消息。
- 过期消息不会继续重试。

## 7.7 阶段成果

完成一个单机部署、具备完整可靠投递能力的消息系统。

# Phase 3：单机高并发与性能优化

## 8.1 阶段目标

理解 Go 网络服务的性能边界，掌握性能测试、Profiling 和系统调优。

## 8.2 实施内容

- 并发连接测试。
- 消息吞吐量测试。
- 延迟测试。
- 内存使用分析。
- Goroutine 数量分析。
- GC 分析。
- CPU Profiling。
- Memory Profiling。
- 锁竞争分析。
- 发送队列优化。
- 网络 I/O 优化。
- 消息编解码优化。

## 8.3 压测计划

逐步测试：

- 1,000 个并发连接。
- 10,000 个并发连接。
- 50,000 个并发连接。
- 100,000 个并发连接。

每个连接规模分别测试：

- 空闲连接。
- 心跳。
- 低频消息。
- 高频消息。
- 慢消费者。
- 大 Payload。
- 集中断线和重连。

## 8.4 技术对比

使用标准库 net 建立基准版本。

再根据 Profiling 结果，评估：

- gnet。
- netpoll。
- 更高效的协议编码。
- Buffer Pool。
- 批量写入。

不预设某项技术一定更好。

## 8.5 验收标准

- 建立可重复的压测环境。

# Phase 5.5：生产化加固（Production Readiness）

## 11.1 阶段目标

Phase 5 完成了分布式 Delivery Engine 的架构主干，但它的验证只覆盖「功能正确」与「单点故障恢复」，缺少生产环境必须的六个方面：全局限流正确性、消费者容错、在线扩缩容、安全基线、可观测性、数据生命周期。

本阶段不以增加功能为目标，而是**消除 Phase 5 已知的全部正确性缺陷与运维盲区**，把交付物从「可运行的分布式引擎」提升为「可上生产、可被运维、可被审计」的运行系统。

阶段完成的判定标准不是「代码写完」，而是：**通过生产就绪门禁（Production Readiness Gate）**。

## 11.2 阶段定位与边界

### 与相邻阶段的关系

- **承接 Phase 5**：不推翻 Outbox、Kafka、租约、分片等已验证机制，只修正其缺陷与边界。
- **不越界到 Phase 6**：不做分库分表、多机房、跨地域容灾、千万级容量验证。Phase 5.5 关注的是**正确性与可运维性**，不是规模上限。
- **独立子阶段**：目录 `phase5.5/`，以 Phase 5 最终态为基线复制为独立 Go module，与 Phase 0.5 的处理方式一致。

### 明确不做

- 不实现 Exactly-Once 投递（仍然保持 At-Least-Once + 客户端幂等消费）。
- 不实现跨节点全局消息顺序（只保证单分区内有序）。
- 不引入 Kubernetes Operator、服务网格等新基础设施品类。
- 不实现 WebSocket 接入与 TLS 卸载（TLS 由网关自身终结，卸载留给部署侧）。
- 不做多机房与异地灾备。

相比 Phase 5 的四处结构性变化：

1. **新增 Shard Rebalancer**：虚拟分片的分配与再平衡从「配置里的静态取模」变为「带租约的在线协调」。
2. **Kafka 增加 DLQ 分支**：毒丸消息有独立出口，不再阻塞分区。
3. **Delivery Worker 内部由单循环改为并行 Pipeline**：扫描、续期、消费、清理互不阻塞。
4. **所有进程统一暴露运维端点与统一生命周期契约**：TLS、鉴权、优雅停机、指标、健康检查。

## 11.4 Phase 5 遗留问题与 Phase 5.5 解决方案对照表

本表是本阶段的核心交付物：Phase 5 的每一条已知遗留问题，都必须在本阶段被一个明确的机制和一条可验证的验收口径闭环。

|---|---|---|---|---|
| 1 | Kafka 消费者遇错即退出主循环、无自动重连 | handler 返回 error 直接冒泡到消费循环 | **错误分级**：可重试错误走退避重试，不可重试错误（反序列化失败、协议非法）写入 DLQ 后提交 offset；消费循环外套 supervisor，panic 捕获后重建 consumer，连接失败按指数退避重连（100ms→30s 封顶，带 jitter） | 注入毒丸消息，消费进程不退出、其余消息继续消费；停 Kafka 后恢复，进程自动重连且不丢 offset |

## 11.5 实施内容

### A. 可靠性与错误处理加固

- 消费循环 supervisor：panic 捕获、连接重建、指数退避重连、抖动。
- 错误分级：可重试（超时、连接中断、依赖不可用）与不可重试（编码失败、参数非法、幂等冲突）分别处理。
- DLQ 主题 `relayx.dlq.v1` 与 `dead_letters` 表，落库原始事件体、错误分类、错误文本、首次与最近发生时间。
- 重放 CLI：从 DLQ 重新投递到原始主题，支持按时间范围与租户筛选，幂等由投递唯一键保证。
- 全链路幂等键规范化，并在协议文档中固化。

### B. 租约、分片与优雅停机

- 虚拟分片：新增 `shard_id` 列与 `shard_assignments` 表（Worker 身份、区间、租约、版本、更新时间）。
- 在线 rebalance：扩容劈裂区间、缩容合并区间，迁移期间双读双写，唯一约束保证不产生重复行。
- 租约守护协程：批量续期、超时自动释放、停机主动释放。
- Worker 主循环改为并行 Pipeline：到期扫描、续期、事件消费、过期清理、outbox relay 各自独立。
- 统一优雅停机：停止领取 → 释放租约 → 排空在途 → 提交 offset → 关闭资源；配合 readiness 与 preStop。

### C. 全局限流与多租户隔离

- Redis 全局令牌桶，Lua 脚本原子完成「检查 + 批量扣减 + 发放」。
- Worker 侧批量申请令牌（按周期或按量触发），本地桶作为零 IO 快速拒绝层。
- 租户接入侧限流：Message Service 按 tenant 对受理 API 限流，避免单租户打满受理链路。
- 配额热更新：租户配置变更后无需重启进程即可生效（带缓存 TTL 与版本号）。
- 配额一致性保证：所有租户配额读取失败时按「零配额」保守处理，不因依赖故障放大流量。

### D. 安全基线

- 客户端鉴权：令牌签发与校验、绑定 tenant 与 user、过期校验、吊销名单（Redis）、令牌版本号支持轮转。
- 握手鉴权：把鉴权纳入连接建立流程，未通过鉴权的连接不得进入任何业务路径。
- TLS：Gateway 与 Message Service 支持 TLS 1.2+/1.3，证书热加载；节点间使用 mTLS，双向证书校验。
- 密钥与配置：敏感项只从环境变量或密钥文件读取，启动日志脱敏；提供密钥轮转流程。
- 审计：受理、鉴权失败、踢人、DLQ、重放等管理动作写审计日志，带操作者与来源。

### E. 可观测性与运维

- Prometheus 指标：连接数、活跃会话、收发帧数、队列水位、受理 TPS、投递 TPS、ACK 延迟、outbox 积压深度、Kafka lag、租约持有数与接管次数、重试次数分布、限流次数、DLQ 数量、DB 连接池水位、goroutine 数。
- 健康检查：存活与就绪分离，就绪按 PostgreSQL、Redis、Kafka 三依赖分别判定并暴露明细。
- 结构化日志：统一 JSON 格式，关键字段（traceID、tenantID、messageID、workerID、shardID）可检索。
- 告警规则：outbox 积压、Kafka lag、投递失败率上升、租约接管频次异常、限流占比过高、就绪失败、DLQ 增长。
- 容量基线：集群压测矩阵与容量模型，输出容量报告。

### F. 数据生命周期与可维护性

- 保留策略配置化：消息、投递、outbox、dead_letters 各自的保留窗口。
- 批量归档与清理：分批小事务执行，避免长事务与锁表，清理任务自身可限速、可暂停。
- 维护 CLI：手动清理、按租户重放 DLQ、租约修复（释放僵尸租约）、配额查看与调整。
- 启动配置校验：缺失或非法配置在启动时立即失败并给出明确原因，避免带病上线。

## 11.6 核心技术问题

- **全局配额与本地快速拒绝如何分层**，既保证总速率不超限，又不让每次投递都付出一次 Redis 往返。
- **虚拟分片迁移期间如何不丢不重**，尤其是 Worker 在劈裂过程中崩溃的窗口。
- **租约续期与投递长耗时的关系**，如何界定「仍在处理」与「已经僵死」。
- **优雅停机与至少一次语义的配合**，如何在退出前确认在途消息已经安全落地。
- **DLQ 与重放的幂等边界**，重放是否会产生重复投递行、重复计费。
- **Redis 不可用时各路径的可用性取舍**，哪些路径可以降级、哪些必须拒绝。
- **鉴权放在哪一层**，连接级令牌校验与业务级 tenant 校验如何分层，避免把认证逻辑散落到业务代码。
- **客户端幂等消费的责任边界**，平台保证什么、客户端必须保证什么，如何在协议中写清楚。
- **生产就绪如何被证明**，如何用门禁而不是主观判断来判定阶段完成。

## 11.7 验收标准

### 功能与正确性

- Phase 5 的全部功能与协议保持兼容，客户端与协议帧无破坏性变更。
- 客户端令牌鉴权、TLS、mTLS 全部启用并有负向测试（无令牌、过期令牌、错误证书全部被拒）。
- 全局限流在多 Worker 下满足配额上限，且租户之间互不影响。

### 可靠性

- 毒丸消息进入 DLQ，消费进程不退出，DLQ 可重放并成功完成投递。
- Kafka 停机后恢复，消费进程自动重连，无需人工重启。
- Worker 优雅退出后其租约被立即释放，接管延迟小于一个扫描周期（不再依赖 TTL 超时）。
- 4→8 Worker 在线扩容，无长时间停顿、无重复投递行、无遗漏行。
- 优雅停机过程中消息零丢失、投递行零重复。

### 安全

- 未授权连接被拒绝，且不影响其他正常连接。
- 证书轮转过程无服务中断。
- 敏感配置不出现在日志与进程参数中。

### 可观测性

- 全部进程暴露 `/metrics`、`/healthz`、`/readyz`。
- 依赖故障时 readiness 正确置为失败，且能在指标与日志中定位到具体依赖。
- 至少一条人为制造的故障能触发预设告警。

### 性能与容量

- 交付集群容量报告：受理 TPS、投递 TPS、端到端 P50/P99、Kafka lag、租约接管延迟。
- 给出容量模型与 Phase 6 的规模换算依据。
- Phase 5 已有场景（端到端、故障注入、租户限流）的验证脚本在 Phase 5.5 下全部通过。

### 工程质量

- `gofmt`、`go vet`、`go test ./...`、`go test -race ./...` 全部通过。
- 每个新增机制都有对应单测，且关键状态转换有故障注入覆盖。
- 所有新增决策记录 ADR-019 及以后。

## 11.8 生产就绪门禁（Production Readiness Gate）

Phase 5.5 完成以下全部条目方可判定为生产可用：

| 门禁项 | 判定标准 |

# 七、工程管理与开发规范

## 13.1 代码规范

- 使用 Go 官方推荐的代码风格。
- 明确模块职责。
- 避免过度抽象。
- 控制接口数量。
- 优先使用标准库。
- 统一错误处理。
- 统一日志格式。
- 关键状态转换必须有测试。
- 并发代码必须考虑生命周期和退出机制。

## 13.2 测试规范

每个模块至少包含：

- Unit Test。
- Integration Test。
- Concurrency Test。
- Failure Test。

涉及并发的代码需要运行：

`go test -race ./...`

性能测试独立维护，避免普通功能测试与压力测试混在一起。

## 13.3 文档规范

每个阶段维护：

- README。
- Architecture Overview。
- Module Design。
- API Specification。
- Data Model。
- Test Report。
- Benchmark Report。
- ADR。

## 13.4 架构决策记录

重要技术选型采用 ADR。

例如：

- ADR-001：为什么使用 Go 标准库 net。
- ADR-002：为什么采用单连接单 Writer。
- ADR-003：为什么使用 Delivery Record。
- ADR-004：为什么引入 Redis。
- ADR-005：为什么使用 Kafka。
- ADR-006：为什么引入数据库分片。

每份 ADR 至少说明：

1. 背景。
2. 当前问题。
3. 候选方案。
4. 选择的方案。
5. 选择理由。
6. 优点和缺点。
7. 后续演进方向。

# 十、第一阶段启动计划

项目启动后，不直接进入千万级架构设计。

Phase 0.5 作为 Phase 0 的独立优化子项目，在 Phase 0 验收后单独规划，遵循「先基准、后优化」的顺序，不阻塞 Phase 1 的功能建设。

## 第一批任务

1. 创建 Go 项目和基础目录。
2. 实现 TCP Server。
3. 实现 TCP Client。
4. 实现自定义二进制协议。
5. 实现消息编解码。
6. 实现并发连接管理。
7. 实现 Connection 生命周期。
8. 实现 Session 管理。
9. 实现客户端身份绑定。

完成一个能够稳定运行、支持多个客户端连接、身份识别、消息转发、心跳和断线处理的单机 TCP Gateway。

完成这一目标后，再进入可靠消息系统建设。

# 十一、项目成功标准

本项目的成功不以代码量、组件数量或技术复杂度衡量。

真正的成功标准是：

1. 能够独立解释系统中每个核心模块的职责。
2. 能够解释每个关键数据模型为什么这样设计。
3. 能够解释消息从发送到完成 ACK 的完整生命周期。
4. 能够通过测试证明核心状态转换正确。
5. 能够通过故障注入验证系统恢复能力。
6. 能够通过 Profiling 找到真实性能瓶颈。
7. 能够说明每次架构演进的原因和收益。
8. 能够根据容量指标设计下一阶段架构。

**最终目标不是提前写出一个看起来很复杂的千万级系统，而是通过不断解决真实的工程问题，逐步成长为能够设计、实现、优化和演进大型分布式系统的工程师。**
