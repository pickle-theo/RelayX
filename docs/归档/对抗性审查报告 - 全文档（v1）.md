### 0.2 三项总体判断

1. **冻结线暴露问题，而非保护语义。**
   P0-4（`from_device` 未持久化）与 P0-7（异步 fanout 后无结算点）都是 S2 契约的遗漏，却只能在 S4/S7 暴露。按文档自身纪律（S2 §12.2、A §4.3），S7 无权修，只能"重开冻结线"。这说明：**冻结前的对抗性评审比冻结后的阶段纪律更重要**；冻结机制只能保证"不再变"，不能保证"当初对"。

2. **"只替换传输"掩盖了观察者位置变化带来的语义后果。**
   S7 把 fanout 改为异步、把事件投影搬出进程，改变的是"谁在什么时刻观察事实"。这不是传输替换。凡涉及观察者位置变化的阶段，都应允许一次契约复审，而不是宣称零改动。

3. **文档质量分布不均，S8 的门禁建立在错误基线上。**
   S2/S4/S7 细度最高；S0/S1 稳定；S3 有一个内存安全缺陷，S6 有一个并发原语缺陷；S8 §3 至少 6 项把前序已实现的能力写成"从未建设"，导致门禁清单与真实风险错位。

## 1. P0：阻断级（按现文档实现会得到错误系统）

### P0-1 投递状态多出一个 `SETTLED`

**定位**：A §4.1:220；S2 §3.1:276–277、§7.2:657–671、§12.2:912

**证据**

- A §4.1 契约清单：
  > 投递状态：`PENDING → SENT → RECEIPT_ACKED → SETTLED`；终态 `FAILED` / `EXPIRED`
- S2 冻结的枚举：
  > `('PENDING', 'SENT', 'RECEIPT_ACKED', 'FAILED', 'EXPIRED')`
- S2 投递状态机中 `RECEIPT_ACKED`、`FAILED`、`EXPIRED` 均直接指向 `[*]`（终态），不存在 `SETTLED`。

**判定**：架构方案是全套文档声明的"单一事实来源"，但它定义的投递状态与 S2 冻结枚举相差一个状态。S4 的 `DeliveryCounts`（`total / receipt_acked / failed / expired`）按 S2 实现，反证 A 是笔误。

**影响**：任何按 A 实现的消费者会等待一个永不出现的 `SETTLED`；按 S2 实现则违反"契约唯一"。S8 门禁"状态机不变"失去判定基准。

**修复**：A §4.1 改为 `PENDING → SENT → RECEIPT_ACKED`，终态 `RECEIPT_ACKED / FAILED / EXPIRED`。同步修正 A §4.2（见 P0-2）。

---

### P0-2 A §4.2 把消息状态机与投递状态机画成一张图

**定位**：A §4.2:232–246

**证据**

```text
[*] --> ACCEPTED: 受理并持久化
ACCEPTED --> SENT: 推送到 endpoint
SENT --> RECEIPT_ACKED: 收到 RECEIPT_ACK
RECEIPT_ACKED --> SETTLED: 全部 endpoint 终态结算
FAILED --> SETTLED: 重试耗尽/无端点
EXPIRED --> SETTLED: TTL 到期结算
ACCEPTED --> EXPIRED: 整体过期
```

**判定**：`ACCEPTED` 是消息级状态，`SENT` / `RECEIPT_ACKED` / `FAILED` 是投递级状态，图中每条边都跨越了两个状态机。对照 S2 §7.1（消息：`ACCEPTED→SETTLED` / `ACCEPTED→EXPIRED`）与 §7.2（投递：`PENDING→SENT→RECEIPT_ACKED`），A 的这张图两边都对不上。

**影响**：这张图不能作为实现依据，也不能作为 S8 门禁的比对基线；`EXPIRED --> SETTLED` 更暗示"过期的消息还会结算"，与 S2 §7.1 的 `EXPIRED --> [*]` 相反。

**修复**：拆为两张图，并在消息图旁注明"SETTLED = 所有 delivery 离开 `PENDING/SENT`，含全失败、全过期、零端点"。

### P0-3 S3 广播缓冲区在入队后立即归还（内存安全）

**定位**：S3 §7.1:458 与 §7.1:461

**证据**

- 扇出伪代码步骤 6：
  > `bufferPool.Put(frame.Bytes)  // 所有订阅者已同步入队后归还`
- 紧随其后的"所有权规则"：
  > `ImmutableFrame.Bytes` 在步骤 6 之前必须保持有效。P2 通道的 `TrySendBroadcast` 是同步入队（把只读引用放入有界队列），不做异步持有；**Writer 从队列取出后写出，写出完成前 buffer 不归还**。

**判定**：两条规则不能同时成立。`TrySendBroadcast` 只是把引用放进队列，Writer 是异步取帧写 Socket；"所有订阅者已同步入队"时，没有任何一帧真正写完。步骤 6 一旦执行，下一轮 publish 就会从池中拿到同一块内存并覆盖，导致已入队的广播帧内容被改写。

**影响**：跨 topic / 跨帧数据污染，表现为"弹幕串台"或帧体错乱；`-race` 无法发现（池化天然绕过竞争检测）。这是全套文档中唯一的直接内存安全缺陷。

**修复**：删除步骤 6，所有权规则唯一化为引用计数：`ImmutableFrame` 带 `refs`，入队 +1、Writer 写完 -1、归零后归还池；或退化为"每连接拷贝入队"并在 ADR 中记录性能代价。二者择一，不得并列保留。

### P0-4 事件路由键 `from_device` 从未被持久化

**定位**：S4 §5.3:437–444；S7 §7.2:341；S2 §3.2:302–327；S2 §5.2:483–492

**证据**

- S4 路由逻辑：
  > `key = (tenant_id, producer_id, from_device)`
  > `// from_device 取发送时 SEND 帧的来源设备（S2 已在连接上下文）`
- S7 路由逻辑：
  > 按 `(tenant, from_user, from_device)` 查找发送设备路由（S6 EndpointRouter）。
- S2 的 `messages` 表字段：`id / tenant_id / producer_id / producer_kind / sender / client_msg_id / payload / payload_size / delivery_mode / fanout / ttl_seconds / max_attempts / platform_state / state_version / application_status / created_at / expires_at / settled_at`——**没有来源设备**。
- S2 的 `SEND` 帧字段：`client_msg_id / target_user_id / target_devices / payload / policy`——**没有来源设备**。

**判定**：来源设备只存在于登录后的连接上下文中，且未落库。"连接上下文"是进程内对象：S4 单机阶段重启后即丢失；S7 的 `client-event-router` 是独立进程，只消费 facts，根本拿不到该上下文。facts 的 `endpoint_id` 是**收件人**端点，不是发送设备。

**影响**：单机重启后、以及 S7 全部场景，`MESSAGE_SETTLED` 无法路由到发送设备；S4 §15.2 与 S7 §9.1 宣称的"协议与 schema 零改动"不成立。修复必须改 S2 表结构，按文档自身纪律即为"重开冻结线"——这是全套文档代价最高的一处。

**修复**（三选一，建议 A）：

- A. `messages` 增 `source_device_id TEXT NOT NULL`；服务端从 session 派生写入（**不改 SEND 帧**，客户端无法伪造）；`message.accepted` 事实的 `payload_summary` 带上该值，S7 router 直接从 facts 取。
- B. `delivery_facts` 增加 `source_endpoint_id` 列（改冻结 schema）。
- C. 事件改投给 `producer_id` 的全部在线设备（放弃 self-scoped 精确性，语义退化，不推荐）。

同时更新 A §4.1 身份模型为 `tenant_id + producer_id + source_endpoint + 可选 sender`。

### P0-5 S7 受理事务与 Fan-out Worker 都负责创建 deliveries

**定位**：S7 §4.1:240–243；S7 §4.2:254；S2 §8.1:721–741

**证据**

- S7 §4.1 受理事务：
  > a. INSERT message（幂等）　b. INSERT deliveries　c. INSERT delivery_facts　d. INSERT outbox(subject=command)
- S7 §4.2：
  > ｜Fan-out｜受理写 Outbox｜Fan-out Worker｜按 `tenant|user` 分区展开 deliveries｜

**判定**：同一动作有两个归属。更严重的是，§4.1 的事务内没有端点解析步骤（S2 §8.1 的 `EndpointRegistry.Resolve` 需要读 `endpoints` 表），因此在受理事务里根本不知道要 INSERT 哪些 deliveries；而如果推迟到 fanout，则 §4.1 的 b、c 两项无法执行。

**影响**：实现者只能二选一，两种选择都与另一份文档冲突；`delivery.created` 事实可能被写两次或写不出，破坏 S2 §4.1"状态变更 + 事实同事务"。

**修复**：明确唯一归属。建议：

- 受理事务只写 `message` + `message.accepted` 事实 + `outbox(command=fanout)`；
- Fan-out Worker 在**自己的事务**内写 `deliveries` + `delivery.created` 事实 + 聚合检查；
- 在 S2 §4.1 事务表中增加一行"S7 起：投递行由 fanout 事务创建，事实仍与状态同事务"，作为契约的显式例外记录（而不是宣称"零改动"）。

### P0-6 S7 Delivery Worker 的触发源自相矛盾

**定位**：S7 §2.1:100–106；S7 §4.2:255；S7 §4.3:262

**证据**

- 拓扑图：`KF --> FAN`、`KF --> DW`、`KF --> ER`
- 三条链路表：`可靠投递 | 到期扫描 | Delivery Worker | 租约领取 → 查 S6 路由 → 回推 Gateway`
- Worker 流程：`2. 扫描本分片的到期 deliveries（SQL now() 判定）`

**判定**：DW 在图里是 Kafka 消费者，在流程里是 DB 轮询者。`command` subject 的消费者角色（fanout 还是 delivery）全篇没有定义，消费者组命名、offset 语义、重复消费边界因此全部悬空。

**影响**：S8 §8.1 停机序列中的"提交 Kafka offset"对 DW 无对象；S8 §3 #1"不丢 offset"无法验证；Kafka 分区数与 Worker 并行度之间没有关系定义。

**修复**：定义 `command` 的唯一消费者为 `fanout-worker`（group: `relayx.fanout`），DW 明确为 DB 分片扫描者，并从拓扑图删除 `KF→DW` 边；若确实要 DW 消费 Kafka，则删除 `到期扫描` 路径并重写 §4.2、§4.3。

### P0-7 异步 fanout 后缺少"完成 / 零端点"结算点

**定位**：S2 §7.4:687–698；S2 §7.3:684–685；S7 §4.2:252–256；A §4.2:238

**证据**

- S2 聚合规则：
  > 当且仅当 `platform_state='ACCEPTED'` 且 `NOT EXISTS (delivery WHERE message_id=? AND delivery_state IN ('PENDING','SENT'))` 则 `SETTLED`
- S2 的聚合是**被动**的：只在 Receipt ACK、投递失败、过期三类事件里触发（§4.1 事务表）。
- A §4.2 注释：`FAILED --> SETTLED: 重试耗尽/无端点`。
- S7 未定义 fanout 完成标记，也未定义"fanout 产生 0 条 delivery"时的处理。

**判定**：S7 把 deliveries 的创建移出受理事务后，消息进入一个"没有 deliveries"的中间态。此时没有任何事件会触发聚合；若 fanout 因崩溃重试、目标用户从未登录、或 `Resolve` 返回空集，`message` 会永久停在 `ACCEPTED`，直到 TTL 才变成 `EXPIRED`——而契约要求"无端点即结算"。

**影响**：查询 API 长期返回 `ACCEPTED`，业务无法判定；S4 的 `PendingTracker` 永不释放；`MESSAGE_SETTLED` 缺失。这是"零语义变更"承诺下的实际语义变更。

**修复**：在 S2 契约中增加 fanout 完成语义（需在冻结点前补）：

- `messages` 增 `fanout_done_at TIMESTAMPTZ`（或 `delivery_count INTEGER`）；
- 聚合守卫改为 `fanout_done_at IS NOT NULL AND NOT EXISTS (...)`；
- fanout 事务提交前写 `fanout_done_at`；若本次展开 0 条，同事务内直接结算；
- S7 验收增加用例：`zero-endpoint-settles` 与 `fanout-crash-recovery-settles`。

### P0-8 S6 Version 守卫是 TOCTOU（读—比较—删非原子）

**定位**：S6 §3.3:233–243；S6 §5.3:312–315

**证据**

```text
连接关闭 / 会话替换：
  1. 读取当前 binding
  2. 若 binding.version == 本连接 version：DEL gateway:endpoint:...
  3. 清本地缓存
```

同时 §5.3 声明：
> 路由查询与绑定并发｜Redis 原子 SET/GET；本地缓存最终一致

**判定**：`GET` 与 `DEL` 是两次独立往返，"原子 SET/GET"不能使"比较后删除"变成原子操作。竞态窗口：旧连接读到 `v1` 并判定匹配 → 新连接 `INCR` 得 `v2` 并 `SET` → 旧连接执行 `DEL`，删掉 `v2` 的路由。这正是该机制宣称要防止的场景。

**影响**：跨节点丢失端点路由；该端点后续消息退化为"离线"，直到客户端下次重连；问题偶发、日志上表现为"无绑定"，难以定位。

**修复**：改为 Lua compare-and-delete：

```lua
-- KEYS[1] = gateway:endpoint:{tenant}:{user}:{device}
-- ARGV[1] = 期望的 version
local v = redis.call('HGET', KEYS[1], 'version')
if v == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

绑定侧同样用 Lua 做"INCR + HSET"原子化；版本号存入 HASH 字段而非 JSON 字符串，避免字符串比较歧义。

## 5. 修复后的复核方法

修订完成后，用下面四条做一次回归，任一失败即视为未闭环：

1. **契约落点回归**：把 A §4.1 的每一行，在 S2–S8 中各找一次落点（章节号）。找不到落点的行 = 未落地；出现第二种定义的行 = 分叉。
2. **冻结清单互比**：把 S0–S8 每份的"冻结清单"拼成一张总表，检查同一资产是否出现两个值（本次已发现：投递状态、`0x30` 段、通道数）。
3. **异常路径回归**：对每个 P0，写出一个可执行反例（如"并发 ACL 与过期扫描"、"fanout 0 端点"、"旧清理事件晚到"），在设计中找到对应的守卫语句。找不到 = 仍会出错。
4. **术语 grep**：全库搜索 `三通道`、`S9`、`S10`、`state`（非 `platform_state`/`delivery_state`）、`SEND_EX`、`后移`、`重排`，零命中方可交付。
