## 2. 新发现 P1（2 项）

### P1-1 架构方案 §7 的 S8 验收仍写"零丢失零重复"

**定位**：A §7 S8 验收:496；对照 S8 §8.3:429-454、§12.1:549

**证据**

- A §7：
  > 验收：…毒丸入 DLQ 可重放；**优雅停机零丢失零重复**；…
- S8 §8.3：
  > "零重复"不是可达目标…可承诺的是「零丢失 + 重复有上界且被幂等吸收」
- S8 §12.1：
  > 优雅停机**零丢失**；重复投递有界…**不承诺"零重复"**

**判定**：v1 P1-9 只改了 S8 自身，漏了上位文档的阶段验收行。A 是门禁的依据文档，这行会让 S8 验收同时存在"必须零重复"与"不承诺零重复"两个标准。

**影响**：S8 门禁无法判定；若按 A 执行，At-Least-Once 系统永远无法通过验收。

**修复**：A §7 S8 验收改为"优雅停机零丢失；重复有界且被幂等吸收（S8 §8.3）"。

### P1-2 多实例 Relay 的归属规则无法在 SQL 层执行

**定位**：S7 §4.5:353-364（取批 SQL）、:373（归属规则）；§9.2:529（索引）

**证据**

- 归属规则：
  > 多实例**必须按 `hash(shard_key) % relay_count` 固定归属**：一个 `shard_key` 只由一个 Relay 处理
- 取批 SQL：
  > `SELECT * FROM delivery_facts WHERE published_at IS NULL ORDER BY occurred_at, event_id LIMIT n FOR UPDATE SKIP LOCKED`
- 索引：
  > `delivery_facts (tenant_id, message_id, occurred_at, event_id) WHERE published_at IS NULL`

**判定**：三处对不上：

1. SQL 没有"只取属于我的 `shard_key`"的谓词。Relay A 仍会取到任意 `shard_key` 的行；若这些行不属于它，它只有两个选择：
   - **跳过不发布**：不更新 `published_at`，下一轮又取到同一批 → 饿死/忙等，其他 Relay 也拿不到（行锁释放后仍按 `ORDER BY` 取到同一批）；
   - **发布不属于自己的行**：归属规则失效，乱序回归。
2. `shard_key` 是逻辑键（`tenant|message`），**不是物理列**。要在 SQL 里按 `hash(shard_key)` 过滤，PostgreSQL 需要与 Go 完全一致的哈希实现，且无法用现有索引；文档没有给这个函数。
3. 索引以 `tenant_id, message_id` 开头，但查询是全局 `ORDER BY occurred_at`，索引无法直接提供顺序，会退化为排序全部未发布行。

**影响**：多实例 Relay 在文档层面"可以并行"，在实现层面只能退化为单实例；若强行按归属过滤，则每轮扫描放大到全表未发布行。

**修复**（三选一）：

- A. **默认并唯一支持单实例 Relay**：把"多实例"从 §4.5 与 §13.2 删除，只保留单实例；吞吐不足时再按 ADR 引入。
- B. **加物理列** `delivery_facts.shard_key`（由 FactWriter 写入）+ 索引 `(shard_key, occurred_at, event_id) WHERE published_at IS NULL`，SQL 改为 `WHERE shard_key = ANY($myShards)`；这需要在 S2 冻结前加列（S7 只能"追加列"，可以）。
- C. **按 `tenant_id` 归属**（现有索引可用）：`WHERE tenant_id = ANY($myTenants)`，把"同 tenant 有序"作为保证，弱于"同 message 有序"；需在契约里下调顺序承诺。

无论哪种，都要同步改 §4.5 的 SQL、§9.2 的索引、§4.6 并发维度表，并加用例"两个 Relay 各持一半归属，同时运行 10 分钟，无乱序、无饿死"。

## 5. 结论

1. **三轮审查已收敛**：v1 的语义级矛盾、v2 的类型级缺陷全部闭环；本轮只剩 2 个 P1，其中一个（A 的"零重复"）是文字残留，另一个（S7 Relay 归属）是"规则写了但机制没写"。
2. **唯一需要决策的是 P1-2**：多实例 Relay 要么承认只支持单实例，要么给 `delivery_facts` 加 `shard_key` 物理列。这是设计选择，不是缺陷——但必须在 S2 冻结点前决定，否则又是一次"冻结后改契约"。
3. **建议的收尾动作**：改 A §7 一行、S7 §4.5/§9.2 三处、其余 P2 十处措辞；然后以"新 P1-2 的选型 + 现有冻结清单"作为 S2 冻结点，进入 S0 实现。

> 一句话：文档已经从"不能照着写"变成"照着写能跑，只有一处并行归属需要拍板"。可以开工。
