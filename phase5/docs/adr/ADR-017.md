# ADR-017：行级租约与分片调度

- 状态：已接受（Accepted）
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/store/lease.go`、`internal/engine/engine.go`、`internal/config/worker.go`、`cmd/delivery-worker/main.go`
- 关联文档：[Engine 设计](../engine-design.md)、[架构说明](../architecture.md)、[ADR-016](ADR-016.md)

## 1. 背景

Phase 5 把投递从 Gateway 移到独立的 Delivery Worker，并且允许部署多个 Worker。`deliveries` 表是共享真值，多个 Worker 同时扫描会出现两个问题：

- 同一行被两个 Worker 同时推送：客户端收到重复 DELIVER，`attempts` 被重复计数，甚至状态互相覆盖。
- 一个 Worker 领到行后崩溃：如果没有超时机制，这行永远不会再被处理。

同时，单表扫描在行数增长后会成为瓶颈，需要一种与 Worker 数量匹配的静态切分方式。

## 2. 问题

1. 如何保证同一时刻只有一个 Worker 处理某一行。
2. Worker 崩溃后，未完成的行如何在有限时间内被接管，且不被旧 Worker 覆盖。
3. 如何让多个 Worker 并行扫描而不互相阻塞。
4. 如何在不引入额外协调组件的情况下完成切分与扩缩容。
5. 租约时长如何取值，过长与过短分别有什么后果。

## 3. 候选方案

### 3.1 单 Worker，无租约

只允许一个 Delivery Worker，扫描全表。

- 优点：实现最简单，不存在并发与接管问题。
- 缺点：无法水平扩展；Worker 崩溃期间投递完全停止；无法滚动升级；单点吞吐上限明显。
- 结论：不采用。

### 3.2 全局咨询锁 + 单扫描者

用一个 PostgreSQL advisory lock 保证同一时刻只有一个 Worker 扫描。

- 优点：实现简单，行级竞争为零。
- 缺点：退化为单 Worker 吞吐；锁持有者崩溃后要等连接断开才能释放；无法并行。
- 结论：不采用。

### 3.3 Redis 分布式租约

每个 Worker 在 Redis 中为投递行抢 `SET NX PX` 租约。

- 优点：抢锁快，TTL 自动过期。
- 缺点：租约与投递状态不在同一事务，Redis 与 PostgreSQL 不一致时会出现「有租约但行已被改」或「行可领但租约还在」；Redis 故障会阻断投递；需要额外的续期与清理逻辑。
- 结论：不采用。可靠性数据已经全部在 PostgreSQL，租约也应放在同一事务边界内。

### 3.4 行级租约 + `SKIP LOCKED` + 静态分片（本决策）

在 `deliveries` 上增加 `lease_until` 与 `worker_id`，用 `FOR UPDATE SKIP LOCKED` 领取，用 `mod(delivery_id, shards) = shard_index` 切分扫描范围。

- 优点：租约与状态更新在同一数据库、同一事务语义内；`SKIP LOCKED` 让并发扫描不排队；分片把扫描成本按 Worker 数量摊开；崩溃靠 TTL 自动接管。
- 缺点：租约是「时间约定」而非强互斥，时钟与执行时长会影响重复推送；分片是静态配置，扩缩容需要整体切换；ID 取模不是一致性哈希，扩分片会迁移全部行。
- 结论：采用。

## 4. 决策

### 4.1 字段与索引

`deliveries` 新增：

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `lease_until` | `TIMESTAMPTZ` | 租约到期时间；`NULL` 表示可领取 |
| `worker_id` | `TEXT` | 持有者标识 |

```sql
CREATE INDEX IF NOT EXISTS deliveries_due_idx
    ON deliveries (next_retry_at, id)
    WHERE state IN (0, 1);
```

索引只覆盖未终结的投递；`next_retry_at` 在前、`id` 在后，匹配 `ORDER BY next_retry_at NULLS FIRST, id`。

### 4.2 领取

`ClaimDueDeliveries` 的 CTE：

```sql
WITH due AS (
    SELECT d.id
    FROM deliveries d
    WHERE d.state IN (0, 1)
      AND (d.next_retry_at IS NULL OR d.next_retry_at <= now())
      AND (d.lease_until IS NULL OR d.lease_until <= now())
      AND mod(d.id, $shards) = $shardIndex
    ORDER BY d.next_retry_at NULLS FIRST, d.id
    LIMIT $limit
    FOR UPDATE SKIP LOCKED
)
UPDATE deliveries d
SET lease_until = now() + $ttl, worker_id = $workerID, updated_at = now()
FROM due
WHERE d.id = due.id
RETURNING ...
```

要点：

- 到期判断与租约写入使用调用方传入的 `now`：Engine 在 `RunOnce` 里取 `time.Now()`，`lease_until = now + lease_ttl`。因此**接管时机受 Worker 本机时钟影响**；`updated_at` 仍由数据库 `now()` 写入。
- `SKIP LOCKED` 跳过其它事务已锁定的行，多 Worker 并发扫描不会相互等待。
- 领取只写租约，不改 `state`；状态只由推送结果或重试决定。

### 4.3 条件更新与接管

所有状态更新都要求 `worker_id` 匹配：`MarkDeliverySentLeased`、`RetryLeased`、`ReleaseLease`。

- 租约过期且被另一个 Worker 接管后，旧 Worker 的更新影响 0 行：推送成功路径计为 `released`，不会把新 Worker 的状态覆盖。
- 主动放弃时 `ReleaseLease` 清空 `lease_until` 与 `worker_id`，让其它 Worker 立即领取，而不是等 TTL。
- 状态写入同时也清空租约，避免「已完成但仍显示被持有」。

### 4.4 租约 TTL

- 默认 `-lease-ttl 30s`，必须大于单批处理耗时与最慢的一次 `NODE_DELIVER` 往返。
- 过短：正常处理中的行会被其它 Worker 抢走，产生重复推送。
- 过长：Worker 崩溃后接管延迟变大，消息延迟随之上升。
- 接管延迟上界约为 `lease_ttl + scan_interval`。
- `store.RenewLeases` 提供按 `worker_id` 续期，但当前 Engine 未调用：一批投递在单轮内处理完，租约只服务于崩溃接管。若未来引入长耗时推送，应在处理中途续期。

### 4.5 分片

- 规则固定为 `mod(delivery_id, shards) = shard_index`，不是哈希，也不是区间。
- `-worker-shards` 至少为 1；`-worker-shard-index` 必须落在 `[0, shards)`，配置层启动即校验。
- 推荐每个 Worker 一个互不重复的 `shard_index`，`shards` 等于 Worker 数。
- 允许两个 Worker 使用相同 `shard_index`：正确性由 `SKIP LOCKED` 与租约保证，只是扫描重复。
- 分片扩容：`shards` 改变后所有行的归属都变化。必须停掉全部 Worker、统一修改配置后一起启动；滚动的、不同 `shards` 的混合部署会出现「某行没有任何 Worker 负责」的窗口。

### 4.6 过期行

`process` 发现 `ExpireAt <= now` 时不推送，调用 `ReleaseLease` 并计入 `released`。最终状态由 Worker 每轮的 `ListExpiredMessages` + `ExpireMessage` 写入 EXPIRED（`state = 5`），这部分不依赖租约。

## 5. 后果

### 5.1 正面

- 同一行在租约期内只被一个 Worker 处理，状态更新带 `worker_id` 条件，接管后旧 Worker 无法回写。
- Worker 崩溃无需人工介入，租约到期后自动接管，接管延迟有明确上界。
- 多个 Worker 共享同一张表并行工作，不需要额外的协调服务。
- 租约与投递状态在同一数据库事务内，不存在跨系统不一致。
- 分片把扫描限制在 `1/shards` 的行上，索引扫描成本随 Worker 数下降。

### 5.2 负面

- 租约不是强互斥：推送耗时超过 TTL、或数据库与 Worker 时钟偏差较大时，可能重复推送。系统按至少一次设计，客户端必须去重。
- 崩溃瞬间已入队但未落库的行会重推，`attempts` 可能略高于实际送达次数。
- 分片是静态的，扩缩容需要停机统一切换；`mod(id, shards)` 在扩容时几乎所有行都会迁移，无法做到只迁移一小部分。
- `deliveries_due_idx` 只覆盖 `state IN (0,1)`，历史行不进入索引，但表本身仍会增长，需要归档策略。
- 两个 Worker 使用同一 `shard_index` 虽然正确，但会放大数据库扫描与锁竞争，属于配置错误而非设计目标。

## 6. 状态

已接受。若未来需要在线扩缩容，可以改为一致性哈希或按虚拟分片映射，但需要同时解决「迁移期间行归属」的问题；当前规模下停机切换可接受。
