# ADR-014：节点直连数据面与 versioned route

- 状态：Accepted
- 日期：2026-11-11
- 决策者：项目作者
- 相关代码：`internal/cluster/hub.go`、`internal/protocol/node.go`、`internal/gateway/gateway.go`、`internal/delivery/worker.go`
- 关联文档：[架构说明](../architecture.md)、[节点协议](../protocol-node.md)、[ADR-013](ADR-013.md)、[ADR-015](ADR-015.md)

## 1. 背景

引入 Redis 注册表（ADR-013）后，发送方可以知道目标设备在哪个节点，但还需要把 DELIVER 和“踢掉旧会话”的请求送到该节点。Phase 4 的可靠性目标是：

- 跨节点实时转发走低延迟通道。
- 转发链路断开时，消息不能丢；已经持久化的投递必须最终被客户端取走。
- 节点间不需要强一致的顺序；不能为了顺序牺牲可用性。
- Redis 不承载消息 payload。

## 2. 问题

需要在以下方案中选择节点间数据面：

1. 消息 payload 是否经过 Redis。
2. 节点间使用什么协议与连接模型。
3. 转发失败时由谁重试，重试与 PULL 如何配合。
4. 如何处理慢节点、断链和节点 ID 冲突。

## 3. 候选方案

### 3.1 Redis Pub/Sub 传 payload

发送方把 DELIVER 发布到“目标节点”频道，目标节点订阅并投递。

- 优点：实现简单；复用 Redis 连接；不需要节点地址发现。
- 缺点：Pub/Sub 是 at-most-once，订阅者断线期间的消息永久丢失；没有 backlog 与确认；Redis 故障或重启会同时打断所有转发；payload 经过 Redis 会增加内存与带宽压力，并受 Redis 客户端缓冲/输出限制；无法提供有界队列与 TCP 背压。
- 结论：不采用。Redis 仍然只做控制面。

### 3.2 Redis Streams

用 Stream 作为节点间队列，消费组按节点消费。

- 优点：有持久化与 ack，断线后可重放。
- 缺点：引入了第二套持久化消息路径，与 PostgreSQL 的 `deliveries` 重复；消费组、pending、claim、裁剪策略复杂；Redis 故障时数据面仍然中断；消息多一次网络跳转。
- 结论：不采用。可靠性已经由 PostgreSQL 的 SENT 行 + 重试 + PULL 承担。

### 3.3 HTTP / gRPC

节点暴露内部 HTTP 或 gRPC 接口，发送方逐条调用。

- 优点：生态成熟，便于调试与观测。
- 缺点：每条消息一次请求/响应，吞吐与延迟不如长连接；需要引入 HTTP/gRPC 依赖与序列化；仍然要自己做队列、超时与重试。
- 结论：不采用。

### 3.4 直连 TCP + 复用现有帧协议（本决策）

每个节点监听内部端口，按需与目标节点建立长连接，复用 21 字节帧头与 CRC 校验，新增 5 种节点帧。

- 优点：数据面与 Redis 解耦；长连接摊薄握手成本；有界发送队列提供背压；协议与客户端协议同源，编解码与测试可复用；失败可以快速回退到数据库重试/PULL。
- 缺点：需要自己实现握手、连接管理、队列与重连退避；明文传输，只适合内网；节点地址需要由 Redis 提供且必须互通。
- 结论：采用。

## 4. 决策

1. 节点间使用直连 TCP；每个节点一个内部监听地址（`-node-addr`），并向其他节点通告 `-node-advertise-addr`（为空时回退到 `-node-addr`）。
2. 不为所有节点预建全连接。Hub 在需要转发或踢人时按 `node_id` 查找已有 peer，没有则拨号；连接建立后保持，直到出错或进程退出。
3. 每个 `node_id` 最多保留一个 peer。新连接替换旧连接，旧连接以 `replaced by new connection` 关闭。
4. 节点帧为 `NODE_HELLO(0x10)`、`NODE_HELLO_ACK(0x11)`、`NODE_DELIVER(0x12)`、`NODE_DELIVER_ACK(0x13)`、`NODE_KICK(0x14)`；帧头仍为 21 字节，字段与旧帧完全一致。
5. `ForwardDeliver` 在帧进入 peer 的有界队列后即返回，不等待对端 ACK；`NODE_DELIVER_ACK` 会被读取和校验，但不驱动发送方的同步重试。
6. 路由携带单调版本号；踢人请求携带版本号，接收方只关闭版本更旧的本地会话。

## 5. 帧设计

完整线格式见 [protocol-node.md](../protocol-node.md)，这里只说明设计意图。

| 帧 | 方向 | 关键字段 | 说明 |
| --- | --- | --- | --- |
| `NODE_HELLO` | 拨号方到监听方 | protocolVersion、nodeID、advertiseAddr | 声明身份与回拨地址；必须是连接上的第一帧 |
| `NODE_HELLO_ACK` | 监听方到拨号方 | status、message | 0 表示接受；非 0 时拨号方关闭连接 |
| `NODE_DELIVER` | 任意节点到 owner 节点 | user、device、fromSessionID、fromUser、fromDevice、payload | 帧头 MsgID 复用平台消息 ID，目标节点回 ACK 时原样带回 |
| `NODE_DELIVER_ACK` | owner 节点到发送方 | status、message | 表示目标节点是否在本地会话上完成了入队；当前仅消费，不参与重试判定 |
| `NODE_KICK` | 新登录节点到旧节点 | user、device、version | 关闭版本更旧的本地会话；没有 ACK |

所有字符串都是 `uint16` 长度前缀 + 原始字节；身份字段长度范围 `[1, 64]`，node ID `[1, 64]`，通告地址 `[1, 128]`，ACK 文本 `[0, 128]`。`MsgID` 与 `payload` 均为二进制安全。

`NODE_DELIVER` 的 body 不重复携带目标节点 ID：node ID 已经由连接身份确定，避免 body 与连接身份不一致时产生歧义。接收方按 `(user, device)` 在自己的本地会话表中查找。

## 6. 单写协程、有界队列与退避

Hub 为每个 peer 启动一个读协程和一个写协程：

- 发送路径只做编码与非阻塞入队，实际 `Write` 全部由写协程串行完成，因此同一 peer 上的帧不会交错，出队顺序即入队顺序。
- 每个 peer 的队列默认 256 帧、4 MiB。字节预算或帧槽位耗尽时立即关闭该 peer 并返回 `ErrQueueFull`，不做无限缓冲，也不阻塞业务协程。
- 写超时默认 5s；读循环使用 `-max-body`（默认 1 MiB）限制单帧 body。
- 拨号超时默认 1s。拨号失败按节点记录指数退避：首次 100ms，逐次翻倍，上限 2s；在退避窗口内直接返回 `ErrBackoff`，避免对已死节点反复阻塞。
- 连接成功注册 peer 时清除该节点的退避状态。
- 半开连接依靠 TCP 写失败或读错误发现；没有应用层心跳。节点存活由 Redis TTL 判断，节点间链路存活由 TCP 与写超时判断。

队列满时选择关闭连接而不是丢单条帧，原因是：单条丢弃会让上层误以为转发成功；关闭连接会让本次 `ForwardDeliver` 返回错误，后续消息会重新拨号，若拨号失败才进入退避，丢失的实时帧由数据库重试/PULL 兜底。

## 7. 端到端 at-least-once 如何成立

Phase 4 不承诺端到端 exactly-once。可靠性链条如下：

1. 发送方在返回 `SEND_ACK` 之前，先在 PostgreSQL 中原子写入 `messages` 与 `deliveries`。
2. 目标被判为在线（本地会话存在，或远程路由存在且节点存活）时，投递行状态为 SENT，`attempts = 1`，并按退避基数设置 `next_retry_at`；否则为 PENDING。
3. 本地目标直接投递；远程目标通过 `ForwardDeliver` 入队。转发本身是单跳、at-most-once：进程崩溃、链路中断、队列满都可能让这一帧丢失。
4. 目标节点收到 `NODE_DELIVER` 后只在本地会话上投递，不写数据库。投递成功返回 `NODE_DELIVER_ACK OK`；会话不存在返回 `NOT_FOUND`。发送方当前不根据 ACK 改变状态，因此 ACK 丢失不会造成额外问题。
5. 客户端收到 DELIVER 后发送 `RECEIPT_ACK` 或 `BUSINESS_ACK`，owner 节点据此清除该投递行的重试调度（或标记终态）。
6. 如果没有收到客户端回执，owner 节点的重试 worker 会按指数退避重新向本地会话投递，直到达到最大尝试次数或回执到达。
7. 如果 owner 节点已经死亡、路由已被回收，任何节点在重试扫描时都可以清除该行的重试调度；行仍保留在数据库中，客户端重新登录后通过 PULL 取走。
8. PULL 会返回 `PENDING` 和 `SENT` 两种状态的行（按投递 ID 升序、游标分页），因此“已转发但未确认”的消息不会因为节点崩溃而永久卡住。

由此得到的是 at-least-once：转发成功但 ACK 丢失、客户端回执丢失、PULL 与实时投递竞争，都可能产生重复 DELIVER。客户端应按平台消息 ID 去重，或接受至少一次语义。

## 8. 跨节点重试归属

重试 worker 按以下顺序判断一条 SENT 投递由谁处理：

1. 本地存在该 `(user, device)` 的会话：本节点就是 owner，直接重试投递；成功后更新尝试次数与下次重试时间，超过上限标记失败。
2. 本地没有会话，但 Redis 路由存在且路由指向的节点存活：本节点不是 owner，跳过，不写数据库，保留原有重试调度。
3. 本地没有会话，且路由不存在或指向的节点已死亡：清除重试调度；行保持 SENT，等待客户端 PULL。

这样设计的目的：

- 只有 owner 节点会修改投递行，避免多个节点同时增加 `attempts` 或重复标记失败。
- 非 owner 不写库，避免在路由刚刚迁移时与 owner 竞争。
- owner 死亡后，其它节点不需要接管实时转发；等路由被回收后清除调度，把恢复责任交给 PULL。
- 如果 owner 存活但节点间链路中断，owner 仍能在本地完成重试，不依赖链路恢复。

需要注意一个窄窗口：路由仍指向本节点、但本地会话已经不存在时，worker 会把该路由视为“属于存活节点”而跳过，保留调度。正常情况下会话关闭会立即用版本 CAS 删除路由，窗口很短；即使残留，PULL 也能恢复。

## 9. 限制

- `SEND` 的 `endpoint:<session_id>` 定向只在本地会话表中查找，session ID 不是全局唯一，因此不能跨节点定向投递。跨节点场景应使用 `user` 目标。
- 不保证跨节点顺序。单个 peer 的发送队列保持该连接上的 FIFO，但不同来源、重试、PULL 与实时投递之间没有全局顺序；客户端不能依赖跨节点消息的到达顺序。
- 节点间只有单跳转发，没有经过第三个节点的中继；两个节点之间必须网络可达。
- 明文传输，没有 TLS、认证或授权；内部端口不得暴露到公网或不可信网络。
- `NODE_KICK` 是尽力而为：没有 ACK、没有重试。链路故障时旧会话不会被关闭，会一直保持到它自然断开；由于路由已指向新节点，按 `user` 目标发送的新消息不会再路由到旧会话，也不会造成双份投递。旧节点上的本地 `endpoint:<session_id>` 定向发送仍可能命中该残留会话。
- 慢节点通过关闭连接处理，不提供跨节点的流量控制或优先级。
- 节点 ID 的唯一性由部署方保证；重复 ID 会导致连接反复替换。
- `-max-body` 决定节点帧 body 上限，所有节点应配置为兼容的值，否则大消息会在接收侧被拒绝。

## 10. 状态

Accepted。后续如需跨节点顺序、TLS 或中继转发，应新增 ADR，并明确这些能力对延迟、可靠性与运维复杂度的代价。
